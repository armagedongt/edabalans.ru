Навигационная сводка по origin/main на 16.09.2026, не новый канон. БД не читалась,
текущая доставка/maintenance не проверялись. Физические документы root старой
ветки могут отличаться. Читать полные источники по ссылкам перед изменением.
Тексты здесь не создаются и не публикуются. Навыки: писатель для редактуры текста,
библиотекарь для поиска, code-writing для изменения поведения.

## Welcome: Telegram

Полные правила: [WELCOME_INTENSIVE](../../../docs/knowledge-base/modules/telegram/WELCOME_INTENSIVE.md).
Найденные MD сообщений: [Интенсив](Интенсив.md).
Рабочая схема сообщений v3 [отдельно](../../free-intensive-rebuild/bot-message-catalog-v3.md):
она помечена рабочей, не реализованной; не путать с описанием main Welcome.

| Этап по выбранному main-документу | Время и условие |
|---|---|
| Первый допустимый вход | Кружок, затем обычный/Яндекс вход с кнопкой части 1 |
| Напоминание части 1 | +15 минут, если день не открыт и единственное напоминание ещё не использовано |
| Промежуточный материал 1 | +12 часов, выбор по подписке и каноническому тегу |
| Часть 2 | +24 часа от входа |
| Проверка открытия части 2 | +8 часов; напоминание, если ещё не использовано |
| Промежуточный материал 2 | +12 часов без напоминания или +14 после напоминания |
| Части 3 и 4 | Каждая +24 часа от фактической отправки предыдущего дня |
| Проверки частей 3/4 | Та же восьмичасовая проверка и единый лимит напоминания |
| Финальное предложение | +24 часа после части 4; закрепление, затем отдельная картинка |
| Дальше | Передача в prepurchase_nurture |

Промежуточный пост/напоминание не сдвигают следующий день. Покупатель в Welcome
не попадает; покупка во время цепочки централизованно завершает presale.
Повтор Start не перезапускает расписание: продолжение активного run, завершённая
выдача, legacy-вход и покупатель имеют разные входные тексты.

Подписка проверяется тихо и выбирает полный/ссылочный вариант поста, но не
блокирует интенсив. Ошибка проверки идёт по безопасной неподписанной ветке.
У вариантов одного материала один канонический тег; тег назначается после
успешной доставки. Точные template IDs, links и tags — в полном документе.

## Welcome: MAX

[Полный MAX-контракт — проверенный main](https://github.com/armagedongt/edabalans.ru/blob/99051db9b3e3435861e220d95e2cb7a516481157/docs/knowledge-base/modules/max/START_AND_ATTRIBUTION.md). Его физического файла в старом root нет; это Git-снимок для чтения, не редактируемый source в текущем vault.

Один общий Welcome-граф, не самостоятельная вторая цепочка. MAX:
не проверяет Telegram-подписку; использует полный промежуточный текст;
не закрепляет финальный пост. Адаптер заменяет Telegram-ссылки на MAX-эквиваленты.
Доступность конкретной замены определяется контрактом, не ручным дублем поста.
Старые MAX-пользователи запускают цепочку следующим явным входом, не задним числом.
Payload iz1/iz2/iz3 выдаёт существующие финальные задания в диалоге.

Общие массовые и послепокупочные рассылки в проверенную границу MAX пока не входят.
Не создаём пустые «MAX-копии» таких сообщений.

## До покупки: prepurchase_nurture

[Полные правила](../../../docs/knowledge-base/modules/telegram/PREPURCHASE_NURTURE.md).

Вход после Welcome; полезные/продающие материалы до покупки.
По схеме документа: дни 1–10 ежедневно, затем дни 12–24 через день,
день 25 завершает run. Указаны 17 редакционных окон.
Это описание выбранной документальной схемы, не сегодняшнее число активных
сообщений в БД. В документе есть production и maintenance ограничения.

Дедупликация по существующему тегу материала: уже полученное пропускается,
в том же слоте выбирается следующий доступный материал, не выдаётся серия
накопившихся постов подряд. Первая дата получения не затирается.
Покупка останавливает run центральным lifecycle, не одинаковыми проверками в
каждом посте. Реализация новой дедупликации в документе отделена от текущего графа.

## После покупки/присоединения к Мастер-классу

[Полный контракт, таблица слотов и условия](../../../docs/knowledge-base/modules/telegram/POST_PURCHASE_MASTERCLASS.md).

Это событийное сопровождение, не последовательное проигрывание всего графа.
Graph disabled как самостоятельная sequence; сообщения запускает outbox-dispatcher.

| Редакционный слот | Событие/условие | Пропуск/отмена |
|---|---|---|
| PP_IDENTITY | Погашена одноразовая ссылка, Telegram связан с user_id | Конфликт CRM, истёкший/повторный token |
| PP_QUESTIONNAIRE | После стартовой сводки есть анкета | Если анкеты нет — понятное пустое состояние |
| PP_DAY_UNOPENED_18H | В 18:00 местного времени доступный день ещё не открыт | Открыт день, завершён курс, стоп-тег, нет доступа |
| PP_COURSE_STALLED | 72 часа нет новой активности незавершённого курса | Новая активность, завершение, стоп-тег, нет доступа |
| PP_EARLY_MISSING | Последний шанс early/second; рецептов нет | Покупка, возврат, нет допустимого предложения |
| PP_EARLY_OWNED | Тот же сигнал, рецепты куплены, есть другой продукт | Всё куплено/предложение запрещено |
| PP_CLOSING_REVIEW_COPY | Участник отправил итоговое саморевью | Нет Telegram-привязки/активного доступа |
| PP_FINAL_OFFER | Последний шанс last_week; есть допустимый продукт | Всё куплено, окно истекло, стоп-тег |

Полные дополнительные DQS/рецептурные события, условия ожидания привязки,
переменные и медиа находятся в контракте; таблица выше — вход к нему, не замена.
Ключевые события включают явный запрос ссылки DQS, первое открытие приложения,
рецептурные точки и отправку саморевью.

**Документальное расхождение:** начало POST_PURCHASE_MASTERCLASS говорит
test-only и POSTPURCHASE_TEST_ONLY=true, а далее ссылается на approved requirements
как основание production-выпуска. В этой задаче не выясняется live-состояние.
Не называем цепочку массово включённой и не исправляем противоречие в каноне.
[Согласованные требования onboarding/открытия дня](../../../docs/plans/MASTERCLASS_TELEGRAM_ONBOARDING_AND_DAY_OPEN_DRAFT.md).

После завершения МК postmasterclass_nurture — отключённый пустой каркас:
не обещаем отсутствующие сообщения через 2/4/7 дней.
[Канонический документ](../../../docs/knowledge-base/modules/telegram/POSTMASTERCLASS_NURTURE.md).

## Ручные ответы и разовые рассылки

[Полный контракт входящих и рассылок](../../../docs/knowledge-base/modules/telegram/INBOX_AND_BROADCASTS.md).

Ручная переписка отдельно сохраняет входящие и исходящие сообщения.
Telegram Bot API не даёт отметку «прочитано»; она не выдумывается.

Разовая рассылка: draft → preview текста и числа получателей → при необходимости
тест владельцу → подтверждение аудитории → отправка/расписание → результаты.
После запуска история неизменяема; повтор текста — новый draft.
Повторяются только failed deliveries. Maintenance ограничивает аудиторию allowlist.
Эта сводка не разрешает отправку реальным людям.
