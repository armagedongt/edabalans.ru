# Список работ: модульная карта и память проекта

Статус: `current task list`  
Дата: 25.08.2026

## 1. Зафиксировать общий язык проекта

1. Определить и закрепить иерархию: платформа → область/продукт → модуль → компонент → программный символ.
2. Зафиксировать, когда владелец просит сделать модуль, функцию, инструмент, страницу, документ или разовую операцию.
3. Определить признаки самостоятельного модуля: цель, входы, выходы, правила, владелец данных и отдельный жизненный цикл.
4. Запретить создание модуля ради одного файла, таблицы, тега или вспомогательной функции.
5. Зафиксировать правило: каждый tracked-файл, скрипт, маршрут, таблица и значимый программный символ принадлежит одному модулю-владельцу; generated outputs отмечаются отдельно как производные артефакты системы карты.
6. Общие компоненты относить к отдельным системным модулям, а не дублировать в продуктовых модулях.
7. Ввести временную категорию `needs_classification` для найденных бесхозных объектов; она должна считаться долгом и не становиться постоянной свалкой.

## 2. Создать единый реестр модулей

8. Спроектировать структурированный канонический реестр модулей.
9. Для каждого модуля хранить название, понятное описание, тип, родителя, статусы документа и реализации.
10. Указывать канонические источники фактов, каталоги и файлы кода, таблицы, маршруты, фоновые процессы и административные инструменты.
11. Указывать входящие и исходящие события, зависимости, потребителей и переиспользуемые части.
12. Привязывать к модулю планы и человекочитаемые примечания без копирования их текста.
13. Заполнить первоначальную карту всеми действующими, разрабатываемыми и явно запланированными модулями проекта.
14. Не смешивать работающие модули с отложенными идеями: отображать состояния явно.

## 3. Построить автоматический технический инвентарь

15. Сканировать весь tracked-репозиторий; во всех каталогах находить файлы, а в исходном коде — Python-функции/классы, API-маршруты, SQLAlchemy-таблицы и основные frontend-символы.
16. Сопоставлять найденные объекты с модулем по правилам реестра.
17. Генерировать машинный JSON-инвентарь и человекочитаемую Markdown-карту.
18. Показывать для каждого объекта его владельца и исходный путь, не копируя исходный код.
19. Находить бесхозные объекты, пересечение владельцев, несуществующие пути, битые ссылки и незарегистрированные таблицы.
20. Добавить проверку в CI, которая не пропускает новый tracked-файл без модуля-владельца и применяет более глубокие route/table/symbol проверки к production-коду.
21. Не требовать ручного перечисления каждой функции в Markdown: подробный список должен генерироваться из кода.

## 4. Перестроить документацию и Wiki

22. Оставить Markdown в Git единственным источником документации.
23. Превратить существующую Wiki в интерфейс чтения, а не отдельную базу знаний.
24. Разделить в интерфейсе памятку владельца, карту модулей, рабочие инструкции, технические документы и планы.
25. Создать короткое руководство владельца: как ставить задачи, что такое plans, local, commit и «отправить на сервер».
26. Сделать карточку каждого модуля конечной точкой дерева с человеческим смыслом и ссылками на технический инвентарь.
27. Убрать или архивировать доказанно устаревшие и дублирующие документы; вместо копий оставить ссылки на канон.
28. Унифицировать статусы документов и отдельно отображать состояние реализации.
29. Обновить `docs/README.md` как короткую точку входа, а не полный ручной список всех объектов.

## 5. Обновить `/control`

30. Сохранить `/control` каталогом независимых специализированных инструментов.
31. Добавить понятные разделы: инструменты, карта системы, как работать с проектом, планы и технические документы.
32. Добавить дерево модулей с поиском, фильтрами по статусу и раскрытием карточки.
33. Строить дерево и карточки только из канонического реестра и Markdown, без ручного редактора карты.
34. Не объединять специализированные админки в один монолит и не унифицировать их дизайн без функциональной необходимости.
35. Оставить NocoDB с отдельным входом и не развивать его в рамках этой задачи.

## 6. Переписать постоянные правила для новых чатов

36. Сократить и структурировать `AGENTS.md`: обязательный старт, маршрутизация по модулям, источники истины, планы, проверки и production.
37. Зафиксировать три масштаба задачи: маленькая — сразу выполнить; средняя — исследовать и задать только нужные вопросы; сложная — исследование, согласование требований, реализация.
38. Preview показывать только по прямой просьбе владельца.
39. Браузерную проверку выполнять только для изменённого пользовательского интерфейса или критического пути, который нельзя надёжно проверить дешевле.
40. Разрешить автономную отправку на сервер, если маршрут понятен и владелец не попросил остановиться перед публикацией.
41. Plans пополнять только после явного отложения владельцем, а не из незавершённой или забытой работы.
42. Перед созданием функции или модуля проверять существующие реализации, черновики, планы и реестр переиспользования.
43. При изменении модуля обновлять его карточку, проверять связи и затронутых потребителей в том же изменении.
44. Запретить параллельным чатам менять один источник истины или одну рабочую ветку; для независимой реализации использовать worktree/ветки и checkpoint.

46.2. Устранить нерабочие ссылки на отсутствующий `~/.claude`/Bash там, где они мешают Windows-процессу.
47. Выполнять минимальные локальные тесты по риску и один полный CI-прогон перед production.
48. Убрать обязательный backup для обычного code-only deploy.
49. Сохранить свежий backup перед migration, импортом и изменением Telegram startup-seed; сохранить ежедневные backup.
