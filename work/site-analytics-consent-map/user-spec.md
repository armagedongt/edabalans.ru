## What We Are Building

Единый контур для cookie-плашки, внутренней продуктовой статистики и
маркетинговой аналитики всех пользовательских страниц edabalans. Центральный
модуль определяет поведение по типу страницы, поэтому владелец не перечисляет
аналитику заново при создании каждой страницы.

На первом этапе плашка показывается только на серверной главной. Остальные
страницы молча читают уже сохранённое согласие: функциональная статистика работает
всегда, а Яндекс Метрика запускается только при наличии согласия.

## Why

Сейчас плашка и аналитика подключены независимо: интенсив сохраняет персональный
прогресс и одновременно сразу запускает Метрику, блог не имеет Метрики, а
плашка уже подключена сразу к нескольким разделам. Из-за этого невозможно одним
взглядом понять фактическое поведение сайта и легко случайно добавить страницу с
неверным сочетанием счётчиков и уведомления.

## Expected Behavior

1. Новый посетитель открывает серверную главную и видит единственную общую
   cookie-плашку.
2. До нажатия «Приемлемо» главная может выполнять только необходимую
   функциональную работу; Яндекс Метрика и рекламные пиксели не загружаются.
3. После нажатия сохраняется versioned cookie сроком на год для корневого домена
   и его поддоменов. Плашка скрывается, маркетинговая аналитика загружается один
   раз и начинает принимать цели.
4. На последующих страницах того же корневого домена плашка не появляется. Если
   согласие сохранено, разрешённая для типа страницы Метрика запускается; если
   согласия нет, страница работает без неё.
5. Участник, пришедший прямо из бота в интенсив без ранее сохранённого согласия,
   не видит плашку. Его персональная сессия, открытие частей, задания, таймеры и
   скидка продолжают сохраняться в нашей базе, но Яндекс Метрика не загружается.
6. ЛК, приложения, вход, оплата и персональные переходы продолжают записывать
   необходимые аккаунту и продукту данные независимо от маркетингового согласия.
7. Юридические страницы не показывают плашку и не запускают маркетинговые
   счётчики.

## Acceptance Criteria

- [ ] В проекте существует один общий runtime cookie-плашки и один общий runtime
  маркетинговой аналитики; страницы не содержат собственных копий загрузчика
  Метрики.
- [ ] Плашка первого этапа визуально появляется только на серверной главной.
- [ ] Нажатие «Приемлемо» сохраняет versioned cookie на один год с `Path=/` и
  областью корневого домена; повторная загрузка главной и страницы того же домена
  не показывает плашку.
- [ ] Без согласия сетевой запрос к скрипту Яндекс Метрики отсутствует на главной,
  в блоге и в интенсиве.
- [ ] После согласия главная, блог и интенсив могут загрузить Метрику не более
  одного раза на страницу и отправлять цели через один адаптер.
- [ ] Прямой персональный вход в интенсив без cookie сохраняет в PostgreSQL
  внутренний прогресс, но не загружает Метрику и не показывает плашку.
- [ ] ЛК, DQS, тренировки, метаболизм, рецепты, Mini App entry, Telegram-вход,
  юридические и платёжные страницы не содержат маркетингового загрузчика и не
  показывают плашку.
- [ ] Новая страница, включённая в общий публичный shell, получает правило по
  объявленному типу страницы; неизвестный тип безопасно не запускает маркетинг.
- [ ] Автоматическая проверка перечисляет все пользовательские HTML routes и
  падает, если новый route не классифицирован в карте.
- [ ] Карта страниц генерируется либо проверяется из того же машинного реестра,
  из которого runtime получает политику; Markdown-таблица не становится вторым
  источником истины.

## Constraints

- Реализация отложена; этот документ не меняет production.
- Внутренняя статистика, необходимая для работы продукта, не зависит от решения
  о маркетинговых cookie.
- На первом этапе плашка показывается только на главной; на интенсиве и в блоге
  она не всплывает.
- «Один раз нажал — не появляется везде» гарантируется внутри одного корневого
  домена и его поддоменов. Между `edabalans.ru` и
  `похудение-это-есть.рф` браузер не позволяет напрямую разделить cookie.
- До окончательного доменного переноса страница без локального согласия молча не
  запускает Метрику, а не показывает вторую плашку.
- Не добавлять новый внешний сервис, расходы или отдельную consent-платформу.
- Счётчик Метрики остаётся `97331502`, если отдельная задача не меняет его.
- Существующие UTM, `yclid`, персональные ссылки, attribution и серверные события
  сохраняют текущий контракт.

## Risks

- **Смешение внутренней и маркетинговой статистики:** отключение всего tracking
  сломает прогресс интенсива. **Mitigation:** разные адаптеры и отдельные тесты
  функциональных событий без согласия.
- **Два корневых домена:** согласие нельзя надёжно перенести обычной cookie.
  **Mitigation:** до cutover не показывать повторную плашку и не запускать
  маркетинг без локального согласия; после cutover использовать один root domain.
- **Потеря ранних целей Метрики:** события могут произойти до асинхронной загрузки
  счётчика. **Mitigation:** очередь разрешённых маркетинговых целей с отправкой
  после готовности Метрики; очередь не создаётся до согласия.
- **Новая неклассифицированная страница:** разработчик может забыть о политике.
  **Mitigation:** безопасное default-off и route inventory test.
- **Дублирование счётчика:** внешний Tilda shell может добавить собственную
  Метрику поверх серверной. **Mitigation:** серверный адаптер проверяет уже
  инициализированный ID, а при доменном cutover отдельно удаляется внешний
  Tilda-загрузчик.

## Accepted Decisions

- Плашка первого этапа показывается только на главной, потому что в интенсив
  основной поток приходит из бота и не должен получать дополнительное окно.
- Внутренний прогресс работает без маркетингового согласия, потому что это часть
  функции продукта, а не рекламный счётчик.
- Страница без плашки и без ранее сохранённого согласия не запускает Метрику.
- Поведение централизуется по типам страниц; владелец не задаёт его вручную для
  каждой новой страницы.
- Юридические, платёжные, кабинетные и прикладные экраны остаются без
  маркетинговых счётчиков и без общей плашки.
- Реализация выполняется позже отдельным пакетом и отдельным выпуском.

## Testing

**Unit tests:** нужны для классификации страницы, чтения/versioning cookie,
идемпотентной загрузки Метрики и очереди целей.

**Integration tests:** нужны для проверки, что все пользовательские HTML routes
классифицированы и подключают только разрешённые runtime-модули.

**E2E tests:** нужны в реальном браузере для трёх сценариев: новый посетитель
главной; согласившийся посетитель переходит в блог/интенсив; прямой персональный
вход из бота в интенсив без согласия. В последнем случае проверяется одновременно
отсутствие запроса к `mc.yandex.ru` и сохранение внутреннего события на backend.
