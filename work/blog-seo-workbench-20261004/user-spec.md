## What We Are Building

Редакционный SEO-конвейер существующего блога: неизменяемый public-архив, одна большая Markdown-карта всех статей для ручного выбора и семантика Wordstat. После согласования — поддержка поискового title в текущем Markdown/API, полноценное авторство, достоверные даты, хлебные крошки, серверная пагинация и максимум одна смысловая рекомендация внутри статьи.

## Why

Владелец должен видеть действующие значения рядом с альтернативами, выбирать их самостоятельно и не терять историю. SEO не превращается в переписывание авторского текста, рекламный запуск или обещание отсутствующего содержания.

## Expected Behavior

1. Получить список публичных identity и фактические HTML title/H1/description/canonical. Admin draft не выдавать за public.
2. Сохранить отдельный датированный архив и одну редактируемую карту: URL/source_id/рубрика, текущие поля, релевантные запросы с параметрами Wordstat, два title, два description, основание и два пустых поля владельца.
3. Подготовка идёт пачками по 5–10 статей: полная текущая основа → предложения → review/pass → точечное добавление в карту. После каждой пачки сохранить checkpoint.
4. Сергей вписывает свои варианты. Пустые поля оставляют текущие значения; редактирование карты само по себе ничего не публикует. Повторная сборка не перезаписывает ручные правки.
5. Только после выбора реализованный parser принимает seo_title вместе с description, безопасно собирает preview/public и сохраняет версию штатным API. Не создавать второй редактор.
6. Авторская строка ведёт в постоянный профиль. Диалог с тем же содержимым допустим как улучшение, но обычная ссылка работает без JavaScript. Фото — принятая аватарка, не генерация. Дополнительный текст профиля сначала согласуется.
7. Исходная дата, появление в блоге и изменение разделяются. Breadcrumbs ведут к блогу и существующему рубричному фильтру. Серверный каталог отдаёт 15 карточек на страницу с прямыми ссылками и соответствующими canonical.
8. Внутри материала — ноль или один интерактивный related после завершённого раздела, затронувшего отдельный вопрос. Три конечные карточки сохраняют отдельную роль.

## Acceptance Criteria

- [ ] Public-архив и карта покрывают все опубликованные identity без дублей; ошибки явно показаны.
- [ ] Снимок exact title/description соответствует публичному HTML после декодирования.
- [ ] Подготовленная статья имеет две пары, читательское основание и Wordstat-привязку либо явное отсутствие данных; неподготовленная не помечается готовой.
- [ ] Пустые поля владельца не означают согласование. Ручные изменения карты не теряются.
- [ ] Wordstat сохраняет источник/дату/географию/тип частоты; показатели не названы прогнозом органического трафика.
- [ ] Старый description-only MD совместим; неизвестные/дублированные/опасные поля отвергаются. seo_title не появляется в теле/TOC.
- [ ] Draft не меняет public; preview/public используют одну логику, optimistic locking сохраняется.
- [ ] H1/body/slug не меняются из-за выбора поискового title.
- [ ] Person/Article и byline ссылаются на одного автора без выдуманной квалификации.
- [ ] Даты основаны на событиях/источниках; нет массовой фиктивной даты обновления.
- [ ] Пагинация по 15 не теряет/не дублирует статьи; адрес следующей страницы доступен без JS.
- [ ] Inline-related максимум один или ноль, только опубликованный уместный кандидат; self/скрытые/дубли исключены.
- [ ] Правила находятся у существующих владельцев документации и доступны из карточки.

## Constraints

Не менять live title/description до отдельного выбора. Не исправлять идеи, медицинскую фактуру или голос ради SEO. Не менять рекламу, цены, домены, cookie/auth, общий footer и курсы. Не создавать новый ключ без отдельного решения. Токены не печатать/не сохранять в Git. Search Console/Вебмастер явно отложены. Адаптивные изображения — следующий этап после измерений; исходники/immutable URL сохранить. Бесплатный Direct Wordstat допустим в квотах; платный Cloud fallback без лимита запрещён.

## Risks

- **Перезапись выбора:** неизменяемый архив, точечный diff рабочей карты, запрет повторной генерации поверх неё.
- **Нерелевантная частотность:** читать полный текст и выбирать запрос по содержанию, не по наибольшему Shows.
- **Несуществующее обещание:** ручную формулу не называть интерактивным калькулятором.
- **Ложный тест:** хранить варианты/даты/versions; не объявлять победителя без сравнимых данных.
- **Конфликт публикации:** получить актуальную version перед изменением и не перезаписывать чужую редакцию.

## Accepted Decisions

- Видимый title и seo_title разные; fallback — действующее название.
- Description по умолчанию — первые два предложения, override только вручную/по согласованию.
- Редакционные ориентиры: title обычно 45–65, description 120–170 символов с пробелами. Это не жёсткие лимиты поисковиков.
- Автор: Сергей Воронцов, тренер по питанию. «Пишу о питании и похудении так, чтобы вы менялись.» Факт «разобрал более 600 дневников питания участников Мастер-класса» предоставлен владельцем; формулировку профиля согласовать.
- Максимум одна внутренняя рекомендация, не обязательная для каждого материала.
- 04.10.2026 — дата действительно выполненного обновления, не дата исходной публикации и не автоматическая смена всем старым страницам.
- Потливость по смыслу не менять; плато остаётся отдельным подробным материалом, второй блок можно бережно актуализировать. Это отдельные решения, не право менять другие тексты.

## Testing

**Unit tests:** строгий parser и metadata fallback/escaping, пагинация, сборка author/dates. Для snapshot — HTML-decoding, ошибка сети и запрет перезаписи.

**Integration tests:** штатные blog/draft проверки; сохранение/preview/publish и неизменность public при draft.

Unit-граница достаточна для чистых функций parser/fallback/escaping и разбиения списка: входы и результаты детерминированы, браузер не добавляет доказательств. Сохранность snapshot проверяется прямым файловым тестом: второй запуск отказывает до сетевых вызовов, bytes/hash прежние; ошибка сети даёт явно неготовую запись.

Сквозные свойства нельзя доказать одним parser-тестом. Integration-граница штатного API и тестовой БД должна пройти draft → save → preview → publish → public с проверкой значений и версии; stale version отклоняется, public до publish неизменен. Это минимальная надёжная граница сохранения metadata и optimistic locking. Ручные поля карты проверяются файловым diff до/после точечного добавления пачки, а не обещанием повторной генерации.

**E2E tests:** только изменённые UI-границы профиля/навигации на desktop/mobile, не полный повторный аудит статей.
