## С чего начинать: сбои и проверка доставки

13.11 обе публичные проверки через физический интерфейс вернули `ready` и пустые
причины; Telegram указал маршрут `relay`. Это текущий срез работоспособности API,
а не доказательство работы каждого входа или отправки. Сервер на a4957b60 подтвердил: временный вход включён, длинная кампания выключена, записей тестовых или рабочих пар моста нет. Канон: [runtime-health](../../docs/runtime-health/README.md).

1. Снять сводку недавних сбоев отдельно для Telegram, MAX, планировщика и БД.
   Сопоставить время с журналом контейнера `telegram-bot`, deploy, локальным
   watchdog и Cloudflare Observability. Различать проблему приёма события,
   ошибку обработки/очереди и ошибку API при доставке. Сначала только чтение.
2. Проверить внешний мониторинг: отдельные счётчики Telegram/MAX, проверка каждые
   30 секунд, инцидент после трёх подряд ошибок; отдельные уведомления и правила
   восстановления рекламы из канона. На срезе не проверялось, что последние
   аварийные уведомления реально дошли до обоих аккаунтов. Не устраивать аварию на
   рабочих ботах ради теста; воспроизвести на тесте и сверить историю реальных инцидентов.
3. Прогнать владельцем/выделенными тестовыми контактами: Telegram Start, подтверждение
   и таймер, ручной Start в пределах таймера, MAX Mini App и реальный webhook Start,
   остановка, повтор, покупатель и связанная пара аккаунтов. Сверить квитанцию
   каждого шага, факт выдачи статьи, один запуск и отсутствие дубля. Проверить
   статистику от отдельной тестовой ссылки до статьи/главной, отказ и восстановление.
4. После утверждения текстов и расписания — сначала маленький тест на известных
   получателях, затем отдельное решение Сергея о массовой рассылке. Критерии:
   обе доставки, статус неудач, ограниченные повторы, стопы/покупки, отчёт и
   понятный способ остановить только новую цепочку без потери истории.

Проверить выдачу подборки, исправить старую отсылку и затем подключить выбранные ссылки к принятым сообщениям.
До выбора Сергеем не переносить массово: блог подходит для постоянного материала,
MAX-пост — для разговора под публикацией. [Ручной список и площадки](../channel-first-rollout-20261018/owner-channel-checklist.md).

**Тест публикации и правки.** Сергей позже выбирает запасной канал/пару, проверяет
свои права, добавляет назначенного бота с минимально нужными правами. Дальше:
одна тестовая публикация из согласованного источника → сохранить ID → увидеть пост
в канале → правка того же поста через бота → убедиться, что ID не изменился и копии
не появилось. Если тестируется зеркало Telegram → MAX, проверить пару ID и правку
в обеих витринах, повтор входящего события и ошибку доставки. Затем отдельно фото
с подписью и рабочие ссылки. Публикацию через Codex считать подтверждённой только
после фактической доставки на запасной канал; в рамках этого пакета ничего не отправлялось.

**Три разных режима.** (1) Зеркало публикаций Telegram → MAX. (2) Два связанных
обычных чата практики — это уже спроектировано в «Идее спринтов»; код в `main`,
на сервере пока нет ни тестовой, ни рабочей пары. (3) Комментарии именно под
парными постами — отдельная доработка, старый код её не реализует.

- В MAX: канал → аватар → карандаш/шестерёнка → включить **Комментарии**.
  Отдельная группа для нативных комментариев MAX не нужна.
  [Инструкция MAX](https://dev.max.ru/docs/channels/manage#как-включить-комментарии-в-канале).
- В Telegram: настройки тестового канала → **Обсуждение** → привязать тестовую
  группу. Комментарий живёт в ветке автоматически пересланного поста.
  [Документация Telegram](https://core.telegram.org/api/discussion).
- [API MAX для комментариев](https://dev.max.ru/docs-api/use-cases/comment-moderation/)
  поддерживает чтение, публикацию, правку, удаление и webhook создания/правки/удаления.
  Для теста: две закрытые площадки, пара постов, по одному текстовому комментарию
  с каждой стороны, ответ и правка. Проверить, что копия пришла в нужную ветку
  один раз и явно подписана площадкой; не обещать автоматическую синхронизацию
  удалений Telegram или медиа до отдельной проверки. Не зеркалить историю подписчиков.
- У моста отдельный MAX-бот и собственный webhook; роли, токены и права сверять
  по [карте контактов](../../docs/knowledge-base/PROJECT_IDENTITY.md) и настройкам.
  Не подменять мостом продуктовых ботов. Не включать рабочие каналы до теста.
  Старый checkpoint ожидал модерацию; более новая карта подтверждает /me бота
  07.10.2026, но это не доказательство прав или подключённой пары.
