# Общий вход, MAX и персональная аналитика

Основание: прямой запрос Сергея21.10 «полностью всё нужно реализовать, максимально,
что мы из этого можем», затем ответы «пока в канал» и «Только входная группа,
дальнейшую рассылку отдельно». Это разрешение реализации перечисленного ниже.
Расширение авторизации между корневыми доменами пока не входит: вопрос задан,
ответ ожидается. После ответа добавить решение, не выдавать consent за вход.

## Что создаём и зачем

Единый проверяемый путь от ссылки до канала, входной группы, статьи и главной.
Устранить разрыв: человек разрешил писать, но не нажал Start; сохранить общую
входную группу и исключить параллельную повторную отправку. Добавить MAX в
существующий конструктор и связать фактический просмотр блоков главной с посетителем.

## Пользовательский путь

1. Telegram `/start` или существующий запрос статьи сразу вызывает общую группу:
   навигация → её закрепление → старый настоящий кружок → текст анонса статьи.
   Действующие ручные повторные запросы и покупательские ветки сохраняются.
2. Подтверждённое сервером новое разрешение писать создаёт устойчивое ожидание
   600 секунд. Сам клиентский callback не даёт оснований для отправки.
3. В срок повторно проверить: пользователь не остановил сообщения, не исключён
   действующими правилами, не купил, не запросил/получил вход вручную. Тогда выдать
   ту же группу через общий helper в точный Telegram-диалог, не в preferred MAX.
4. Start и таймер используют общий claim. Частичная/неопределённая доставка не
   вызывает слепую повторную группу. Повтор webhook не создаёт новый таймер.
5. После группы завершить этот процесс. Новые14 дней и старые60 постов не включать.
   Будущее продолжение остаётся отдельной явной связью графа, не новой копией входа.
6. В конструкторе у одной записи/кода есть Telegram- и MAX-ссылки. MAX запускает
   существующий `/max-app`, различает канал и обычные приложения, проверяет
   подписанный initData, сохраняет платформу/источник, открывает настроенный MAX-канал.
7. MAX по умолчанию ведёт в `MAX_CHANNEL_URL`; можно менять допустимый собственный
   адрес через общий конструктор. Не создавать второго бота, кабинета, приложения.
8. MAX Start выдаёт общую группу: навигация → исходное видео кружка обычным видео
   → текст статьи. Закрепление личного MAX-диалога не обещается. Отдельного
   requestWriteAccess в MAX нет; один Mini App open не считать bot_started или
   разрешением на автоматическую отправку. Предусмотреть обычный запуск бота,
   когда для дальнейшей доставки это требуется.
9. Входная посадка, Mini App, подтверждённая идентичность и персональная статья
   используют существующий browser journey; разрешение без Start тоже связывает
   действительный исходный browser context с CRM, не притворяясь стартом.
10. Существующий observer главной дополнительно сохраняет для того же browser/user
    виденные секции с каноническими IDs/названиями, глубину/процент, визит и время.
    Прокрутка до конца не означает, что промежуточные блоки были просмотрены.
11. Подписанный transfer при переходе между публичными корнями переносит visitor
    и действующее согласие на cookies. Главная, блог и LK внутри корня используют
    общий путь `/`. Проверенная сессия LK связывает историю с user_id; anonymous
    context сам по себе не выдаёт авторизацию. Admin-сессия не переносится.

## Технические границы

Существующие SequenceRun/StepDelivery/TrackingEvent/managed_documents/CRM.
Без новой физической схемы, migration, самостоятельного scheduler или панели.
Тексты и старое видео не переписывать и не конвертировать. Сохранить авторские
слоты `tpl_onepage_entry_navigation`, `tpl_entry_circle`, `tpl_channel_article_entry`.
Общая группа — один источник для двух способов запуска, не три скопированных MESSAGE.
Представить условия и задержку в действительном графе и административной проекции.

Новые таймеры только для новых подтверждений после включения, не запускать массовую
ретроспективную выдачу всей базе. Внешние тестовые отправки только владельцу.
Согласие переносить через проверенный канал, не через доверие query `accepted=1`.
Прямой независимый вход на другой root без transfer не может прочитать прежнюю cookie;
не обещать такую идентичность без фактического обмена между origins.

## Риски и проверки

- Дубли: row locks/общий claim/уникальные receipt и явная обработка uncertain.
- Чужая идентичность: серверные подписи, точный messenger+ID, проверенная account session.
- Неверный канал отправки: explicit_exact для разрешившего Telegram-бота.
- Потеря MAX приложений: отдельная ветка сырого channel payload перед старым dispatch.
- Ложное чтение: реальные section observations отдельно от scroll depth.
- Согласие и права: перенос visitor/consent не заменяет account/admin credentials.

Unit/integration: граница599/600, повтор, stop/buyer/manual/race/restart, MAX подписи,
запрет чужих redirect, report windows, разрешение без Start, backfill, section allowlist,
правильные названия/пропуски, invalid transfer, отсутствие выдачи чужих прав.
Browser: общий путь через главную/блог/LK, переход между roots с consent, настоящий
homepage observer, bridge обоих мессенджеров и существующие MAX приложения.
Owner-only live: группа уже отправлена; проверить MAX регистрацию и мобильный переход.
Штатный CI/deploy, затем безопасные API/browser проверки без рассылки клиентам.

## Testing

Таймер, повтор webhook, ручной вход и stop проверяются интеграцией с реальной БД
и новым Session после сохранения: это подтверждает устойчивость, а не только расчёт времени.
Конкурентный claim дополнительно проверяется двумя соединениями PostgreSQL с общим user lock;
SQLite не подтверждает row locking. Внешний sender заменяется только на границе API.
MAX подпись и независимые identity, signed consent и backfill — API/DB интеграция.
Секции главной проверяются observer в браузере плюс допустимость событий на API;
нельзя подменять их вычисленным списком предыдущих секций.

## Agent Verification

Исполнитель запускает профильные bot/backend тесты, проверяет фактические записи/граф,
browser consent/observer и совместимость MAX home/account, затем CI и production health.
Проверка владельца нужна только для нативного MAX запуска на телефоне и подтверждения
внешнего отображения; три Telegram сообщения уже отправлены владельцу.

Результат выпуска и фактические ограничения: [verification.md](verification.md). Нативные MAX критерии остаются открыты до проверки владельцем; API и SDK dispatch проверены автоматически.
