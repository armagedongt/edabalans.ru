# Очищенный каталог продуктов для калькулятора рецептов

Статус: `current`
Владелец: модуль `products.recipes`

Этот каталог собран из локальной базы Calorizator без изменения исходного
SQLite-файла. Он предназначен для поиска ингредиентов в калькуляторе, а не для
хранения готовых блюд, ресторанных позиций и нескольких одинаковых карточек
одного базового продукта.

## Что увидит человек

- Название со звёздочкой, например `Творог 5% *`, — базовый продукт. Бренды
  обычного продукта схлопнуты, а КБЖУ усреднены только по совместимым карточкам.
- Значимые варианты остаются разными: `Творог 5% *` и `Творог мягкий 5% *`,
  сухой и отварной рис, разные сыры, сорта и способы обработки.
- Малые расхождения жирности приводятся к понятному варианту: `0,5%` к `0%`,
  `1,8%` к `2%`. `2%` и `5%` не объединяются.
- Брендовые продукты с собственной рецептурой остаются под исходным названием.
  Смеси хлопьев вроде «4 злака» не усредняются между производителями.
- Готовые блюда, ресторанные позиции, слишком общие названия и явные ошибки КБЖУ
  не показываются в поиске.
- При одинаковом начале названия поиск сначала показывает личный продукт, затем
  базовый продукт со звёздочкой и после него брендовые варианты. Порядок задан
  явно и одинаков для PostgreSQL и локальных тестов.

Звёздочка не означает, что продукт «полезнее» остальных. Она означает только
обобщённую базовую карточку, удобную для расчёта рецепта.

## Файлы и восстановление

| Файл | Назначение |
| --- | --- |
| `original-products.jsonl` | Неизменяемый снимок всех исходных названий, категорий, ссылок и КБЖУ. |
| `curation-log.jsonl` | Одно решение на каждую исходную строку: оставить бренд, объединить, скрыть или исключить как выброс. |
| `curated-products.jsonl` | Активный набор для калькулятора. |
| `summary.json` | Контрольная сумма источника, итоговые количества и распределение решений. |

Скрипт `backend/scripts/curate_recipe_catalog.py` генерирует эти четыре файла
детерминированно. Исходный `data/calorizator/calorizator.sqlite` остаётся локальным
и не попадает в Git.

Перед изменением production-каталога обязателен свежий backup PostgreSQL.
После стандартного deploy файлы входят в backend-образ. Применение очищенного
набора в production:

```bash
docker compose exec -T backend python -m scripts.import_recipe_catalog \
  --catalog data/recipe_catalog/curated-products.jsonl \
  --curation-log data/recipe_catalog/curation-log.jsonl \
  --deactivate-missing
```

Команда не удаляет строки из PostgreSQL. Исключённые исходные карточки становятся
неактивными, поэтому рецепты, которые уже на них ссылаются, продолжают считаться.
Личные продукты и обычные глобальные карточки вне журнала не меняются. Старые
карточки пространства `curated://recipe-catalog/`, которых больше нет в активном
наборе, тоже становятся неактивными.

Идентификатор базовой карточки зависит от названия и итоговых КБЖУ. Если будущая
пересборка изменит среднее, она создаст новую карточку, а прежнюю только скроет из
поиска. Поэтому КБЖУ уже сохранённого рецепта не меняются задним числом.

Точечное восстановление одной исходной карточки:

```bash
docker compose exec -T backend python -m scripts.import_recipe_catalog \
  --catalog data/recipe_catalog/original-products.jsonl \
  --only-source-url "https://calorizator.ru/product/example"
```

Полное возвращение исходного набора без отката кода и без потери новых рецептов:

```bash
docker compose exec -T backend python -m scripts.import_recipe_catalog \
  --catalog data/recipe_catalog/original-products.jsonl \
  --curation-log data/recipe_catalog/curation-log.jsonl \
  --deactivate-missing
```

Точную причину любого решения искать в `curation-log.jsonl` по `source_url`.
