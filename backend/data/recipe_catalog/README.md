# Очищенный каталог продуктов для калькулятора рецептов

Статус: `current`
Владелец: модуль `products.recipes`

Этот каталог собран из локальной базы Calorizator без изменения исходного
SQLite-файла. Он предназначен для поиска ингредиентов в калькуляторе, а не для
хранения готовых блюд, ресторанных позиций и нескольких одинаковых карточек
одного базового продукта.

Вход во весь [контур рецептов](../../../docs/knowledge-base/RECIPE_CONTOUR.md)
связывает этот источник с приложением, авторскими материалами и карточками.

## Источник и единицы

Вход — локальный `data/calorizator/calorizator.sqlite` основной рабочей копии
проекта. Таблица `products` даёт `source_url`, название и категорию,
`product_nutrients` — `field_code` и числовое значение. Для сборки обязательны
все четыре поля: `protein`, `fat`, `carbohydrate`, `kcal`. Значения относятся
к 100 г продукта, а не к указанному в рецепте весу. Строки без полного набора
не включаются в исходный снимок расчётного набора и его журнал.

Это подготовленная локальная база, не запрос к Calorizator при каждом поиске.
Файл сейчас находится в `data/calorizator/` основного checkout; в отдельный
worktree автоматически не переносится. При смене локального адреса используют
проверенный исходник и явный `--sqlite`, не создают новый источник данных из
скриншотов или текущей поисковой выдачи.

## Что увидит человек

- Название со звёздочкой, например `Творог 5% *`, — базовый продукт. Бренды
  обычного продукта схлопнуты, а КБЖУ усреднены только по совместимым карточкам.
- Значимые варианты остаются разными: `Творог 5% *` и `Творог мягкий 5% *`,
  сухой и отварной рис, разные сыры, сорта и способы обработки.
- Малые расхождения жирности приводятся к понятному варианту: `0,5%` к `0%`,
  `1,8%` к `2%`. `2%` и `5%` не объединяются.
- Брендовые продукты с собственной рецептурой остаются под исходным названием.
  Смеси хлопьев вроде «4 злака» не усредняются между производителями.
- Готовые блюда, ресторанные позиции, слишком общие названия и явные ошибки КБЖУ
  не показываются в поиске.
- При одинаковом начале названия поиск сначала показывает личный продукт, затем
  базовый продукт со звёздочкой и после него брендовые варианты. Порядок задан
  явно и одинаков для PostgreSQL и локальных тестов.

Звёздочка не означает, что продукт «полезнее» остальных. Она означает только
обобщённую базовую карточку, удобную для расчёта рецепта.

## Файлы и восстановление

| Файл | Назначение |
| --- | --- |
| `original-products.jsonl` | Исходный снимок строк с полными КБЖУ: названия, категории, ссылки и значения до очистки; вручную не редактируется. |
| `curation-log.jsonl` | Одно решение на каждую исходную строку: оставить бренд, объединить, скрыть или исключить как выброс. |
| `curated-products.jsonl` | Активный набор для калькулятора. |
| `summary.json` | Контрольная сумма источника, итоговые количества и распределение решений. |

Скрипт `backend/scripts/curate_recipe_catalog.py` генерирует эти четыре файла
детерминированно. Исходный `data/calorizator/calorizator.sqlite` остаётся локальным
и не попадает в Git.

### Как восстановить происхождение среднего

Ключ исходной строки — `source_url`. Журнал повторяет её исходные поля и
добавляет `decision`, `reason`, `canonical_key`, `canonical_name`,
`canonical_source_url`. Решения: `merge` — входит в обобщённую карточку;
`keep_brand` — отдельная карточка с исходным URL; `exclude` — скрыта по смыслу;
`exclude_outlier` — исключена из среднего как недостоверная/несовместимая.

Для базовой карточки собирают строки по её `canonical_source_url` и смотрят
решения каждой: строка-выброс может сохранять связь с группой, но в среднее не
входит. `member_count` обозначает число членов группы, `averaged_count` — число
действительно использованных источников. Среднее арифметическое считается
отдельно для каждого нутриента по совместимым источникам после исключений;
в очищенном наборе БЖУ округлены до десятых, ккал — до целых. Это подготовка
справочника, отдельная от точного расчёта и окончательного округления рецепта.
Порогами сопоставления и выбросов владеет скрипт очистки; не менять их только
в отображении или журнале. Несовместимые пары могут остаться отдельными карточками.

`summary.json` хранит `schema_version`, SHA-256 всего входного SQLite,
количества исходных/активных/скрытых/объединённых строк и распределение решений.
Числа брать из файла нужной ревизии, не дублировать постоянной таблицей здесь.
Hash сверяет вход сборки; дата скачивания источника этим полем не доказывается.
Текущая схема не хранит отдельную дату получения каждой карточки Calorizator.

### История изменений и пересборка

`curation-log.jsonl` — полная карта решений одной сборки, не append-only журнал
всех запусков и не журнал PostgreSQL. Предыдущие состояния четырёх файлов и
правил очистки сохраняются в Git. Для вопроса «почему/когда изменили этот продукт»
сравнить его `source_url` в нужных ревизиях, причины, состав группы и summary.
Первоначальная обратимая очистка принята в `1252eb9`; следующие редакции определяют
история файлов и фактический импорт. Дата commit не является датой сбора сайта.

Пересборка использует `curate_recipe_catalog.py --sqlite <проверенный исходник>
--output <каталог проверки>`. Сначала получить независимый результат, сверить
diff решений/средних и профильные тесты, затем принять согласованный набор.
Ручное исправление только `curated-products.jsonl` разрывает связь с генератором.
Вывод импортёра содержит source_rows/eligible/skipped/created/updated/deactivated;
отчёт применения сохраняется вне Git в evidence выпуска. Постоянного SQL-аудита
каждой операции импортёр не создаёт.

Перед изменением production-каталога обязателен свежий backup PostgreSQL.
Операционный порядок — `docs/OPERATIONS.md`. Перед записью выполнить ту же
команду с `--dry-run` и проверить пакет. У импортёра этот флаг явный:
без `--dry-run` он пишет в PostgreSQL; отдельного `--apply` у него нет.
После стандартного deploy файлы входят в backend-образ, но автоматически в
PostgreSQL не импортируются. Применение очищенного
набора в production:

```bash
docker compose exec -T backend python -m scripts.import_recipe_catalog \
  --catalog data/recipe_catalog/curated-products.jsonl \
  --curation-log data/recipe_catalog/curation-log.jsonl \
  --deactivate-missing
```

Команда не удаляет строки из PostgreSQL. Исключённые исходные карточки становятся
неактивными, поэтому рецепты, которые уже на них ссылаются, продолжают считаться.
Личные продукты и обычные глобальные карточки вне журнала не меняются. Старые
карточки пространства `curated://recipe-catalog/`, которых больше нет в активном
наборе, тоже становятся неактивными.

Идентификатор базовой карточки зависит от названия и итоговых КБЖУ. Если будущая
пересборка изменит среднее, она создаст новую карточку, а прежнюю только скроет из
поиска. Поэтому КБЖУ уже сохранённого рецепта не меняются задним числом.

Это гарантия замены **обобщённого среднего новым source_url**, а не снимок всех
источников рецепта. Повторный импорт изменённых значений под тем же исходным URL
обновляет существующий продукт; связанные блюда используют его текущие значения.
Личные продукты и вложенные блюда также имеют живые связи. Неизменяемые снимки
личной копии авторского оригинала описаны отдельно в контракте приложения.

Точечное восстановление одной исходной карточки:

```bash
docker compose exec -T backend python -m scripts.import_recipe_catalog \
  --catalog data/recipe_catalog/original-products.jsonl \
  --only-source-url "https://calorizator.ru/product/example"
```

Полное возвращение исходного набора без отката кода и без потери новых рецептов:

```bash
docker compose exec -T backend python -m scripts.import_recipe_catalog \
  --catalog data/recipe_catalog/original-products.jsonl \
  --curation-log data/recipe_catalog/curation-log.jsonl \
  --deactivate-missing
```

Точную причину любого решения искать в `curation-log.jsonl` по `source_url`.
