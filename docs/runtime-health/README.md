# Работоспособность и восстановление edabalans

Модуль: `operations.health`. Это единственная точка входа по доступности сервера,
Telegram и MAX, аварийным уведомлениям, остановке/возврату рекламы, резервному
исходящему DNS и безопасным проверкам восстановления. Начинайте с этого файла,
а не с памяти старого чата. Фактическую выпущенную версию проверяйте отдельно:
принятый Git commit и работающий production — разные состояния.

## Коротко для Сергея

- Внешний наблюдатель в Cloudflare проверяет сервер, Telegram и MAX каждые 30 секунд.
- Три последовательные ошибки одной границы подтверждают аварию; единичная ошибка
  сама по себе не останавливает рекламу.
- При подтверждённом отказе любой площадки останавливается реклама, ведущая в оба
  мессенджера. Остановленные до аварии кампании не включаются.
- Возврат рекламы — после двух полных минут исправности всех трёх проверок и
  минимум четырёх успешных наблюдений. При обычном интервале это пятая проверка.
- Telegram- и MAX-only сбой не вызывает перезагрузку сервера.
- Уведомления об аварии, действиях и восстановлении приходят в технический
  Telegram-диалог через отдельного `@TetrisgfgfgfBot`. При исправной работе
  постоянных сообщений «всё хорошо» нет.
- Зелёный статус не означает, что каждый пользователь прочитал сообщение.
  Доступность, доставка сообщения и прочтение материала — три разных факта.

## Что входит и что не входит

Владелец этого модуля отвечает за правила наблюдения и восстановления; исходники
ботов остаются у модулей сообщений, Caddy и Telegram relay — у `operations.proxy`,
CI и выпуск — у `operations.delivery`, backup/restore — у `operations.backup`.
Они связаны с этим контуром, но не переносятся физически ради одной папки.

Этот модуль не меняет тексты, граф Welcome, расписание сообщений, рекламные
креативы, бюджеты и посадки. Автоматическое восстановление availability не
возобновляет вручную остановленные Welcome-цепочки.

## Какие проверки реально работают

| Проверка | Что проверяет | Чего не доказывает |
| --- | --- | --- |
| `/ready` | Caddy, backend, PostgreSQL и обязательную конфигурацию backend | Работу каждой страницы, оплату или отправку каждого письма |
| `/api/health/telegram` | Базу, включённый планировщик, его рабочую активность, свежий успешный polling Telegram и ожидаемый маршрут `relay` | Доставку каждому человеку и открытие интенсива |
| `/api/health/max` | Базу, планировщик, MAX API, регистрацию webhook и доступность настоящего входящего обработчика | Что MAX действительно прислал каждое событие и пользователь получил каждое сообщение |
| Docker `/health` контейнера ботов | Отвечает ли процесс на локальный HTTP-запрос | Исправность внешнего API мессенджера |

Telegram забирает события сам. Успешный polling не старше 60 секунд подтверждает
фактический путь: российская VM → закрытый Cloudflare relay → Telegram API.
Планировщик считается устаревшим после 300 секунд без рабочей активности при
текущей конфигурации. Его явная ошибка сразу делает readiness красной.

MAX получает события через webhook: отсутствие новых людей или сообщений
не является ошибкой. Поэтому раз в 30 секунд отдельная фоновая задача:

1. Выполняет авторизованный `GET /me` и проверяет ответ о боте.
2. Выполняет `GET /subscriptions`: должен присутствовать точный публичный URL
   `/api/messaging/max/webhook` и события `bot_started`, `bot_stopped`,
   `dialog_removed`, `message_created`, `message_callback` либо подписка на все события.
3. Отправляет на этот URL синтетический запрос `runtime_health_probe` с нашим
   секретным заголовком. Настоящий обработчик его игнорирует: контакты, цепочки
   и сообщения не создаются. Это проверяет DNS/HTTPS/Caddy/маршрут/авторизацию входа.

Каждое HTTP-обращение имеет настроенный timeout 4 секунды на сетевую операцию;
это не жёсткий общий предел всей составной проверки. Фон работает вне HTTP event
loop. Публичный MAX health отдаёт только сохранённый результат и не запускает
новые API-запросы. Результат старше 75 секунд — ошибка, даже если раньше был зелёным.
Свежий отказ API, неправильный webhook, отсутствие токена/секрета или ошибка базы
делают MAX readiness красной.

Официальные договоры MAX: [список webhook-подписок](https://dev.max.ru/docs-api/methods/GET/subscriptions),
[секретный заголовок и регистрация событий](https://dev.max.ru/docs-api/methods/POST/subscriptions).
Список подписок не возвращает установленный секрет. Синтетический запрос доказывает,
что наш сервер принимает наш секрет, но не доказывает, что такой же секрет сохранён
на стороне MAX. Это подтверждается настоящим подписанным событием при ручном smoke.

## Авария: порядок автоматических действий

| Событие | Действие |
| --- | --- |
| Одна или две ошибки | Наблюдать, не объявлять подтверждённую аварию |
| Третья последовательная ошибка одной границы | Открыть один incident, отправить причину в Telegram |
| Incident открыт, прошла минута от начала отказа | Сохранить включённые разрешённые кампании и остановить их |
| Отказал только Telegram, только MAX или оба; backend исправен | Не перезагружать VM |
| Общая платформа непрерывно недоступна минимум 240 секунд и отказ подтверждён | Один запрос перезагрузки российской VM через Timeweb |
| Все проверки снова исправны | Начать новый двухминутный интервал устойчивости |
| Новая ошибка до окончания интервала | Обнулить интервал и успешные наблюдения |
| Две минуты исправности и достаточно наблюдений | Возобновить только сохранённые кампании; закрыть incident после успешного возврата |

Перезагрузка VM не повторяется в том же incident: потерянный ответ провайдера
не позволяет понять, принята ли первая команда. Ошибки остановки/возврата рекламы
повторяются с паузой 120 секунд. После трёх неудачных попыток приходит отдельное
предупреждение; повторы рекламного действия продолжаются, это не предел попыток.

Incident, список кампаний и очередь уведомлений хранятся в SQLite-backed Durable
Object Cloudflare, а не только в памяти одного запуска. Действия сериализованы,
параллельные cron не отправляют конкурирующие команды. После закрытия incident его
запись очищается: это не бессрочный журнал всех рекламных изменений.

## Правило рекламы — одинаковое для Telegram и MAX

Реклама одновременно предлагает обе площадки. Отказ любой из них блокирует
возврат рекламы. `YANDEX_CAMPAIGN_IDS` ограничивает доступ автоматике; текущие
разрешённые кампании: поиск `714152601` и РСЯ `714157420`. Список не означает,
что обе включены. Мониторинг получает их реальные состояния, сохраняет только
`ON` до mutating-запроса и применяет `Campaigns.suspend`.

`Campaigns.resume` вызывается только для сохранённых ID. Если ранее всё было
остановлено — ничего не запускается. Отдельные объявления автоматика не включает,
не снимает их ручную паузу и не меняет модерацию или архив. Старое отдельно
остановленное объявление не станет активным при возврате кампании.

Во время открытого incident нельзя вручную менять эти кампании при включённом
`ACTIONS_ENABLED`: Яндекс не сообщает автора изменения. Перед ручным вмешательством
выключить автоматические действия и проверить сохранённый incident. Выключение
actions не выключает наблюдение и уведомления. Отключение actions не удаляет
сохранённые ID: перед последующим включением нужно согласовать состояние incident.

## Локальный перезапуск процесса

`edabalans-telegram-watchdog.timer` работает на российской VM раз в минуту.
Несмотря на историческое имя, контейнер `telegram-bot` обслуживает и Telegram,
и MAX. Если Docker видит `unhealthy`, `exited` или `dead`, локальный watchdog
перезапускает этот общий контейнер не чаще одного раза в 300 секунд. Отсутствующий
контейнер поднимается. Во время deploy используется общий lock, проверка пропускается.

Этот слой не перезапускает исправный процесс из-за внешнего отказа MAX/Telegram.
Не путать 300 секунд защиты от повторного restart с DNS timeout и двухминутным
ожиданием перед возвратом рекламы. Повторные restart не исправляют ошибку кода или
недоступность внешнего провайдера.

## Исходящий DNS всего российского сервера

Изначально сеть автоматически получила четыре адреса DNS Timeweb. Сейчас список
заменён на Яндекс `77.88.8.8` и Cloudflare `1.1.1.1`; адресов Timeweb в нём нет.
Это выбранная схема двух независимых сервисов, а не доказательство, что Timeweb
DNS всегда неисправен. Третий проверенный DNS Timeweb допустим как отдельное
согласованное изменение, но не был добавлен в этой задаче.

Настройка действует для исходящих запросов VM и контейнеров, использующих её
resolver: Docker `127.0.0.11` → host `127.0.0.53` → выбранный upstream DNS.
DHCP по-прежнему выдаёт IP и gateway. Данные и сервер не переезжают. DNS посетителя,
публичные DNS-записи сайта и Tilda не меняются.

Resolver переключается после ошибки; это не одновременный опрос всех DNS.
Стандартный начальный UDP timeout systemd v255 — около 5 секунд, не гарантия
восстановления приложения за 5 секунд. Дополнительные сетевые повторы могут
продлить ожидание. Резерв DNS не чинит разрыв интернета, отказ VM, relay или API.

Источник: `infra/network/10-netplan-eth0.network.d/90-edabalans-dns.conf`.
Установленная копия: `/etc/systemd/network/10-netplan-eth0.network.d/90-edabalans-dns.conf`.
Она дополняет Netplan-generated `10-netplan-eth0.network`; отключает получение DNS
из DHCPv4/DHCPv6/IPv6 RA и сохраняется после reboot/перегенерации Netplan. При смене
имени базового network-файла нужно перенести drop-in к реальному файлу интерфейса.

Установка: проверить выбранные DNS с VM, установить этот drop-in с правами `0644`,
выполнить `networkctl reload`, проверить IP/gateway, `resolvectl status` и обе
messenger readiness. Перезагрузка VM или Docker не нужна. Одного `FallbackDNS=`
недостаточно: при полученном DHCP списке он не служит таким независимым резервом.
Откат: удалить только наш drop-in, выполнить `networkctl reload`,
`resolvectl revert eth0`, `resolvectl flush-caches`; проверить возврат DHCP DNS
и readiness. Если drop-in существовал до изменения, вернуть сохранённую копию.
Netplan, базу и сетевой интерфейс не удалять.

## Как разбирать очередное уведомление

1. Записать время и текст ошибки, определить границу: backend / Telegram / MAX.
2. Проверить соответствующий health и фактически выпущенный commit.
3. Сопоставить время с журналами приложения, локального watchdog, deploy и
   Cloudflare. Сохранить конкретную причину и доказательство без персональных данных.
4. Отделить отказ сети/API от ошибки кода, формата сообщения и отдельного контакта.
   Не объявлять любое падение бота проблемой DNS и не перезагружать всё подряд.
5. Исправить причину в её модуле, выполнить адресные тесты и smoke после выпуска.
6. Убедиться в устойчивом восстановлении и точном списке возвращённых кампаний.

Основные журналы: контейнеры `telegram-bot`, `backend`, `caddy`; systemd units
`edabalans-telegram-watchdog.service`, `edabalans-deploy-poll.service`;
Cloudflare Observability для `edabalans-watchdog`. SSH: `edabalans-prod`;
production-каталог: `/opt/edabalans`. Не выводить `.env`, токены и личные сообщения.
Cloudflare logs могут быть sampled: они не заменяют полный журнал каждого лида.

## Настройки и секреты

В Cloudflare secrets: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALERT_CHAT_ID`,
`TIMEWEB_API_TOKEN`, `TIMEWEB_RU_SERVER_ID`, `YANDEX_DIRECT_TOKEN`,
`YANDEX_CAMPAIGN_IDS`, `ACTIONS_ENABLED`, `DRILL_TOKEN`.
`TELEGRAM_REQUIRED_ROUTE` — необязательный аварийный override `relay`/`proxy`.
`YANDEX_DIRECT_CLIENT_LOGIN` нужен только при агентском доступе, для текущего
собственного аккаунта не требуется. `MARKETING_REPORT_TOKEN` относится к
отдельному суточному отчёту, не к availability.

В защищённой server `.env`: токены/имена обоих ботов, `MAX_WEBHOOK_SECRET`,
настройки Telegram relay, БД и планировщика. MAX API токен в Cloudflare не передаётся:
проверка выполняется на российском сервере с действующим клиентом и доверенным CA.

Не секретные URL и пороги — в `wrangler.jsonc`. Timeweb-токен ограничен
управлением облачными серверами; не выдавать права на DNS, S3, баланс и другие
сервисы ради мониторинга. Удаление без Telegram-кода не разрешать.

## Проверки, выпуск и откат

Перед выпуском: адресные pytest ботов, Node-тесты watchdog и relay, shell-тест
локального watchdog, проверка registry и `pnpm check`. Все сетевые аварии в
автоматических тестах имитируются, production и реклама не ломаются ради теста.
Для pytest использовать отдельную временную папку, не production БД.

Порядок нового MAX-выпуска: server commit → успешный CI → штатный deploy
ботов/Caddy → проверка публичной `/api/health/max` → отдельный `pnpm deploy`
watchdog. Нельзя сначала включить в Worker отсутствующий MAX endpoint.
Server deploy проверяет MAX readiness, если MAX токен настроен; ошибка обнаружения
конфигурации не должна молча пропустить проверку. Нужны только затронутые сервисы;
текущая классификация docs также пересобирает backend. Миграций в MAX health нет.

Watchdog выпускается из `infra/monitoring/cloudflare-watchdog`:
`pnpm install --frozen-lockfile`, `pnpm test`, `pnpm check`, `pnpm deploy`.
Секреты существующего Worker сохраняются. Проверить активную версию и cron.
При неуспешной попытке server deploy скрипт сам возвращает предыдущую версию
без миграций. После уже успешного выпуска откат — отдельный обратимый commit,
отменяющий наш diff поверх свежего `main`, успешный CI и штатный deploy нового
`origin/main`. Просто передать старый SHA нельзя: deployer отклонит его.
Worker откатывается повторным deploy предыдущего исправного исходника.
Не откатывать к несовместимой форме
открытого incident и не удалять его сохранённый список кампаний.

Alert drill: закрытые `POST /drill/fail` и `/drill/recover` для Telegram,
`POST /drill/max/fail` и `/drill/max/recover` для MAX; `Authorization: Bearer DRILL_TOKEN`.
Каждая площадка использует отдельный Durable Object. Четыре fail-запроса проверяют
открытие/отсутствие дублей, пять recover — две полные минуты по тестовым часам.
Реальные уведомления идут в технический Telegram-диалог, но код жёстко запрещает
Direct/reboot/report для drill. Ожидаются два сообщения на площадку.
Постоянные workers.dev и preview URL выключены. При необходимом внешнем drill
workers.dev включается только кратковременно и обязательно выключается после.

Telegram relay имеет отдельный release path и непубличный `PRODUCTION_RELAY_NAME`;
его URL и секрет не публиковать. Подробный сетевой source contract —
`infra/monitoring/cloudflare-telegram-relay/README.md`. Аварийный возврат на
европейский Squid — `infra/telegram-proxy/README.md`; без отдельного поручения
выключенная европейская VM не является автоматическим резервом.

## Известные ограничения, не выдавать за завершённую защиту

- Подтверждение сейчас считает три ошибки одинакового полного набора проверок.
  При постоянном отказе MAX и чередующемся отказе Telegram счётчик сбрасывается:
  incident может не открыться. Исправление на отдельные счётчики каждой границы
  запрошено владельцу; до решения production-выпуск MAX-контроля не выполнен.
  Описанное выше правило трёх ошибок одной границы — принятая цель, но этот случай
  ещё не покрыт фактическим алгоритмом.
- Фильтр Caddy удаляет `X-Max-Bot-Api-Secret` из новых access logs. Старые журналы
  до установки фильтра могли сохранить этот заголовок. Они не очищены этой задачей;
  смена webhook-secret требует согласованного изменения и server, и подписки MAX.
- После частичного или потерянного ответа `Campaigns.resume` повторный отказ
  может не остановить уже включённые кампании: в открытом incident прежняя остановка
  уже отмечена завершённой. Дефект воспроизведён 16.09.2026; отдельное решение на
  исправление запрошено. Пока оно не выпущено, считать этот сценарий незакрытым.
- У отдельных Welcome-run отправка с ошибкой может оставить статус `error` без
  автоматического восстановления. Зелёный availability этого не исключает.
  Возобновление цепочек отложено владельцем; не запускать их молча этим контуром.
- MAX webhook probe не имитирует настоящее событие от инфраструктуры MAX и не
  проверяет отправку сообщения конкретному человеку. Для полного пользовательского
  smoke нужны Start, доставленный message ID и персональная ссылка тестового контакта.
- Relay и наблюдатель находятся в одном Cloudflare account. Это не независимый
  резерв при общем отказе аккаунта/провайдера. Нового второго провайдера не подключали.
- DNS резерв — профилактика DNS отказа, не доказанный диагноз всех прежних остановок.
  Подтверждённые разрывы RU→EU и запрет Telegram-кружка имели другие причины.
