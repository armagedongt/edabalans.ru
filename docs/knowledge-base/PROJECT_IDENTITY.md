## Для нового и продолжающегося чата

Это общий вход к идентичности проекта и владельцам продуктовых фактов. Открывать
его при первом связанном обращении Сергея: «мой сайт», «похудение.рф», «наш
канал», «бот», «МК», «рецепты», «калорийный», «консультация», «сопровождение».
Сокращение помогает найти объект, но не утверждает новое публичное название,
домен или цену. Проверка нужна и при обычном упоминании, а не только при правке.

В старой рабочей копии читать принятые документы и registry из свежего
`origin/main` по [правилам потоков](../CHAT_WORKSTREAMS.md). История чата,
старое название репозитория, черновик, дизайн-макет и поисковая выдача не
заменяют владельца факта. Разделы боковой панели не дают чатам общую память.

## Обязательное правило адресов

Перенос завершён 18.10.2026. В ответах и новых пользовательских ссылках использовать
только `https://похудение-это-есть.рф` и нужный путь этого сайта. Не выдавать прежний
host как второй вход, альтернативу или «серверную» версию. Административный
поддомен и `old` имеют отдельные назначения ниже. История, имена репозитория и
техническая совместимость не являются пользовательскими адресами.

## Название и домен

| Объект | Каноническое обозначение | Как использовать |
|---|---|---|
| Название сайта в шапке | **Похудение — это есть.рф** | Название, а не URL; регистр оформления задаёт поверхность |
| Название без доменного окончания | **Похудение — это есть!** | Утверждённая форма, используемая в кабинете и сервисных письмах |
| Полный публичный домен | `похудение-это-есть.рф` | В URL сохранять все слова и дефисы |
| Репозиторий и техническая платформа | `edabalans.ru` | Технический идентификатор и совместимый старый origin; новые пользовательские маршруты используют полный публичный домен |

«Еда Баланса» и «Едабаланс» не подставляются вместо полного названия сайта.
«Похудение.рф» в репликах Сергея всегда означает сокращённое название
`похудение-это-есть.рф`, в том числе при переносе с Tilda. Отдельного короткого
домена у владельца нет; не предлагать его как цель переноса. Подтверждено
Сергеем 18.10.2026.
Дословную цитату или готовый текст Сергея не переписывать
молча. Если он явно просит переименовать проект, это новое решение владельца.
В этой задаче существующие визуальные варианты шапок не переименовываются.

### Как чату выбрать маршрут и где изменить карту

1. Читать свежий `origin/main:docs/knowledge-base/PROJECT_IDENTITY.md` перед
   каждой отправкой. На production этот же канон лежит в
   `/opt/edabalans/docs/knowledge-base/PROJECT_IDENTITY.md`; вход —
   `docs/README.md`. Это единая карта, отдельная копия в личном серверном каталоге не нужна.
2. Определять категорию по цели сообщения: платёж/финансовое обязательство →
   финансовый; результат рекламы/расходы Директа/воронка → рекламный;
   разработка, деплой, сбой или восстановление → технический;
   календарь, таймдоска и личное планирование → planning, только личному;
   остальные личные дела → технический. Например,
   аудит эффективности Директа относится к рекламе, а исправление его API —
   к разработке. Уведомление об аварийной остановке рекламы остаётся техническим.
3. Для уже работающего автоматического события применять его действующий
   маршрут из таблицы. Не перенастраивать его вслед за категорией нового
   разового сообщения. Основной продуктовый бот обслуживает клиентские
   сценарии и явно перечисленные исключения владельцу.
4. Явно указанные Сергеем бот и получатель имеют приоритет. Если смысл не
   раскрывает категорию, использовать технический маршрут; не рассылать
   один отчёт несколькими ботами. Отсутствие токена/ошибка API не меняют роль.
5. Перенос потока по просьбе Сергея означает изменение его действующей
   конфигурации/отправителя и этой карты с проверкой фактического бота и
   получателей. Одна правка Markdown не переключает автоматическую доставку.
   Секретные значения находятся в `/opt/edabalans/.env` и Cloudflare secrets;
   в Git и ответы их не переносить.

В этом проекте команда «отправь мне в Telegram» использует оба аккаунта и роль
бота из этого раздела, если Сергей прямо не указал иной маршрут. Это проектное
решение имеет приоритет над общим личным адресатом из
`sergey-development-workflow`. Наличие адреса не разрешает отправку: нужны
прямое поручение и конкретный получатель. Ссылки с `start` для рекламы и персональной доставки
берутся из общего каталога атрибуции, а не собираются из имени продукта.

### Проверка перед разовой отправкой

Обязательна для отчётов Codex, инструкций, проверок и других разовых сообщений,
включая отправку из SSH/Python-скрипта напрямую в Telegram API. Исправление
файла на диске не обновляет старые инструкции в истории уже открытого чата.

1. Перед отправкой перечитать этот раздел из актуального `origin/main`, затем
   выбрать роль по содержанию сообщения. Старый prompt, прежний receipt,
   checkpoint и разовый скрипт не задают маршрут новой отправки. Отчёт о выпуске
   приложения — техническое сообщение; отчёт о деньгах — финансовое, об
   эффективности Директа — рекламное независимо от того, какой чат их готовит.
2. Использовать только токен выбранной роли из действующей конфигурации. Для
   технического отчёта — `TECHNICAL_TELEGRAM_BOT_TOKEN`; использование
   `MARKETING_TELEGRAM_BOT_TOKEN` для такого отчёта запрещено. Отсутствие токена
   или недоступность диалога не разрешают подставить токен другого бота.
3. До `sendMessage` проверить `getMe` тем же клиентом и с тем же токеном,
   которыми пойдёт сообщение. Username должен совпасть с ботом выбранной роли
   из таблицы выше. Несовпадение или ошибка проверки блокируют отправку;
   проверка конфигурации выполняется без пробного сообщения.
4. Проверить обоих получателей из действующих настроек выбранной роли, если
   Сергей прямо не указал других. Сохранить username фактически использованного
   бота и результат отдельно по каждому получателю, без токенов. Частичный успех
   не выдавать за доставку обоим и не повторять успешную доставку.
5. Не пересылать уже доставленный отчёт ради проверки исправления и не удалять
   ошибочное сообщение без отдельного поручения. Историческую ошибку пометить
   как ошибку маршрута, а не использовать её как образец следующей отправки.

## Поддержание полноты

При создании или переименовании продукта обновлять его активную редакцию и
маршрут в `PRODUCT_CATALOG.md`; при изменении контакта — владельца настройки и
эту карту; при доменном переносе — доменный контракт и карту адресов. Не
создавать второй каталог в skill, карточке курса, плане или истории чата.
Новый постоянный канал/бот добавляется после отдельного решения о его роли.

Неустановленное имя, адрес, программа или статус отмечаются как неизвестные;
поиск продолжается у владельца факта. Вопрос Сергею нужен только когда
источники не разрешают различие смысла. `status` редакционного каталога,
техническая готовность приложения и доступность продажи — разные факты.
В частности, наличие активной цены сопровождения не даёт чату права молча
переписать его редакционный `status` или обещать доступ к приложению.
