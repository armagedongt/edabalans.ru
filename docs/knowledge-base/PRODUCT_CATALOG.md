# Канонический каталог продуктов и тарифов

Статус: `current`  
Состояние внедрения: `implemented`  
Владелец содержания: Сергей Воронцов

## Назначение

Один версионный документ `product-catalog/core` в `managed_document_versions`
владеет пользовательскими названиями продуктов и тарифов, короткими
дескрипшнами и внутренним редакционным контекстом для ИИ.

Публичные поверхности получают эти значения по стабильному коду: личный кабинет,
Мастер-класс, карточки допродаж и серверный блок входных тарифов. Новая страница
или бот не должен добавлять свою строку с названием продукта: он получает данные
из этого каталога.

Имена сайта, полные домены и роли каналов/ботов находятся в
[общем входе каталога](PROJECT_IDENTITY.md). Редактор продуктов не хранит цены,
DNS и настройки мессенджеров: общий вход направляет к их владельцам.

## Чтение до ответа или текста

Каталог обязателен при первом упоминании курса, услуги или тарифа в задаче,
даже если Сергей не просил менять название. Короткая реплика владельца —
ключ поиска стабильного кода. Не превращать её в новую публичную формулировку.

1. Прочитать активную редакцию через защищённый
   `GET /admin/api/product-catalog` или редактор `/admin/products`.
   В ответе API документ находится в `active.manifest`: списки `products` и
   `tariffs`; `active.version` указывает проверенную редакцию.
2. Найти продукт по `code`. `fullName` — полное публичное название, `shortName` —
   утверждённая короткая форма, `descriptor` — точный дескрипшн, `marketing` —
   внутренний контекст. Для тарифа читать `name`, `descriptor`, `products`.
   Не делать собственное сокращение вместо `shortName` и не выводить `marketing`
   пользователю как готовое описание.
3. Для концепции и программы перейти к модулю из таблицы ниже; для цены — к
   активному pricing, для адреса — к `PROJECT_IDENTITY.md`. Редакционный `status`
   не заменяет техническую готовность, право доступа или доступность продажи.
4. При следующем обращении перечитать источник, если факт менялся, речь о
   действующей цене/статусе или чат продолжает работу после перерыва. Не считать
   однажды прочитанную редакцию вечной памятью.

Если API-сессии нет, установленный SSH-маршрут `edabalans-prod` позволяет
**только прочитать** активную строку `managed_document_versions` для
`document_type=product-catalog`, `document_key=core`, `is_active=true` в backend.
При аудите использовать read-only транзакцию. Не вызывать `ensure_seed_document`
или публикацию для чтения: они могут записать данные.

Без доступа к активной редакции резервный источник —
`PRODUCT_CATALOG_SEED` в `backend/app/product_catalog_service.py` из свежего
`origin/main`. Он содержит точные поля названий, но является fallback, а не
доказательством текущей production-редакции. Для внутреннего контекста учитывать
нормализацию и `MARKETING_CONTEXTS` того же сервиса. При недоступности runtime
явно обозначить предел проверки; не выдумывать название, цену или программу.

## Граница

В редакторе `/admin/products` доступны только редакционные поля. Они разделены на
«Показывается пользователю» и «Для работы и ИИ». Внутренний контекст хранится
одним полем с подзаголовками: без сокращения исходных маркетинговых тезисов,
механики, результатов, болей и источника фактов. Он не выводится клиенту сам по
себе и служит источником для последующего написания текста.

Цены, скидки и временные ступени принадлежат `PRICING_CATALOG.md`. Права доступа,
коды ресурсов и идентификаторы приложений принадлежат контуру доступов; они не
показываются в редакторе и не дублируются в каноне продуктов.

Состав тарифов хранится для описания тарифа, но его изменение не выполняется
редактором: оно меняет доступы и требует отдельной задачи.

## Быстрый маршрут `copy-only`

Изменение существующего публичного названия, дескрипшна, статуса или внутреннего
редакционного контекста не является изменением схемы базы. Оно выполняется через
штатный редактор `/admin/products` либо тот же контракт
`PUT /admin/api/product-catalog`. Сохранение создаёт новую активную версию
`product-catalog/core`, фиксирует автора и сохраняет предыдущую редакцию для
восстановления.

Для такого изменения не создавать Alembic migration, не запускать migration-выпуск
с backup/test restore и не размножать тот же текст по потребляющим страницам. После
сохранения достаточно проверить активную версию каталога и одну публичную поверхность,
которая читает изменённое поле.

Если Сергей дал готовую пользовательскую формулировку, каталог сохраняет её дословно.
При редакционном, юридическом или медицинском сомнении возможную замену сначала
согласовать с Сергеем; самостоятельно менять смысл или степень категоричности нельзя.

Alembic нужен только при реальном изменении схемы, обязательного состава либо
системных полей каталога. Такие изменения штатный редактор намеренно отклоняет и они
оформляются отдельной технической задачей.

Текущие публичные поля продуктов `recordings` и `consultation` утверждены
владельцем 30.08.2026. Их нельзя сокращать, перефразировать под поверхность или
возвращать к старым названиям без нового прямого решения владельца. Точные строки
принадлежат активной версии `product-catalog/core`; fallback-каталог в коде обязан
их зеркалировать. Дескрипшн не обязан начинаться со слова «Как», если владелец
утвердил другую формулировку.

## Названия комплектов Мастер-класса

У каждого самостоятельного продукта есть одно публичное название из этого
каталога. Карточка допродажи, описание в поп-апе и строка «В составе» берут
его по стабильному коду; локальную версию названия на странице создавать нельзя.

До отдельного решения о более удачном имени неполного комплекта действуют два
временных публичных названия:

1. **Все самостоятельные программы** — для любого цифрового комплекта, включая
   временно неполный.
2. **Все самостоятельные программы с консультацией** — для любого комплекта с
   консультацией, включая временно неполный.

Фактический состав всё равно всегда раскрывается в блоке «В составе». Позднее
владелец отдельно утвердит лучшее имя неполного комплекта; до этого не создавать
локальные перечисления названий продуктов и новые маркетинговые варианты.

Точное правило сборки хранится рядом с runtime в
[`modules/masterclass/OFFERS_MODULE.md`](modules/masterclass/OFFERS_MODULE.md).
Базовые и текущие суммы по-прежнему принадлежат
[`PRICING_CATALOG.md`](PRICING_CATALOG.md).

## Правило добавления нового продукта

1. Сначала создать стабильный код и технические правила доступа отдельно.
2. Затем добавить продукт в канонический каталог с публичными полями и
   внутренним контекстом.
3. Новые пользовательские интерфейсы используют каталог по коду, а не собственные
   копии текста.
4. Цены добавляются отдельной строкой в каталог цен.

## Источники содержания

- Мастер-класс, рецепты, Калорийный курс, консультация и сопровождение сверяются с
  главной страницей сайта.
- Бесплатный интенсив берёт короткую формулировку и подробный контекст из
  `INTENSIVE_PAGES.md` и `plans/FREE_INTENSIVE_LAST_WEIGHT_LOSS_CONCEPT.md`.
- Если для продукта нет отдельного утверждённого описания, это прямо указывается
  во внутреннем поле. Нельзя заменять отсутствующий источник выдуманными
  маркетинговыми обещаниями.

## Полнота и проверенные ограничения

Аудит 03.10.2026 подтвердил в production-редакции `v5` восемь продуктов и три
входных тарифа: у каждого продукта заполнены `fullName`, `shortName`,
`descriptor` и внутренний контекст. Это датированный результат проверки,
а не фиксированный навсегда состав каталога.

В рамках аудита штатным сервисом опубликована `v6`: только внутренний контекст
`recordings` приведён к уже утверждённому источнику `MARKETING_CONTEXTS`.
Старое имя из служебного описания удалено; публичные поля, цены и состав не
менялись. Предыдущая редакция сохранена в истории версий.

Каталог не является полным ТЗ всех будущих услуг. Подробная программа двух
разборов ещё не утверждена; название и дескрипшн уже утверждены, поэтому
отсутствие программы не разрешает вернуть старое имя «Записи консультаций
других участников». Для консультации и сопровождения есть описание формата,
но отдельная исчерпывающая программа отсутствует. Не дополнять её обещаниями.

Редакционный `coaching.status=planned` в проверенной версии существует наряду
с реализованной коммерческой подпиской. За фактической покупкой и условиями
обращаться к `platform.commerce`; эти два статуса не объединять догадкой.
Справочник контактов и адресов вынесен в `PROJECT_IDENTITY.md`, цены — в pricing,
поэтому отсутствие этих полей в редакторе продуктов не является отсутствием фактов.
