# Постоянная папка материалов

## Для Сергея

Папка `D:\Codex\work\edabalans-materials` — одна рабочая копия для Obsidian
и Codex. Откройте её в Obsidian как хранилище. `Каталог.md` содержит ссылки на
сами материалы: текст нигде не дублируется. Измените файл, сохраните, откройте
ярлык «Опубликовать материалы», выберите изменения и нажмите «Опубликовать выбранные».
Можно выбрать один материал или несколько. Неизменённые материалы не пересылаются.

«Получить обновления с сервера» обновляет чистые файлы и сохраняет ваши черновики.
Если ту же статью изменили на сервере, появится конфликт: попросите Codex объединить
правки. Название папки и пути повторять в каждом поручении не нужно.

Сервер хранит принятые редакции. Эта папка хранит рабочие правки и номер серверной
основы. Выпуск программного кода не заменяет ни серверный текст, ни локальные правки.
Успешная публикация обновляет основу того же файла. Правки, сделанные в Obsidian
во время публикации, остаются новым черновиком.

## Маршрут Codex

Любой запрос о существующем материале сначала разрешать через `Каталог.md` и
`.publisher/state.json` этой папки. Редактировать найденный файл непосредственно;
не создавать его редакционную копию в worktree, `work/` репозитория или временном
экспорте. Worktree разрешён для разработки кода, но не становится оригиналом текста.
Если файл ещё не зарегистрирован, использовать обновление каталога; не искать
случайный старый Markdown в checkout вместо действующей редакции.

Рабочие команды из актуального checkout:

```powershell
python tools/editorial_vault.py status
python tools/editorial_vault.py refresh
python tools/editorial_vault.py publish public:program blog:ARTICLE_SLUG
python tools/editorial_vault.py publish --owner-edited course:masterclass-21:STEP_ID
```

`publish` требует точные выбранные IDs. Автоматического «перезаписать всё» нет.
Без команды публикации сохранять черновик; по команде публикации выполнить тот же
клиент, что вызывает ярлык. Проверить результат каждого выбранного материала.
Авторскую редактуру выполнять через Писаря и существующие договоры проверки.

Ярлык публикует с профилем `owner_edited`: это явное действие Сергея для его
собственных сохранённых правок в Obsidian. В CLI ему соответствует
`publish --owner-edited <IDs>`. Профиль освобождает ручную редактуру владельца
от отчётов ИИ-Писаря, но сохраняет защиту версии, конфликты, проверки серверного
формата и ограничения рецептов. Codex не применяет этот профиль к своему
написанному или переработанному тексту: для такой работы курса остаётся обычный
`publish` с writer gate. Передача готовых правок Сергея без ИИ-редактуры может
использовать профиль владельца; он не является способом получить фиктивный pass.

| Остальная логика бота и новые картинки | Не имеют универсального редактирования этой кнопкой; сохраняются действующие владельцы и продуктовые операции |

У HTML-материала расширение `.md` позволяет видеть его в Obsidian; служебный
`format` хранится отдельно, публикатор отправляет HTML как HTML. Преобразование
в полноценную MD-разметку — отдельная адресная работа с проверкой содержания и вставок.

Новые картинки пока идут через существующий маршрут файлов продукта и Codex:
универсального media-upload API нет. Кнопка не отправляет все изображения и не
обещает публикацию неизвестного локального ресурса. Обновление существующего
текста со стабильными ссылками не требует повторной доставки картинок.

Для текста обычного курса, написанного или переработанного Codex, действует
существующий `verify_publish_gate`: рядом со
служебным состоянием нужны `.publisher/reviews/<ID с двоеточиями, заменёнными
на подчёркивания>.pack.json` и `.report.json`, привязанные к точному хешу рабочего
файла. Codex получает их штатной проверкой Писаря; клиент не создаёт фиктивный pass.
Неподключённые рецепты и файлы без серверного профиля блокируются до выполнения
собственного маршрута. Git-материал курса с подключённым профилем использует тот
же договор проверки текста курса, затем свой Git API; договор рецептов — ниже.
У непубликованного `source-current` renderer удаляет служебные метаданные. Это
поведение сохраняет серверный профиль; клиент не выбирает его вручную и не
рассылает полные исходники без проверки текущей основы.

### Git-материал курса

`day-01-article-02` сохраняет прежний ID `course:masterclass-21:day-01-article-02`
и файл в постоянной папке. Серверный `publication_profile` связывает его с
существующим `/admin/api/editorial/masterclass/materials/<step_id>` и фиксированным
Git-оригиналом; пользователь не выбирает произвольный путь. Draft и publish
проверяют Git SHA. Успех подтверждается совпадением runtime hash с принятым текстом,
до доставки выпуск остаётся `queued`.

При обновлении прежней локальной регистрации меняется маршрут публикации того же
файла. Чистый файл обновляется; локальный черновик сохраняется, а расхождение с
серверной основой отмечается конфликтом. Незавершённую публикацию сначала разрешает
Codex. Исторические `day-07-recipe-*` этим подключением не становятся обычными
редактируемыми статьями.

### Полный исходник source-current

Если активный шаг ссылается на существующий Markdown в `source-current` и ещё не
имеет DB-редакции, сервер объявляет профиль `masterclass-source-current`.
Git-особые материалы и рецепты не переводятся на него. В действующей программе
такой fallback сейчас у `day-18-video-01`; это результат активной структуры,
а не новый фиксированный список материалов.

GET материала возвращает полный `source_content`, `source_hash` и профиль.
Первый PUT на существующий `/admin/api/courses/masterclass-21/materials/<step_id>`
требует `format: markdown`, `expected_version: 0` и `expected_source_hash` точного
прочитанного исходника. Изменившийся Git-исходник даёт конфликт.

Клиент `tools/publish_course_material.py` при явном `--expected-version 0`
принимает `--expected-source-hash` из исходного GET; автоматически выбранная
актуальная версия передаёт hash того же GET. Сохранённый hash не заменять свежим
ради обхода конфликта. Постоянная папка использует свой сохранённый baseline.

Сервер сохраняет полный MD и свой профиль в той же версии, что HTML; renderer убирает служебную
шапку из читательского текста, сохраняя прежние вставки. После первого принятия
новые правки читаются из DB-оригинала, а прежний Git fallback больше не заменяет
его. Следующие PUT используют обычный expected_version и сохраняют профиль;
переключение материала на HTML этим маршрутом запрещено.

Восстановление такой редакции через существующий API истории проверяет текущий
expected_version, возвращает точный сохранённый HTML и полный MD вместе с его
профилем. Обычные материалы этим правилом не очищаются от авторского текста.
Клиент использует тот же постоянный файл и writer gate либо явный профиль
ручных правок владельца; отдельного каталога копий не создаётся.

### Главная

`content/public-site/homepage/homepage.md` — seed одного документа, после первой
редакции оригиналом служит активная серверная версия. Текущий документ содержит
163 текстовых поля в 11 разделах, включая 17 вопросов FAQ и подписи пяти карточек.
Пять подробных описаний продуктов остаются отдельными существующими оригиналами,
а цены — данными каталога цен. Их тексты и значения в главную не копируются.

Редактировать текст внутри парных комментариев `homepage:<key>`. Ключи,
`homepage_inline(...)` и существующую строчную разметку сохранять: менять
структуру через Codex. API `GET/PUT /admin/api/public-site/homepage` использует
`markdown` и `expected_version`. При публикации компилируются фрагменты всех
полей; сервер подставляет их в прежний HTML целиком. Нет отдельного запроса на
каждый блок. Внешнее оформление, изображения, ссылки встроенных действий и
аналитические идентификаторы сохраняются. Полный договор — [PUBLIC_SITE](PUBLIC_SITE.md).

### Интенсив

Единственный Git-оригинал — `content/masterclass/editorial/weight-loss-roadmap.md`.
`GET /admin/api/editorial/intensive` возвращает опубликованный файл, draft и
`runtime_source.sha256`; `/draft` и `/publish` используют ожидаемые Git SHA.
Нельзя менять порядок структурных маркеров и подменять индивидуальный профиль
обычной статьёй: их проверяет существующий renderer интенсива. API публикует
точный файл в main, штатный выпуск доставляет его серверу. До совпадения hash
runtime с опубликованным текстом клиент сообщает `queued`, а не завершённую
публикацию. Локальную правку, появившуюся за это время, не заменять.

### Рецепты

День 7 и самостоятельный курс используют те же `day-15-recipe-*`; прежние
одноимённые Git-статьи дня 7 не становятся местом обычной правки рецепта.
Подключение полного оригинала выполняет Codex по
[договору рецептов](../../content/masterclass/recipes/README.md): POST
`/admin/api/courses/masterclass-21/materials/<step_id>/recipe-source` принимает
`content`, `format: markdown`, `expected_version` только при совпадении SHA-256
оригинала с metadata и его rendered HTML с опубликованной версией. Не совпало —
найти принятую редакцию; не перепубликовывать старую основу.

После подключения обычный PUT сохраняет полный MD, версию статьи и namespace
калькулятора одной транзакцией. GET показывает `recipe_authoring.status`:
`ready`, `adoption_required` или `original_sync_required`. Скрытые комментарии
расчёта, изображения, компоненты, цели ссылок и заголовок защищены от изменения
этим маршрутом. Числа и растровые карточки изменять через существующий workflow
рецептов. Восстановление полной MD-версии также синхронизирует калькулятор;
исторический HTML без исходника этим маршрутом не восстанавливается.

### Сообщения бота

Файл в Obsidian имеет расширение `.md`, но его тело — точный `body_source` в
Telegram HTML, а не Markdown сайта. Не переводить его автоматически в другую
разметку. Служебная оболочка показывает код, цель, ТЗ писателю и места использования;
контекст графа — отображение действующих связей, а не новая логика рассылки.
Редактируемые оригиналы обнаруживаются через `/bot-api/content-audit`, чтение
использует `/bot-api/content/<code>/authoring`, запись — существующие `/validate`
и `/publish` с `expected_version`. Изменение шаблона не отправляет сообщения,
не меняет условия, таймеры, получателей или расписание. Текст сообщения и
исполняемый граф публикуются как разные оригиналы; договор графа — ниже.
Фото без подписи тоже читается как оригинал: пустое тело не превращается в
выдуманный текст. При публикации остаются прежние серверные проверки подписи и
формата сообщения; возможность чтения не отменяет эти проверки.

### Исполняемая логика двух цепочек

`Логика бота/welcome_intensive.md` и `prepurchase_nurture.md` содержат JSON
самих существующих sequence/steps/edges, а не пересказ условий. Сохраняются все
шаги и связи, включая отключённые, задержки, приоритеты, условия, nullable-поля
и configuration. `content_code` ссылается на оригинал сообщения; его текст не
копируется в граф. Служебную метку `_editorial_graph` вручную не менять.

GET `/bot-api/sequences/<code>/source` возвращает опубликованный оригинал и
черновик. PUT `/source/draft` принимает source, expected_published и
expected_draft; POST `/source/publish` — ожидаемые редакции обеих стадий.
Каждая ожидаемая редакция содержит `version` и `sha256`; сервер также проверяет,
что черновик создан от текущего опубликованного оригинала. После неоднозначного
сетевого результата клиент сначала читает принятый граф, а не повторяет запись
по арифметике номера версии.

Публикация создаёт новую исполняемую версию, сохраняет архивные оригиналы и
не перезапускает существующие runs. Они остаются привязаны к прежней версии;
переход из такой цепочки в другую по действующему механизму выбирает последнюю
опубликованную версию целевой цепочки. После первой редакционной публикации seed
не переписывает принятый граф; создание одного черновика владение не переключает.
Это договор двух цепочек, а не полный файл всей логики бота: стартовый router,
maintenance и событийные процессы после покупки сохраняют прежние источники.
Имя и описание редакции принадлежат её оригиналу. Общая запись Sequence сохраняет
стабильное техническое имя для прежнего реестра админки; переименование новой
редакции не меняет имя в архивных оригиналах.

### Каталог, названия и цены

`Каталог/Продукты и тарифы.md` — рабочая редакция полного
`product-catalog/core`, один JSON-блок без второй таблицы с копиями текстов.
Меняются названия, descriptor, marketing и разрешённый статус продукта/тарифа;
коды, порядок и состав защищены. GET/PUT `/admin/api/product-catalog` использует
активный manifest и expected_version. Цены и права доступа не становятся
редакционными полями каталога.

`Курсы/<code>/Названия.md` содержит полный активный manifest поддерживаемого
курса (`masterclass-21`, `calories`). Обычный клиент разрешает только title
дня/этапа и title/label существующего материала. PUT
`/admin/api/courses/<code>/structure` сохраняет expected_version и полную структуру;
переименование не меняет ID, порядок, hidden/locked, задания, required и прогресс.
Название продукта берётся из каталога, а не переопределяется этим файлом.
Равный нормализованный оригинал может подтверждаться той же версией — это штатное
сохранение без нового выпуска. Добавление/перестановка остаются задачами Codex.

`Каталог/Цены.md` содержит полный оригинал действующей pricing version в одном
JSON-блоке. В Obsidian можно менять `regular_amount`, `compare_at_amount`,
`sale_amount`, название версии и примечание. Суммы сохраняются с точностью до
копейки; nullable-поля могут оставаться `null`. Коды, названия строк, разделы,
состав ресурсов, валюта, порядок, `enabled` и metadata сохраняются. Имена продуктов
по-прежнему принадлежат каталогу продуктов. Служебную метку `_editorial_pricing`
вручную не менять.

Кнопка получает текущую активную редакцию, создаёт её точный черновик, сохраняет
изменения и отдельно активирует проверенный результат. Чужой или устаревший draft
не присваивается и не перезаписывается; уже существующий совпадающий черновик
можно публиковать только с той же активной основой. После неоднозначного сетевого
ответа клиент подтверждает точный принятый оригинал чтением. Отсутствие active
версии — ошибка, draft не подставляется вместо неё. Полный серверный договор и
влияние на новые покупки — [каталог цен](PRICING_CATALOG.md).

Существующая админка сохраняет возможность менять `enabled` под той же защитой
редакции; ограничение денежными полями относится к обычной кнопке материалов.
Активация не создаёт платёж или списание; уже созданные платежи и действующие
подписки сохраняют прежние снимки. Изменение фактических цен требует отдельного
поручения Сергея, подготовка и установка клиента их не меняет.

Прежний файл цен для чтения переводится в новый формат только когда он чистый и
не имеет незавершённой публикации. Его путь сохраняется. Если в нём есть локальные
правки, обновление оставляет файл и просит Codex перенести их в действующий
оригинал; старый JSON не отправляется новым протоколом автоматически.

### Письма

Оригиналы пяти шаблонов находятся в `content/service-messages/email/`:
`account-onboarding`, `account-direct`, `account-messenger`, `login-code`,
`renewal-failed`. Действующие отправители читают эти файлы, а не отдельные копии
текста. Один `.md` содержит именованные разделы `##` и точный текст в блоках
`text`/`html`; это шаблоны писем, не Markdown статьи. Имена разделов и переменные
`${...}` сохранять: они проверяются схемой отправителя.

API `/admin/api/editorial/service-emails` перечисляет разрешённые шаблоны;
`/<code>` возвращает Git-оригинал, draft и hash runtime. `/draft` и `/publish`
используют тот же договор Git SHA, что интенсив. До совпадения runtime hash
публикация остаётся queued. Редактирование не отправляет письмо и не меняет
условия отправки, получателя, SMTP, авторизацию или платежную логику. Здесь
показаны именно подключённые шаблоны, а не обещание полного каталога всех
возможных сообщений проекта.

## Версии, ошибки и восстановление

`.publisher/state.json` содержит ID, путь, тип, base_version, base_hash,
статус конфликта и pending_draft. Служебные поля не вставляются в авторский MD:
ограниченный frontmatter блога остаётся совместимым. Переводы строк Windows
нормализуются только для сравнения, содержание файла сохраняется.

Перед записью клиент получает текущую редакцию и сравнивает обе основы; API
дополнительно проверяет expected_version. При конфликте запись не выполняется.
Операции защищены одним локальным `operation.lock`. После аварийного закрытия
Codex проверяет отсутствие живого процесса перед удалением этого конкретного lock.

Неопределённый результат сети сначала разрешать чтением. Если текст уже принят,
новую редакцию не создавать. Для блога сохранение и публикация — разные операции;
pending_draft остаётся до подтверждения публичной редакции. Частичная ошибка
одного файла не отменяет успешные результаты соседних и показывается отдельно.

Откат выполнять существующим API истории выбранного материала, затем `refresh`.
Если локально есть черновик, сохранить/объединить его, не заменять молча. Откат
не удаляет историю и не пересобирает базу курса.

## Установка клиента

`tools/install_editorial_vault.ps1` устанавливает версионируемые инструменты в
`D:\Codex\tools\edabalans-editorial`, создаёт ярлыки на рабочем столе и постоянную
папку. Исходный код инструмента принадлежит Git, эта установленная копия — runtime,
а не ещё один каталог текстов. При изменении клиента повторить установку.
Требуется существующий Python с Tkinter и SSH-алиас `edabalans-prod`; серверные
пароли не сохраняются локально. Альтернатива — существующие переменные
EDABALANS_ADMIN_USERNAME / EDABALANS_ADMIN_USER и EDABALANS_ADMIN_PASSWORD,
HTTP Basic исключительно через HTTPS.

## Адресные изменения структуры через Codex

Название дня/материала, порядок, добавление, перемещение и скрытие принадлежат
структурному документу курса, а не имени MD-файла или заголовку статьи. Для такой
задачи открыть продуктовый структурный/runtime-контракт и получить активную структуру.
Переименование и скрытие поддерживает обычный PUT с expected_version. Добавление,
удаление, перемещение и перестановку оба обычных редакторских PUT запрещают (422):
не посылать туда изменённый список IDs. Новые шаги Мастер-класса добавлять существующим
`publish_course_seed_additions` (`backend/scripts/publish_course_structure_seed.py`),
который объединяет добавления с активной версией и задаёт requiredForAllAfterRevision.
Для перестановки/перемещения пока нет универсального публичного метода: это отдельная
адресная структурная задача Codex с изменением активного payload и проверкой договора
прогресса; не применять к ней одноразовый `publish_final_masterclass_structure.py`,
который предназначен для конкретной исторической сборки дней 6–20. Сохранить step_id,
связи, доступы, события и накопленный прогресс; проверять required_step_ids и
structure_revision_no. Не пересоздавать ContentItem или всю базу ради перестановки.
После принятия структуры обновить каталог, чтобы название и связь показывались
актуально; рабочие черновики текстов не трогать.

Добавление статьи блога остаётся Codex + manifest + обычный выпуск кода;
неизвестный slug не создаётся этим текстовым API. Общий материал в нескольких
поверхностях правится по одному ID, с проверкой всех потребителей.
