# Яндекс.Директ: эксплуатация, отчёты и передача работы

Это первый файл, который читает новый чат перед изменением Директа или ответом о
результатах рекламы. Операции выполняются API-first. Браузер нужен только для того,
чего нет в API, ручной проверки визуального превью и действий владельца. Значения
токенов и паролей не копируются в этот файл, Git, логи и сообщения.

занят, сначала по той же последовательности архивируется освобождаемый вариант.
Предпочтительная раскладка — контроль, текущий тест и слот следующего кандидата.
Критерии выбора между отдельным `ad_id` и заменой внутри существующего объявления,
а также правила измерения смешанных суток принадлежат
[методологии тестов](YANDEX_DIRECT_CREATIVE_TESTING.md#техническая-конструкция-турнира).

## Атрибуция и смысл событий

Посадка заранее получает одноразовый `U...` и сохраняет UTM/`yclid`, мессенджер,
способ входа и устройство. `link_prepared` не означает действие человека.
`landing_button_click` — нажатие кнопки; `landing_qr_scan` — фактическое открытие
QR; `start_first`/подтверждённый MAX delivery — реальный Start. Параметр устройства
означает устройство посадки: при QR это ПК, даже если сканирует телефон.

После Start источник сохраняется для всей воронки: открытие персональной ссылки,
главной интенсива, дня 1, видео и кнопки в конце дня. Событие блокировки после
успешного первого сообщения — отток пользователя, не техническая ошибка 403.

Для глубины дня 1 браузер отправляет идемпотентные `page_progress` с порогами
`25/50/75/100`, а видео — `video_engaged`, `video_progress` `25/50/75` и
`video_complete` как `100`. В `details` обязательны `day=1` и
`progress_percent`; повторное достижение порога тем же пользователем не создаёт
новую строку. Отчёт связывает глубину с рекламной когортой: CTA/QR сделан в
отчётные сутки, Start и дальнейшее действие произошло до среза 03:00.

## Ежедневный отчёт

Срез формируется ежедневно после 03:00 МСК за предыдущие календарные сутки и
отправляется дополнительным ботом после 06:00 МСК. Direct API отдаёт календарные
сутки. В таблицах каналов и объявлений Start относится к CTA/QR того же календарного
дня и может произойти до 03:00 следующей ночи: так расход, объявление и лид остаются
в одной рекламной когорте. Эта же рекламная когорта продолжается в единой таблице
пути до дня 1, глубины текста, видео, финальной кнопки и подписки.
Повторные, технические, неизвестные и органические Start не входят в CPA нового лида.
CTA/QR считаются по всем уникальным `journey_id`, включая тех, кто не запустил бота.
Снимок и готовые Telegram-сообщения сохраняются в
`marketing_daily_reports`, поэтому другой чат читает уже готовый результат, а не
тратит повторные запросы.
Поздний Start может произойти через несколько дней после CTA/QR: пока он несёт исходный
`journey_id`, это не ошибка атрибуции. Аварийное предупреждение появляется только у
Яндекс-Start без `journey_id`, а не из-за того, что посадочное событие вышло за окно
конкретного суточного отчёта.

Отчёт приходит одним сообщением и содержит три таблицы:

1. «РСЯ»: строка ИТОГО и строки каждого объявления.
2. «Поиск»: тот же состав строк для поисковой кампании. В обеих таблицах показаны
   показы, рекламные клики, CTR, расход за календарный день, подтверждённый Start и
   CPA Start. Под каждой таблицей — итог предыдущего дня. В подвале отдельно указаны
   общий дневной расход и для каждой кампании расход/лимит/остаток текущей недели.
3. «Путь лида»: одна вертикальная таблица от рекламного клика до подписки. Строки:
   клики рекламы; визиты посадки; подстроки телефон и ПК; зафиксированные переходы
   в бота; подстроки кнопка и QR; реальный Start; открытие дня 1; отправленное
   напоминание; открытие не позднее трёх часов после напоминания; текст
   `25/50/75/100`; запуск видео и видео `25/50/75/100`; кнопка в конце дня;
   подтверждённая подписка. Колонки: количество, конверсия от логического
   родительского этапа и конверсия от рекламного клика.

«Клики рекламы» — данные Директа. «Посетили посадку» — `Sessions` из отчёта
Директа, то есть визиты Метрики после клика. Это не одно и то же: счётчик может не
загрузиться после клика, а один рекламный клик может дать повторный визит, поэтому
числа иногда различаются и `Sessions` даже может быть немного больше кликов.
Колонка называется «Кол-во», а не «Людей»: клики и визиты не являются уникальными
людьми, тогда как CTA/QR далее дедуплицируются по `journey_id`.

Текущая цепочка отправляет первое напоминание через 15 минут, если день 1 ещё не
открыт. Отчёт отдельно считает получивших его и тех, кто открыл день 1 в течение
трёх часов после фактической отправки. Эти данные читаются из
`tg_step_deliveries` по `welcome_reminder_day1`, а не выводятся из косвенных событий.

TG/MAX продолжают сохраняться в БД и доступны подробному анализу, но в ежедневное
сообщение не выводятся. Телефон/ПК и кнопка/QR выводятся подстроками единой воронки.
Если посадочное событие, глубина или напоминание ещё
не инструментированы для рассматриваемой даты, таблица показывает `НД`, а не
ложный ноль. Значение `0` используется только для исправно собираемого сигнала.
Границы включения задаются `MARKETING_REPORT_ENTRY_TRACKING_FROM` и
`MARKETING_REPORT_DEPTH_TRACKING_FROM`; их ставят на первую полную календарную дату
после production-выпуска соответствующего события.
Сообщения отправляются через Telegram Bot API `sendRichMessage`: нативные таблицы
с рамками, полосами и переносом ячеек. При несовместимости клиента или API бот
переходит на карточки «один объект — несколько строк», а не на псевдотаблицу из
пробелов. Изображения отчёта не генерируются: нативная таблица остаётся доступным
текстом, масштабируется клиентом и не требует отдельного графического сервиса.
Числовые показатели центрируются. Под сообщением находится закрытый блок
«Что значат показатели». Названия «Клики рекламы», «Посетили посадку», «Перешли в
бот», «Нажали Start» нельзя сокращать до двусмысленного «клики» или CTA без пояснения.
Согласованный этап нельзя молча убрать: при отсутствии сигнала ставится `НД` и
фиксируется, какой сбор данных нужно восстановить.

### Владение и приёмка глубины

- задача «Я.Директ!» владеет всей вертикалью: браузерной телеметрией страницы,
  агрегацией `course_events`, форматом Telegram, ежедневным расписанием,
  документацией и финальной production-приёмкой;
- «Дизайн», VSL и QR-переключатель не получают дублирующих заданий. Их подключают только если
  проверка выявит конкретно отсутствующее событие на принадлежащей им поверхности.

Готовность подтверждается не наличием кода, а сквозной проверкой: тестовый участник
достигает порогов текста и видео, в `course_events` появляются уникальные события,
повторная прокрутка не создаёт дублей, внутренний API собирает их в его Start-когорту,
а тестовый `sendRichMessage` показывает числа в нужных строках. Только после этого
`НД` для новых полных суток считается снятым.

Сохраняется также накопительный итог с `2026-09-08`: первые два дня запуска не
входят только в итог как технические артефакты, но сырые данные не удаляются.
Авторазбор без ИИ отключён: он оказался бесполезным пересказом цифр. Полезная
интерпретация появится только после отдельного подключения ИИ; до этого отчёт
содержит сухие данные, сравнение CPA каналов со вчерашним днём и сохранённые сырые
срезы для последующего анализа.

## Реестр гипотез

Реестр живёт отдельно от ежедневного отчёта. У каждой строки: вопрос, зачем,
нужные разрезы, порог достаточности, статус и действие при каждом результате.

1. Поиск или РСЯ дешевле даёт реальный Start — перераспределить недельный бюджет.
2. Какой креатив РСЯ дешевле даёт Start — оставить победителя, затем тестировать текст.
3. Какая поисковая группа даёт качественный Start — расширять её ядро, слабые запросы минусовать.
4. Где теряются люди click→CTA и CTA→Start — менять посадку либо переход в конкретный мессенджер.
5. Кнопка или QR эффективнее на desktop — решить, оставлять ли показы на ПК.
6. QR из поиска или РСЯ используют чаще — определить ценность desktop отдельно по каналу.
7. После QR чаще выбирают TG или MAX — изменить порядок и визуальный приоритет QR.
8. TG или MAX лучше конвертирует действие в реальный Start — исправлять конкретную ветку.
9. Источник/креатив влияет только на Start или также на день 1/видео/финальную кнопку — оценивать качество, а не только цену лида.
10. Пользовательские блокировки отличаются по источнику — искать несоответствие обещания и welcome.
11. Direct, Метрика и БД сходятся — обнаруживать лаг offline-конверсий или сломанную атрибуцию.
12. Площадки РСЯ дают дешёвые клики без Start — дополнять исключения по новой статистике.
13. Увеличение бюджета ухудшает предельный CPA — масштабировать ступенчато.
14. День недели и время меняют CPA — корректировать расписание только после объёма.
15. Цена глубокого действия (день 1/финальная кнопка) меняет победителя по сравнению с CPA Start — выбирать бизнес-победителя.

Ориентиры достаточности: креатив — около 3 000 показов и 50 кликов для CTR;
CPA Start предварительно после 15 Start, увереннее после 30; глубокая воронка —
20–40 созревших Start. Раннее отключение допустимо после расхода примерно двух
целевых CPA без единого Start. Статусы: `недостаточно`, `предварительно`,
`готово к решению`, `закрыто`. В ежедневный текст попадают максимум три наиболее
актуальные гипотезы.

## Аварийная автоматика

Watchdog проверяет сайт/API и Telegram каждую минуту. После подтверждённой аварии
он перезагружает нужный сервер и через заданную задержку останавливает рекламу.
Перед остановкой `Campaigns.get` фиксирует только кампании со State `ON`;
возобновляются только эти ID после трёх последовательных здоровых проверок.
Кампании, уже остановленные владельцем до аварии, не запускаются. Если владелец
вручную меняет статус уже во время аварии, Direct не сообщает источник изменения;
это ограничение фиксируется в аварийном уведомлении и журнале.

## Будущее подключение ИИ

ИИ сейчас не подключён. Позже сервер вызывает OpenAI Responses API один раз на
сохранённый суточный snapshot. Рекомендуемая модель — `gpt-5.6-terra` с medium
reasoning. Контекст состоит из этого файла, компактного реестра гипотез и последних
сохранённых отчётов; сырые данные не переписываются. Ответ модели сохраняется рядом
с отчётом и отправляется отдельным сообщением после сухих цифр. Требуются
`OPENAI_API_KEY` и `MARKETING_ANALYSIS_MODEL`; пополнение API остаётся ручным.
Модель обязана: сравнить день, предыдущий день, накопительный период и релевантный
исторический benchmark; не путать старые цели с Start; назвать только доказанные
изменения; максимум три гипотезы; завершить конкретным «делать/ждать/проверить».

## Приёмка изменения

После любого изменения: API-read всех трёх уровней Direct, проверка production
health, один тестовый путь TG и MAX, сверка `yclid`/campaign/creative/device/entry,
реального Start и дня 1 в БД, затем dry run отчёта. Запуск/остановка кампании —
только по явной команде владельца, кроме описанного аварийного восстановления уже
работавших кампаний.

При диагностике цели через Direct Reports API всегда указывать ту же модель
атрибуции, что стоит в стратегии кампании. Для текущих кампаний это
`AttributionModels: ["AUTO"]`; без параметра отчёт может показать ложный ноль,
даже когда offline-конверсии уже обработаны Метрикой и доступны стратегии.
