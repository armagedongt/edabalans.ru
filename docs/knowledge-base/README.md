# База знаний проекта

Статус: `current`
Проверено: 25.08.2026
Назначение: человекочитаемый смысл бизнеса, продуктов, модулей и рабочих процессов.

Wiki на `/admin/knowledge-base` читает Markdown и checked-in project map из Git.
Отдельной Wiki-БД и ручного редактора карты нет. Это защищает проект от двух
расходящихся копий одного правила.

## Три вида знания

1. **Карточка модуля** отвечает: зачем модуль нужен, что умеет, где его граница,
   с кем он связан и где лежат полные источники.
2. **Канонический документ** подробно описывает бизнес-правило, продуктовый процесс
   или рабочую инструкцию. Один факт имеет одного владельца; другие места ссылаются.
3. **Технический inventory** автоматически показывает файлы, routes, таблицы,
   migrations и программные символы. Он не пересказывает продуктовый смысл.

Вход в дерево: `modules/catalog/`. Полная иерархия и техника строятся из
`../modules.toml` в `../generated/module-map.md` и
`../generated/module-inventory.json`.

## Как карта остаётся актуальной

Wiki не получает информацию из чата сама по себе. При изменении фактического поведения
Codex обновляет канонический источник, карточку и связи затронутого модуля. Если меняются
реестр, карточка модуля, ownership, связи или технический состав, интегрирующий поток
пересобирает inventory; обычные канонические документы Wiki читает напрямую. После
commit/push/deploy Wiki показывает эту версию. Поэтому не нужно отдельно просить «внести
в базу знаний» после реальной разработки.

Если обсуждение закончилось решением без реализации, нужно явно сказать «зафиксируй
решение». Если идея отложена, нужно явно сказать «положи в планы».

## Памятки и рабочие инструкции

| Задача | Документ |
|---|---|
| Понять термины, поставить задачу, отправить на сервер | `OWNER_PROJECT_GUIDE.md` |
| Проверить клиента и выдать доступ | `ACCESS_MANAGEMENT_GUIDE.md` |
| Изменить цены и тарифы | `PRICING_MANAGEMENT_GUIDE.md` |
| Навести порядок в группах Tilda | `TILDA_GROUP_CLEANUP_GUIDE.md` |

Рабочая инструкция обновляется вместе с фактическим процессом. Будущая идея
находится только в `../plans/`, если владелец явно отложил её на потом.

понятное резюме и ссылку; полный факт остаётся в каноне.

## Карточка модуля

Каждый файл `modules/catalog/<module_id>.md` содержит frontmatter:

```yaml
---
title: Понятное название
summary: Одно короткое объяснение
document_status: current
implementation_status: implemented
---
```

Допустимые статусы закрыты и описаны в `../README.md`. В теле карточки находятся
граница, функции, источники истины и важные связи. Список технических объектов
подставляется из inventory и вручную не дублируется.

## Что ещё может быть draft

Позиционирование, методика, отзывы, маркетинговые каналы и список внешних сервисов
не следует заполнять догадками. Пока нет подтверждённых материалов владельца, такие
документы остаются `draft`; будущая функция — `planned`.

## Безопасность

Не хранить в Git пароли, токены, ключи, приватные выгрузки, телефоны/email клиентов,
дампы или оригиналы непубличных отзывов. Разрешено указать безопасное место доступа
без самого секрета. Юридические правила и места сбора данных описаны в
`LEGAL_DOCUMENTS.md`.
