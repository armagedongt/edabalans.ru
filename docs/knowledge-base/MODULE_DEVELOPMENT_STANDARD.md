# Общий стандарт разработки модулей

Статус: `current`
Владелец: `admin.project-knowledge`
Проверено: 27.08.2026

Этот документ задаёт минимальный общий цикл для любого модуля edabalans.ru.
Специализированные стандарты могут добавлять требования своей области, но не
создают второй реестр модулей, второй источник фактов или параллельный процесс.

## 1. Когда появляется модуль

- **Функция** — отдельное пользовательское или системное поведение внутри уже
  существующей цели.
- **Модуль** — самостоятельная возможность с собственной устойчивой целью,
  границей, входами/результатами и владельцем фактов.
- **Компонент** — файл, экран, route, таблица, job, migration, скрипт или документ,
  которым реализуется функция. Компонент сам по себе модулем не становится.

Сначала расширяется существующий модуль. Новый создаётся только когда новая
возможность не помещается в его границу без смешения разных целей или источников
истины. Техническую классификацию выполняет Codex; Сергей принимает только
продуктовое решение, если возможны две разумные границы.

## 2. Перед изменением

1. Найти `module_id`, карточку, владельцев затронутых файлов и фактов.
2. Проверить существующие функции, компоненты и связи, чтобы не создавать дубль.
3. Определить масштаб:
   - маленькая механическая правка внутри установленного поведения;
   - среднее изменение поведения существующего модуля;
   - новый, разделяемый, объединяемый или существенно меняемый модуль.
4. Для средней задачи собрать все продуктовые вопросы одним пакетом. Для крупной
   сначала зафиксировать требования и границы; полный user-spec нужен только при
   реальной неоднозначности.

## 3. Создание и существенное изменение

Для нового модуля или новой устойчивой границы должны быть определены:

- понятное название и `module_id`;
- родительская область или приложение;
- назначение, функции и то, что остаётся за границей;
- входы, результаты и договоры взаимодействия с соседними модулями;
- единственные владельцы изменяемых фактов;
- основные компоненты, routes, таблицы, события и зависимости;
- наблюдаемое поведение, ошибки и способ проверки;
- карточка в `docs/knowledge-base/modules/catalog/` и запись в
  `docs/modules.toml`.

Не требуется вручную переписывать в карточку функции, классы и полный состав
кода: технический inventory извлекает их автоматически. Карточка объясняет смысл,
границу и каноны человеку.

## 4. Проверка по масштабу

| Изменение | Достаточная проверка |
|---|---|
| Текст, название, ссылка, локальный CSS или другая механическая правка | Diff и одна ближайшая статическая или адресная проверка; отдельный reviewer не обязателен |
| Наблюдаемое поведение существующего модуля | Минимальный test на изменённый контракт и один профильный review |
| Несколько модулей, данные, доступы, платежи, новый внешний договор | Integration-проверка и применимые code/test/security reviews |
| Migration, импорт данных или production-инфраструктура | Специальный безопасный маршрут из `docs/OPERATIONS.md` |

Browser применяется только для реально изменённого интерактивного или
адаптивного поведения, которое нельзя дешевле проверить кодом, API или
детерминированным render. Preview показывается Сергею только по прямой просьбе.

## 5. Завершение

Перед завершением Codex сам проверяет:

1. Поведение находится в правильном модуле, а новые компоненты получили owner.
2. Изменён канонический источник, а не его Wiki/generated-копия.
3. Обновлены только действительно изменившиеся функции, границы, связи и каноны.
4. Пройдена минимальная достаточная проверка без ритуального дублирования.
5. `docs/generated/*` оставлены генератору CI/production; отдельный commit только
   ради их обновления не создаётся.

Отдельно просить «внести в базу знаний» не нужно: долговечное изменение модуля
включает обновление его карточки и канона. Идея попадает в `docs/plans/` только по
явному решению Сергея отложить её.

## 6. Разделение, объединение и удаление

- Сначала выбирается будущий владелец каждого факта и компонента.
- Потребители переводятся на новый канонический договор; старая копия не остаётся
  «на всякий случай» без срока и владельца.
- При удалении убираются routes, ссылки админки, связи, ownership, тесты и
  устаревшие документы одного удаляемого поведения.
- Исторически полезное описание получает статус `archived`; бесполезный дубль
  удаляется после проверки входящих ссылок.
- Два активных чата не выполняют такую перестройку одного источника параллельно.
