# Как Сергей работает с проектом и Codex

Статус: `current`  
Проверено: 25.08.2026  
Назначение: короткая памятка владельцу без необходимости знать программирование.

## С чего начинать

Открой `/admin`. Это «админка админок»: она не заменяет маленькие инструменты,
а даёт ссылки на них, на карту системы, инструкции, планы и технические документы.

В новом чате не нужна специальная стартовая команда: можно сразу писать задачу обычными
словами. Новый чат сначала сам ориентируется в проекте и готовится принять работу.

Он обязан пройти маршрут из `AGENTS.md`: открыть навигатор, найти модуль,
его карточку, источники истины, связи, активную работу и явные планы. Пересказывать
весь проект заново не нужно.

## Как называется устройство проекта

```text
Платформа edabalans.ru
└── область / продукт
    └── модуль
        ├── функции — что умеет модуль для человека или системы
        └── компоненты — чем функция реализована
            ├── экран или админка
            ├── API route
            ├── таблица
            ├── job / событие
            ├── файл / скрипт / migration
            └── программные символы
```

- **Модуль** — самостоятельная возможность с понятной целью, входами и результатом.
- **Функция** — одно поведение внутри модуля: например, «опубликовать структуру курса».
- **Компонент** — техническая деталь реализации. Отдельный файл не становится модулем
  только потому, что он существует.
- **Программный символ** — функция, method или class в коде. В обычной постановке
  задачи Сергею этот термин почти не нужен.
- Ниже функции находятся правило, действие, поле и состояние. Они не требуют новых
  модулей сами по себе.

У каждого файла, route, таблицы и извлекаемого программного символа есть один
модуль-владелец. Другие модули могут пользоваться им через явную связь. Полный
технический список строится автоматически — вручную поддерживать сотни строк не нужно.

## Как формулировать задачу

Подойдут обычные фразы:

- «В модуле дополнительных продаж добавь функцию повторной проверки цены».
- «Измени текст в Telegram-модуле после покупки».
- «Сделай маленький инструмент для просмотра структуры курса».
- «Положи в планы для модуля DQS идею …».
- «Сначала исследуй и задай все важные вопросы, потом сделай и отправь на сервер».
- «Перед отправкой на сервер покажи preview».

Если Сергей не знает, модуль это или функция, чат обязан определить границу сам и
простыми словами объяснить её только тогда, когда выбор влияет на решение.

Это не нужно отдельно напоминать в каждой задаче. Перед завершением работы Codex сам
проверяет: появилась ли функция, изменился ли модуль, нужна ли новая связь или обновление
карточки. Если есть две разумные границы либо задача затрагивает несколько модулей, он
предложит понятный вариант и спросит только решение, которое может принять Сергей.

## Как выбирается глубина работы

| Задача | Что делает Codex |
|---|---|
| Маленькая и ясная | Смотрит затронутый код, сразу делает, запускает минимальную проверку |
| Средняя | Исследует проект и одним пакетом задаёт только вопросы, меняющие результат |
| Большая или неоднозначная | Проводит research, фиксирует поведение/ТЗ, затем реализует и ревьюит |

Preview не является обязательным этапом. Codex показывает его только по прямой просьбе.
Browser-проверка нужна для изменённого интерфейса или реального междоменного пути; обычную
серверную логику быстрее и надёжнее проверять автоматическими tests.

## Как выбирать модель

Модель выбирается по риску конкретной задачи, а не закрепляется за модулем навсегда.

| Пример | Рекомендация |
|---|---|
| Тексты, названия, точечный CSS, механическая правка карточки | `GPT-5.6 Luna` (`low` или `medium`) |
| Редактор структуры курса, отдельный экран админки, адаптация HTML-референса под сайт | `GPT-5.6 Terra medium` |
| Платежи, доступы, migration, production, новый Telegram-сценарий, правила допродаж с таймерами и связями | `GPT-5.6 Sol high` |

Например, у модуля дополнительных продаж правила и связи с Telegram лучше проектировать
на `Sol`, а поправить внешний вид симулятора — на `Terra`. Для редактора курса изменение
хранимой структуры или migration требует `Sol`, обычная работа с экраном — `Terra`.

## Рабочие слова

| Слово | Простой смысл |
|---|---|
| `local` | Изменения есть только в рабочей копии; реальные пользователи их не видят |
| `preview` | Специально показанный предварительный результат |
| `tests` | Автоматические проверки ожидаемого поведения |
| `commit` | Контрольная точка изменения в Git; это ещё не публикация |
| «отправь на сервер» | Выполнить нужные commit, push и deploy до production |
| `production` | Версия, которой пользуются реальные люди |
| `migration` | Отдельное изменение структуры или обязательных данных PostgreSQL |
| `rollback` | Вернуться к предыдущей рабочей версии |

`push` — техническая отправка commit в GitHub. Сергею обычно не нужно заказывать её
отдельно: команда «отправь на сервер» покрывает весь штатный маршрут. Push в `main`
запускает CI; сервер принимает только успешно проверенную версию. Migration не выпускается
автоматически и требует отдельного безопасного шага.

## Когда Codex останавливается

Если не было просьбы показать preview или остановиться перед сервером, Codex может
продолжать автономно. Он обязан снова спросить, если:

- изменилась цель или последствия;
- нужен новый внешний сервис или расход;
- операция удаляет данные или трудно отменяется;
- найдено неожиданное production-состояние;
- нет доступа или среда требует подтверждения;
- два активных чата собираются изменить один источник истины.

## Как работают планы

Фраза «когда-нибудь было бы здорово» сама по себе ещё не план. Запись появляется только
после ясного решения «положи в планы» или «это делаем потом».

Планы находятся в `docs/plans/` и группируются по `module_id`. Можно спросить:
«Что у нас в планах?» — чат перечислит их по модулям. Черновик текущей работы, забытый
deploy или незаконченная ветка планом не становятся.

## Где живёт знание

- Карта модулей и связи — `docs/modules.toml`.
- Понятное описание каждого модуля — его единственная карточка в
  `docs/knowledge-base/modules/catalog/`.
- Полные продуктовые правила — канонические документы, на которые ссылается карточка.
- Текущая реализация — код, config, migrations и runtime PostgreSQL.
- Явное будущее — `docs/plans/`.
- Временная работа — `work/`.
- Wiki — только удобный экран чтения этих источников, не отдельная база.

Карта и технический инвентарь обновляются через код и Git. Ручного редактора карты нет,
поэтому она не может разойтись с отдельной «версией в админке».

Практически это работает так: Codex меняет канонический код, документ или реестр модуля и
в той же работе обновляет карточку и связи. Если изменился реестр, карточка модуля, ownership,
связи или технический состав, интегрирующий поток пересобирает техническую карту. Обычные
канонические документы Wiki читает напрямую. После commit/push/deploy Wiki показывает новую
версию. Она ничего не «запоминает» сама и не забирает случайные сообщения из чата — иначе
возник бы второй источник истины.

Поэтому при реальной разработке отдельно просить «внести в базу знаний» не нужно. Отдельно
сказать стоит лишь о решении без реализации («зафиксируй решение») или явно отложенной идее
(«положи в планы»).

## Несколько чатов

Практичный режим: не больше двух независимых потоков реализации плюс один чат для
обсуждения/исследования. Перед параллельной работой каждый поток фиксирует module id,
файлы, источник истины и точку передачи. Если оба хотят менять один contract, таблицу,
порядок дней или документ, один ждёт готовый checkpoint другого.

Обсуждение можно передать другому чату, но сам разговор не является источником истины:
сначала результат фиксируется в spec/checkpoint в Git, затем свободный чат получает
точный путь и задачу.
