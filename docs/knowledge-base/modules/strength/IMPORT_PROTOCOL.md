# Протокол подготовки и импорта истории силовых тренировок

Статус: `current`  
Модуль: `products.strength`  
Назначение: повторяемо переносить историю из Google Sheets, Excel, CSV и вручную
собранных таблиц в серверный профиль, не придумывая тренировочные факты.

## Что является результатом

Перед записью всегда собирается отдельный staging-файл с шестью вкладками:

| Вкладка | Содержимое |
|---|---|
| `Sessions` | одна строка на тренировку: шаблон, номер, дата, происхождение |
| `Session_Exercises` | упражнения и комментарии внутри тренировки |
| `Sets` | plan/fact/RPE по каждому подходу, включая исходные текстовые значения |
| `Exercise_Mapping` | решение по каждому названию упражнения |
| `Review_Queue` | всё неоднозначное, решение и источник решения |
| `Meta` | источники, приоритет, правила дат и целевой профиль |

Это не новая база и не пользовательский экран. Staging — проверяемый промежуточный
слой: он отделяет разбор чужого формата от записи в приложение.

В приложении у человека есть единый серверный профиль, общий каталог упражнений,
три шаблона тренировок и их история. Базовые упражнения принадлежат приложению;
неизвестные или личные названия принадлежат конкретному профилю. Историческая
тренировка хранит собственный снимок названия и набор подходов, поэтому смена
будущего каталога не стирает прошлые записи.

## Правила разбора

1. Сначала определить структуру источника, а не колонки по буквам: где начинаются
   блоки тренировок, разделители шаблонов, упражнения, подходы, plan, fact и RPE.
   Один и тот же протокол работает для горизонтальной матрицы, вертикального списка
   и разрозненных таблиц.
2. У каждой строки сохранить происхождение: файл/вкладка/ячейка или строка, а также
   приоритет источника. Если актуальный и архивный источник содержат один день и
   один шаблон, загружается актуальный; архивный дубль остаётся в `Review_Queue`.
3. Преобразовывать в число только однозначные числа. Текст вроде `4 RIR`, `20/17`,
   `след. вес`, диапазона, названия тренажёра или свободного комментария остаётся
   буквальным в поле `*_raw`. Запрещено вычислять из него вес, повторы или RPE.
4. Комментарий к упражнению переносится в `note`. Например, фраза о боли — это
   комментарий, а не диагноз и не повод менять факт выполнения.
5. Неизвестное упражнение не подменяется похожим базовым. Ему даётся устойчивый
   профильный идентификатор и сохраняется исходное название. Если владелец позднее
   подтвердит соответствие базовому упражнению, это отдельная явная правка.

## Неполные данные и вопросы владельцу

Не нужно останавливать перенос из-за отсутствующего значения. Нужно сохранить
границу знания и задать только вопрос, который меняет данные.

| Ситуация | Как заносим сейчас | Что уточняем, если это важно |
|---|---|---|
| Нет даты блока | По заранее разрешённому правилу ставим предыдущую или среднюю между соседними датами; в `legacy_group` и `Review_Queue` ставим `owner-authorized estimate`. | Нужна ли точная дата или допустима приблизительная. Без такого разрешения дату не выдумываем. |
| Дата есть не у всех блоков | Заполненные даты оставляем источником; только пустые получают отдельную пометку происхождения. | Ничего, если действует правило приблизительных дат. |
| Нет RPE | Оставляем пустым. Нельзя выводить RPE из веса, повторов или словесной оценки. | Только если владелец хочет восстановить RPE из другого достоверного источника. |
| Есть только факт | Записываем факт; план остаётся пустым. | Ничего. |
| Есть только план | Записываем план; факт и RPE остаются пустыми. | Ничего. |
| Есть только текст в ячейке | Сохраняем текст в соответствующем `*_raw`; числовое поле пустое. | Что означает текст — лишь если это понадобится для будущего каталога или аналитики. |
| Непонятно упражнение | Сохраняем исходное название как личное/историческое, без медицинской или тренировочной интерпретации. | «Это какое упражнение и совпадает ли оно с одним из упражнений каталога?» |
| Меняется упражнение в одной позиции таблицы | С точной точки смены начинается отдельная история упражнения; обычные пояснения не меняют упражнение. | Только если заголовок двусмысленен. |

`status` не должен притворяться подтверждением тренировки. В текущем приложении
он выводится как `filled`, когда в данных есть RPE; отсутствие RPE не удаляет
записанный факт и не оправдывает его выдумывание.

## Безопасная запись в сервер

1. Найти целевой серверный `user_id`, проверить доступ к силовым и текущий объём
   истории. Не выбирать профиль только по похожему имени.
2. Сверить staging: число тренировок, упражнений и подходов; уникальность
   `session_id`; отсутствие пустых дат, если они не помечены как разрешённая
   оценка; отсутствие неразобранных пунктов в `Review_Queue`.
3. До записи выполнить свежий backup PostgreSQL и test restore.
4. Запустить dry-run в production-контейнере. Он обязан проверять, что цель не
   изменилась с момента сверки, и не имеет права менять общий каталог упражнений
   или данные другого человека.
5. Записывать профиль под блокировкой состояния и только после успешного dry-run.
   Повторный запуск должен останавливаться при уже непустой истории, а не создавать
   дубли.
6. Сразу перечитать сервер: те же количества, диапазон дат, наличие контрольных
   текстовых значений и комментариев. Только после этого сообщать о завершении.

Исходные файлы, выгрузки и staging с персональными данными не коммитятся в Git и
не публикуются. В репозиторий попадают только код и этот протокол без персональных
данных.

## Постоянная анкета для следующего файла

Когда владелец присылает новую историю, сначала достаточно собрать одним пакетом:

1. Чей это уже существующий профиль и какой источник считать актуальным при
   противоречии.
2. Можно ли приблизительно поставить отсутствующие даты; если да — каким правилом.
3. Какие названия упражнений точно соответствуют каталогу, а какие оставить как
   пользовательские/исторические.
4. Есть ли отдельный источник RPE, plan или fact, если они отсутствуют в файле.

Если ответов нет, перенос всё равно можно подготовить: неизвестное остаётся
буквальным, а вопросы попадают в `Review_Queue`. Запись в production выполняется
только после того, как для всех влияющих на данные пунктов есть решение владельца
или явно разрешённое правило.
