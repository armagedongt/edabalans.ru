# SEO: редакционные решения и история вариантов

Решения владельца от 04.10.2026. Этот документ задаёт согласование metadata,
не объявляет технические доработки реализованными. Голос принадлежит Писарю;
действующие форматы API — в [BLOG_API_AUTHORING](../../BLOG_API_AUTHORING.md).

## Название, поисковый заголовок и описание

Видимый авторский заголовок и SEO title — отдельные поля одной публикации.
Смена поискового варианта не меняет H1, slug, семью или тело. Markdown поддерживает
description и seo_title по [действующему API-контракту](../../BLOG_API_AUTHORING.md).
Если seo_title отсутствует, используется исходный title. Поисковое поле влияет
на HTML title; заголовки карточек, Open Graph и Article сохраняют авторское название.

Без согласованного description используются первые два предложения текущего
публичного Markdown. Предложение нового анонса не является разрешением замены.
Metadata доступны владельцу для ручного выбора; не создаётся второй редактор.

Практический ориентир для title — 45–65 символов с пробелами, для description —
120–170. Это не запрет более длинного текста и не лимит поисковой системы:
обрезание зависит от ширины, устройства и выдачи. Самое важное ставить в начале.
Кратко назвать тему и оставить интерес; не пересказывать весь вывод и не
забивать поле ключами. Не обещать отсутствующее содержание, результат или
калькулятор. Ручной расчёт — не интерактивный калькулятор.

Поисковики могут заменить title и snippet. Частота Wordstat не равна показам
нашего сайта, трафику или кликам. Запрос выбирается по полному смыслу статьи,
а не только по максимальному числу. Фиксировать дату, географию, вид частоты и
ограничения выборки. При недоступном API не придумывать цифры.

## Архив и ручная карта

Перед изменениями сохраняется неизменяемый снимок фактических public title,
H1, description и canonical с source_id, URL, временем и хешем HTML. Активный
admin draft и Git fallback не выдаются за опубликованную версию.

Рабочая карта — одна Markdown-страница со всеми публичными identity. Каждая
содержит текущие поля, релевантные запросы, два предложенных title и description,
основание и отдельные пустые «Мой заголовок» / «Мой description». Карта не является
publication source: заполнение поля ничего не выпускает. Повторная генерация
не перезаписывает ручные правки; новые предложения вносятся точечно.

До выпуска фиксировать выбранный вариант, предыдущие значения, дату решения,
дату фактического применения и publication version. Не объявлять вариант
победителем или смену полноценным A/B-тестом без сравнимых данных; поисковые
отчёты анализируются отдельно. Пустое поле не означает согласование.

## Авторство, даты и навигация

Автор один: Сергей Воронцов, тренер по питанию. Основная фраза — «Пишу о питании
и похудении так, чтобы вы менялись.» Дополнительные факты о квалификации/опыте
берутся у владельца; не выводятся из темы статьи. Ссылка возле H1 должна вести
на постоянную страницу автора; диалог допустим как улучшение открытия этой же
ссылки, а не как единственный недоступный без JavaScript профиль. Публичный текст
профиля сначала согласовывается. Дополнительная большая концевая плашка не нужна.

Исходная публикация, появление в блоге и обновление — разные даты. Первую
проверять в канале/на Пикабу; неизвестную не вычислять как «минус день».
04.10.2026 допустимо как дата реально сделанного обновления, не как массовая
дата для всех старых страниц. Указание дат в Article должно соответствовать
событиям, показанным читателю. Одна смена черновика не обновляет public.

Breadcrumbs: блог → существующая рубрика → статья, первые два пункта кликабельны.
Серверный каталог сохраняет 15 карточек на страницу; прямые ссылки и собственные
canonical страниц обеспечиваются техническим этапом, не маскировкой JS-пагинации.
Реализация каталога отдаёт только выбранные карточки. Рубрики и номера страниц —
обычные query-ссылки; первая страница не добавляет `page=1`, выбор рубрики сохраняется
при переходе. Некорректный номер/неизвестная рубрика сохраняют прежний fallback,
слишком большой номер ограничивается последним; canonical нормализует выбор.
Внутренняя рекомендация — максимум одна по
[редакционному workflow](../../BLOG_EDITORIAL_WORKFLOW.md#смысловая-рекомендация-внутри-статьи).

## Проверка и этапы

До предложений по действующим статьям и новых тем провести исследование спроса:
подтвердить существующий Wordstat-доступ реальным ответом, измерить основной
запрос и его уточнение на одной географии, проверить задачу читателя по
содержательным результатам поиска. Частоты разных операторов и движков не смешивать;
ошибку API не выдавать за ноль. Не переносить чужие эвристики трафика как прогноз.

Новую тему сверять не только с опубликованным блогом, но и с семейным реестром
Библиотекаря и последними решениями владельца. «Нет отдельной публичной статьи»,
«другой угол», «расширение существующей» и «есть отложенный/учебный источник» —
разные результаты. SEO не снимает банк, ручной разбор и границы закрытых материалов.
Если покрытие источников неполное, не утверждать отсутствие темы во всём архиве.

К рекомендациям приложить измерения и читательское основание; к новой статье —
также отличие от ближайшей семьи, источник авторской основы, приоритет и риски.
Writer pass проверяет редакционную пригодность, а не доказывает поисковый спрос
или лёгкость продвижения. Нельзя называть тему перспективной только из-за
широкой частоты и не учитывать соответствие полного текста обещанию сниппета.

Исследование → снимок → Wordstat → полнотекстовые пачки Писаря → review/pass →
ручной выбор → технически поддержанная публикация → проверка public. SEO не
даёт права исправлять идеи, медицинские утверждения и авторскую интонацию.

Метрика и её события (прокрутка, дочитывание как условный показатель, клики,
показы/закрытия popup, переходы в ботов и атрибуция) перенесены владельцем на
последний этап вместе с Search Console/Вебмастером. До этого этапа выполнять
функциональную подготовку интерфейса, но не подключать новые счётчики, цели и
отправку событий. Показ popup не доказывает подписку, прокрутка не доказывает чтение.

Search Console/Вебмастер отложены владельцем; адаптивные изображения — следующий
этап после измерения веса, размеров и скорости. Не менять working домены,
рекламные кампании, общий cookie/footer и текущий контур входа попутно.

Первичные правила: [Google title](https://developers.google.com/search/docs/appearance/title-link),
[Google snippets](https://developers.google.com/search/docs/appearance/snippet).
