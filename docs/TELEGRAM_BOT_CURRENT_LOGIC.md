# Фактическая логика Telegram-бота

Статус: `current`
Назначение документа: каноническое описание текущей реализации.
Дата фиксации: 25.08.2026
Проверенная версия: текстовое представление модулей и исполняемый граф по состоянию
на 25.08.2026; основной бот и канал проверены через Telegram Bot API.
Статус выпуска: основной `@Fitness_Talks_bot` подключён к нашему long polling в
режиме ремонта; полная логика разрешена только двум аккаунтам владельца,
post-purchase дополнительно ограничен выбранными тестовыми профилями.
Проверены HTTPS API и `go.похудение-это-есть.рф`, защищённый admin API, три legacy
alias, закрытый порт PostgreSQL, Telegram `getMe` через proxy и восстановление
последнего backup в изолированные базы. Tilda не переключалась; основной Telegram-
бот защищён maintenance allowlist до ручного приёмочного теста.

Этот файл описывает **как Telegram-бот работает сейчас по факту**. Он не описывает
интерфейс админки и не является описанием желаемой будущей логики.

Канонические требования ко всему глобальному модулю «Старт и атрибуция» находятся
в `knowledge-base/modules/telegram/START_WELCOME_ROUTING.md`; технические детали
его ссылочного подмеханизма — в `LEAD_ENTRY_OWNER_REQUIREMENTS.md` и
`LEAD_ENTRY_TECHNICAL_SPEC.md`. Граница следующего модуля зафиксирована в
`knowledge-base/modules/telegram/WELCOME_INTENSIVE.md`. Каноническая схема может
описывать утверждённое целевое поведение, а этот файл всегда отдельно отмечает,
какая его часть уже исполняется production-кодом.

## 1. Где находится источник истины

- Приём входящих событий и `/start`: `telegram-bot/service/app/main.py`, функции
  `polling_loop()`, `process_update()` и `_upsert_contact()`.
- Исполняемое решение стартовой ветки: `telegram-bot/service/app/start_router.py`;
  порядок правил зарегистрирован как `START_ROUTER_RULES` в `app/graph.py`. Раздел
  «Модули» автоматически превращает те же узлы и связи в текстовую
  последовательность; отдельной рисованной копии логики нет.
- Исполнение шагов цепочки: `telegram-bot/service/app/engine.py`, функции
  `start_run()`, `advance_run()`, `resume_callback()` и `due_runs()`.
- Начальный шаблон двух цепочек: `telegram-bot/service/app/seed.py`.
- Фактическая опубликованная структура после инициализации хранится в PostgreSQL,
  в таблицах `tg_sequences`, `tg_sequence_versions`, `tg_sequence_steps` и
  `tg_sequence_edges`. Поэтому работающий бот исполняет данные БД, а не повторно
  читает шаблон `seed.py` при каждом сообщении.
- Тексты и медиа хранятся в `tg_content_items`; отправляет их Telegram-клиент из
  `telegram-bot/service/app/telegram.py`.
- Описание таблиц Telegram-модуля находится в
  `telegram-bot/service/app/models.py`, схема создаётся миграциями из
  `backend/migrations/versions/`.

## 2. Как бот получает события Telegram

Сейчас используется long polling, а не webhook:

```text
Telegram Bot API
  -> getUpdates через исходящий proxy
  -> polling_loop()
  -> process_update()
```

- `polling_loop()` находится в `telegram-bot/service/app/main.py`.
- HTTP-запросы `deleteWebhook` и `getUpdates` выполняет
  `TelegramClient` из `telegram-bot/service/app/telegram.py`.
- `allowed_updates` включает `message`, `callback_query`, `chat_member` и
  `chat_join_request`.
- Адрес proxy берётся из настройки `telegram_proxy_url`, описанной в
  `telegram-bot/service/app/config.py`.
- Полученный `update_id` записывается в `tg_update_receipts`. Повторный update с
  тем же ID не исполняется второй раз.
- При сетевой ошибке polling ждёт две секунды и повторяет запрос, не подтверждая
  необработанный update.

## 3. Как создаётся ссылка и определяется источник

Одна запись `tg_tracking_links` теперь является правилом: она хранит название,
тип назначения `bot_start/channel_invite`, корневой маршрут либо разрешённое
исключение, состояние и старые совместимые поля `platform/placement/campaign`.

Публичные адреса правила находятся отдельно в `tg_tracking_link_aliases`. Поэтому
новый код и несколько старых LeadTeh UUID могут означать один и тот же источник,
а статистика показывается и суммарно по правилу, и отдельно по каждому адресу.
Код не удаляется и не используется повторно; его можно архивировать или отключить.

Новые короткие коды имеют вид `B` или `C` плюс четыре символа. `B` означает ссылку
на бот, `C` — invite-ссылку канала. Пятый после кода символ `V` распознаётся только
на домене `go.` и выводит предупреждение о VPN. В прямом Telegram payload `V` не
имеет специального значения.

Для bot rule админка выдаёт:

```text
https://t.me/TetrisgfgfgfBot?start=B7K4P
https://go.похудение-это-есть.рф/B7K4P
https://go.похудение-это-есть.рф/B7K4PV
```

Маршруты `GET /go/{token}` и совместимый `GET /r/{token}` реализованы в
`telegram-bot/service/app/main.py`. Они разрешают alias, сохраняют `web_click` в
`tg_tracking_events` и переводят только на настроенный Telegram bot/invite URL.
Произвольный внешний redirect из query не допускается.

Если к `go.` пришли UTM, они сохраняются без догадок. Точные ручные правила
`parameter + normalized value -> existing tag_id` лежат в `tg_utm_tag_rules`.
Для передачи UTM через Telegram создаётся краткоживущая одноразовая запись
`tg_tracking_sessions`; наружу уходит непрозрачный start payload. Неразобранные UTM
вычисляются из сырых событий и не получают отдельную дублирующую таблицу.

Связь правила с существующими CRM-тегами хранится в `tg_tracking_link_tags`.
Новый тег не создаётся при переходе. Администратор отдельно выбирает существующий
тег либо явно подтверждает создание нового. При merged tag функция
`canonical_tag()` из `telegram-bot/service/app/tracking.py` следует к актуальному
`tags.id`.

В админке правило получает теги через одно поле поиска: по мере ввода показываются
совпадения из общего каталога CRM, выбранные теги добавляются под полем и могут быть
сняты до сохранения. Если точного тега нет, только тогда появляется отдельное
явное действие создания нового тега с подтверждением.

При `/start` функции `resolve_start_payload()` и `assign_first_touch()`:

1. классифицируют payload как известный, неизвестный, пустой либо истёкшую session;
2. неизвестный код безопасно направляют в обычный корневой `/start`;
3. записывают `start_first`, `start_repeat`, `start_unknown` либо
   `start_expired_session` в `tg_tracking_events`;
4. атомарным признаком первого полноценного посещения используют
   `messenger_accounts.main_scenario_seen_at`;
5. только при первом посещении назначают выбранные существующие `user_tags` и
   создают CRM `attribution_events`;
6. повторный `/start` источник и теги не перезаписывает и welcome не перезапускает;
7. `tg_contacts.last_source_token` новой логикой больше не обновляется.

Для канала Telegram client принимает `chat_member` и `chat_join_request`. Событие
с известной уникальной invite-ссылкой сохраняется до будущего `/start` того же
Telegram user ID; первый старт забирает это событие и применяет теги правила.
Создание/revoke invite и чтение подписки реализованы и проверены на основном боте,
который является администратором канала.

Три предоставленных legacy UUID добавляются миграцией `0012`: главная ссылка
Пикабу получает существующий тег `Пикабу`; две ссылки конкретных постов получают
теги `Пост - Не с похудения` и `Пост - Скорость похудения`, если такие теги уже
есть. Источник двух последних не угадывается. Остальные UUID без mapping работают
как обычный корневой старт.

## 4. Как определяется пользователь

Функция `_upsert_contact()` в `telegram-bot/service/app/main.py` получает от
Telegram `user` и `chat` и создаёт либо обновляет `tg_contacts`:

- Telegram user ID;
- chat ID;
- username;
- имя и фамилию;
- язык;
- время последней активности;
- статус `active`.

Затем она ищет `messenger_accounts` с `platform='telegram'` и тем же
`platform_user_id`:

- если запись найдена, её общий `user_id` сохраняется в `tg_contacts.user_id`;
- если записи нет, создаются новый `users` и связанный `messenger_accounts`, а
  новый `user_id` сохраняется в `tg_contacts.user_id`.

Канонические CRM-модели описаны в `backend/app/models.py`; минимальные ORM mapping,
которыми Telegram service безопасно обращается к тем же таблицам, находятся в
`telegram-bot/service/app/models.py`. Создание/обновление выполняет
`ensure_crm_identity()` из `telegram-bot/service/app/tracking.py`.

Текущее ограничение: оплата из Tilda ищет человека преимущественно по email в
`backend/app/tilda_service.py`, а Telegram создаёт человека по Telegram ID.
Автоматическое безопасное объединение этих двух записей ещё не завершено. Если
они оказались разными `users.id`, бот может не увидеть покупку этого человека.

## 5. Первый `/start` и повторный `/start`

До пользовательских ответов и запуска Start-router действует временный production-
предохранитель. Контакт, payload/M-link, first-touch и факт покупки мастер-класса
определяются до него. При `TELEGRAM_MAINTENANCE_MODE=true` только ID из
`TELEGRAM_MAINTENANCE_ALLOWED_USER_IDS` проходят дальше. Остальные получают
`tpl_maintenance_notice`, статус `maintenance_waitlist` и события
`start_maintenance`/`maintenance_contact`; их источник и связь с покупателем не
теряются, но `main_scenario_seen_at` не выставляется и sequence не запускается.

Тот же предохранитель блокирует их callback-кнопки, due-run, post-purchase,
разовые и ручные сообщения. Благодаря этому чистовой username можно подключить до
наполнения всех авторских текстов без случайной рассылки клиентам.

Маршрут первого запуска хранится в `tg_bot_routes`. Начальное значение создаёт
`_ensure_routes()` в `telegram-bot/service/app/seed.py`:

```text
/start -> start_router -> welcome_intensive (только для новой Welcome-ветки)
```

После тихой атрибуции и maintenance gate `start_router.py` использует уже
вычисленный факт покупки и строго по порядку проверяет:

1. подтверждённую покупку одного из трёх тарифов мастер-класса либо активное право
   `ACCESS_MASTERCLASS`;
2. первое ли это посещение;
3. доставлен ли четвёртый обязательный материал (`welcome_day4`);
4. существует ли active/waiting run `welcome_intensive`;
5. запускалась ли новая версия Welcome когда-либо.

Результат ровно один:

- покупка → остановить Welcome/pre-purchase run и отправить
  `tpl_start_has_masterclass`;
- первый вход или новая рассылка ещё не запускалась → запустить
  `welcome_intensive`;
- День 4 доставлен → отправить оглавление завершённого интенсива
  `tpl_start_intensive_complete`;
- Welcome run активен → отправить `tpl_start_intensive_waiting` с фактическим
  `next_action_at`, не меняя шаг и расписание;
- Welcome раньше запускался, но run потерян и День 4 не доставлен → записать
  `start_routing_error` в `tg_tracking_events`, ничего человеку не отправлять.

Системные ответы читаются из `tg_content_items`, а отправки записываются в
`tg_manual_messages` с оператором `system:start_router`. Старый LeadTeh-тег первого
посещения не считается запуском новой Welcome-версии.

В админке **Пользователи → Что ответит Start** показывает решение по текущему
состоянию без отправки и без изменения данных. API предпросмотра:
`GET /bot-api/contacts/{contact_id}/start-preview`; чистая симуляция фактов:
`POST /bot-api/start-router/simulate`.

Отдельный вход покупателя по одноразовой M-ссылке развёрнут на основном боте.
Он связывает Telegram-аккаунт с уже существующим CRM user и запускает центральную
обработку покупки.

## 6. Три отдельные цепочки до покупки

Структура из трёх модулей развёрнута на основном боте и является текущей
исполняемой структурой.

### 6.1. Start и атрибуция

`start_router.py` исполняет проверки и выбирает один конечный ответ. Отдельной
контентной Start-sequence нет. Для нового человека зелёный выход запускает
`welcome_intensive`; все сообщения первого входа находятся уже там.

Полная последовательность условий первого/повторного Start показана в разделе
админки «Модули». Она автоматически строится из исполняемого графа; утверждённый
продуктовый смысл описан в
`knowledge-base/modules/telegram/START_WELCOME_ROUTING.md`.

### 6.1.1. Что разрешено менять в админке

Админка не является конструктором архитектуры. В ней можно редактировать текст,
форматирование, ссылки, подписи кнопок и медиа сообщений, а также использовать
отдельные рабочие инструменты пользователей, библиотеки, рассылок и ссылок.
Условия, порядок, задержки и переходы между модулями доступны только для чтения.
Раздел «Модули» получает `nodes` и `edges` из `GET /bot-api/map` и строит из них
входы, последовательность, ветки и выходы при открытии страницы.

### 6.2. Welcome — запуск и первые четыре дня

Sequence `welcome_intensive` выполняет:

```text
общая навигация + закреп → кружок → «Сделайте похудение проще» + кнопка → WAIT_BUTTON
→ условие подписки
  ├─ да: сразу День 1
  └─ нет: просьба + повторная кнопка
          ├─ подписался: сразу День 1
          ├─ ещё нет: вернуться к просьбе, не сдвигая срок
          └─ прошло 5 минут: сразу День 1 без блокировки
→ 11 ч → полезный пост 1
→ 12 ч → День 2 → 12 ч → полезный пост 2
→ 12 ч → День 3 → 12 ч → полезный пост 3
→ 12 ч → День 4 → 12 ч
→ GOTO prepurchase_nurture
```

После каждого из семи содержательных постов тихо фиксируется состояние подписки.
Проверок покупки внутри Welcome нет.

### 6.3. Основная рассылка

Sequence `prepurchase_nurture` получает управление через 12 часов после Дня 4 и
начинается с продающего поста без дополнительной задержки, затем содержит
отдельный каркас полезных и продающих сообщений. Проверок `has_product` перед
постами нет: единое lifecycle-правило завершает активные presale-run сразу после
M-link либо обнаружения `ACCESS_MASTERCLASS`.
Она не смешана со Start и Welcome.

Старая объединённая sequence `prepurchase_masterclass` сохраняется как архивная
для совместимости данных, но скрыта из рабочего списка и не является маршрутом
нового `/start`.

Во всех трёх модулях тексты хранятся в `tg_content_items`, шаги — в
`tg_sequence_steps`, переходы — в `tg_sequence_edges`, состояние пользователя —
в `tg_sequence_runs`. Переходы между модулями исполняет `GOTO` в `engine.py`.

## 7. Нажатие кнопки «Начать интенсив»

Шаг `WAIT_BUTTON` переводит `tg_sequence_runs.status` в `waiting` и записывает
ожидаемый `callback_data` в `tg_sequence_runs.context`.

Нажатие кнопки приходит как `callback_query`. `process_update()` передаёт его в
`resume_callback()` из `telegram-bot/service/app/engine.py`. Если callback
совпадает, run снова становится `active`, переходит по следующей связи из
`tg_sequence_edges`, и `advance_run()` продолжает цепочку.

## 8. Проверка подписки на канал

В Welcome существуют начальная, повторная и семь тихих проверок:

```text
condition = subscription_check
enabled = true
stage = before_day1 / after_prompt / after_...
```

Основной `@Fitness_Talks_bot` является администратором канала `@Fitness_Talks`.
Числовой channel ID хранится только в production-конфигурации. Проверка вызывает
Telegram `getChatMember`: `creator`, `administrator`, `member` и активный
`restricted` считаются подпиской; `left` и `kicked` — отсутствием подписки.
Временная ошибка Telegram даёт `subscribed=null` и пропускает человека дальше,
чтобы недоступность API не закрыла интенсив. Тайм-аут WAIT_BUTTON хранится в
`tg_sequence_runs.next_action_at`; scheduler продолжает ветку через явную edge
`timeout`.

Каждый результат хранится в `tg_tracking_events`; известный реальный статус также
обновляет `messenger_accounts.subscription_status`, `subscription_checked_at` и
ровно один существующий канонический тег `Подписан`, `Не подписан` или
`Отписался`.

## 9. Центральная реакция на покупку

Перед каждым рекламным постом больше нет конструкторской ветки `has_product`.
Покупка мастер-класса создаёт доменное событие `masterclass_purchase_confirmed`.
Единый lifecycle-обработчик:

- признаёт общий CRM-доступ `ACCESS_MASTERCLASS`;
- останавливает активные и ожидающие run до покупки;
- после привязки Telegram по M-ссылке помещает в outbox идентификационное сообщение
  и анкету;
- использует сверку по `ACCESS_MASTERCLASS` как страховку для пропущенного события.

Сообщения после покупки отправляются отдельными доменными событиями, а не полным
последовательным run. На основном production-боте этот dispatch пока разрешён только
для выбранных тестовых профилей. Полный контракт — в
`knowledge-base/modules/telegram/CUSTOMER_LIFECYCLE_TECHNICAL_SPEC.md`.

## 10. Как исполняются задержки и шаги

`scheduler_loop()` в `telegram-bot/service/app/main.py` регулярно вызывает
`due_runs()` и `advance_run()` из `engine.py`.

- Текущее состояние человека: `tg_sequence_runs` (`current_step_key`, `status`,
  `next_action_at`, `context`, `time_scale`, ошибка).
- `DELAY` берёт `tg_sequence_steps.delay_seconds`, умножает на
  `tg_sequence_runs.time_scale` и записывает результат в `next_action_at`.
- Обычный режим использует `time_scale=1`.
- Ускоренный тест обычно использует `time_scale=1/720`: 24 часа превращаются
  примерно в 2 минуты, 12 часов — примерно в 1 минуту.
- Тихих часов и часового пояса пользователя сейчас нет: все задержки считаются
  буквально от предыдущего шага.
- `DB_READ` читает условие/переменную; `DB_WRITE` записывает значение в
  `tg_user_variables`; логика находится в `_variable()`, `_write_variable()` и
  `advance_run()` файла `engine.py`.

Движок понимает типы `MESSAGE`, `PHOTO`, `VIDEO`, `VIDEO_NOTE`, `VOICE`, `DELAY`,
`WAIT_BUTTON`, `CONDITION`, `DB_READ`, `DB_WRITE`, `GOTO` и `STOP`.

## 11. Отправка, защита от дублей и ошибки

Перед отправкой контента `advance_run()` создаёт запись в `tg_step_deliveries` с
идемпотентным ключом `<run_id>:<step_key>`.

- Если этот шаг уже имеет статус `sent`, повторная отправка пропускается.
- Telegram message ID сохраняется в `platform_message_id`.
- Ошибка сохраняется в `tg_step_deliveries.error_message`, а run получает статус
  `error` и текст в `tg_sequence_runs.last_error`.
- Для ошибок `blocked by the user` и `chat not found` контакт в `tg_contacts`
  получает статус `blocked`.

Формирование запросов `sendMessage`, `sendPhoto`, `sendVideo`,
`sendVideoNote` и `sendVoice` находится в
`telegram-bot/service/app/telegram.py`. Telegram-разметку из сохранённого текста
готовит `to_telegram_html()` из `telegram-bot/service/app/formatting.py`.

## 12. Разовые и личные сообщения

Разовая рассылка хранится в `tg_broadcasts`, список адресатов и результат каждого
— в `tg_broadcast_recipients`. Отправку выполняют `_deliver_broadcast()` и
`scheduler_loop()` в `telegram-bot/service/app/main.py`. Текущая сегментация
фактически выбирает контакты по статусу, обычно `active`; полноценные сегменты по
покупкам и тегам ещё не реализованы.

Личное исходящее сообщение оператором отправляется функциями
`manual_message()`/`manual_message_by_user()` в `main.py` и записывается в
`tg_manual_messages`. Оно не двигает автоматическую цепочку. Обычные входящие
сообщения сохраняются туда же с направлением `in`; карточка пользователя строит
единую временную ленту входящих, ручных ответов, sequence-доставок и рассылок.

Разовая рассылка проходит обязательные стадии draft → preview аудитории →
owner-test → подтверждение точного числа → немедленная отправка или schedule →
результаты → retry только failed. В maintenance аудитория независимо от сегмента
ограничивается двумя owner ID. Канон и схема:
`knowledge-base/modules/telegram/INBOX_AND_BROADCASTS.md`.

## 13. Что пока отсутствует или намеренно закрыто

- массовая post-purchase доставка: dispatcher работает, но остаётся
  `POSTPURCHASE_TEST_ONLY=true` до заполнения текстов и приёмочного прогона;
- отдельная рассылка после полного завершения мастер-класса: существует только
  отключённый пустой каркас;
- единая атрибуция `ссылка -> пользователь -> покупка -> выручка` в CRM;
- отдельный MAX-адаптер.
- интеграция Tilda/сайта с cookie и покупкой из
  `plans/WEBSITE_CLICK_PURCHASE_ATTRIBUTION.md`.

При изменении фактической логики бота этот файл должен обновляться в том же
коммите, что и код/миграция, изменившие поведение.
