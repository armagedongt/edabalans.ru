# Перенос публичного домена

Статус: `current`
Проверено: 18.10.2026
Владелец: `operations.proxy`

Перенос завершён 18.10.2026. Действующий сайт — `https://похудение-это-есть.рф`,
админка — `admin.похудение-это-есть.рф`. Старый host не предлагать как второй
вход. Остаточные технические зависимости ниже не отменяют это правило.

Эта инструкция сохраняет историю и порядок повторного переноса публичной и пользовательской части
платформы с `edabalans.ru` на `похудение-это-есть.рф`. Она описывает смену публичного
адреса уже работающей системы. По уточнению владельца 18.10.2026
административная оболочка также переключена на
`admin.похудение-это-есть.рф`. Сохранённые технические старые endpoints не
считаются действующими пользовательскими адресами.
Перенос дизайна и содержимого сайта с Tilda на собственный сервер — отдельная
работа, которая должна быть закончена до смены DNS.

## Принятый этап 18 октября 2026 года

Основной домен и `www` направлены на VM; главная, `/blog`, `/lk`, интенсив,
приложения и `/payment*` обслуживаются напрямую. Админка и CRM доступны на
`admin.похудение-это-есть.рф`. Старый blog-поддомен отвечает 410 без редиректа.
`old.похудение-это-есть.рф` подключён к Tilda и закрыт от индексации;
ремонт динамической главной архива отложен владельцем.

Завершающий выпуск заменил исходящие origin в генераторах,
`/podgotovka`, ресурсах уже локальных изображений, Robokassa, MAX, мониторинге
и MCP. `PUBLIC_DOMAIN=edabalans.ru` сохраняется как имя совместимого блока Caddy;
публичный origin бота задаётся независимо через `TELEGRAM_PUBLIC_BASE_URL`.
Это не разрешение использовать прежнее имя в новых пользовательских ссылках.

Владелец разрешил сохранять старые входящие edabalans-ссылки; выключать весь
legacy-контур не требуется. Новые маршруты должны обходиться без него.
Изображения с внешних хранилищ, рассылка старым участникам, новые slug статей,
удаление `/articles/` и ссылки постов Telegram вынесены за границу этого выпуска.
Изменение адресов статей завершено отдельным потоком; канальные правки ведутся
отдельным чатом по своему заданию. Отложенные изображения и внешняя регистрация
Mini App требуют отдельных проверок; доступность /c не доказывает настройку BotFather.

## Правило ссылок и повторный перенос

Решение владельца 18.10.2026: внутренние браузерные переходы одного сайта
хранятся как пути от корня: `/lk`, `/blog/<slug>`, `/intensive`.
Query и fragment сохраняются: `/lk?open=…`, `/#pricing`. Не использовать
`../` для переходов между разделами: результат зависит от глубины страницы.
Это правило применяется к новым материалам и правке существующих ссылок.
Не добавлять промежуточные страницы, redirects, сетевые запросы конфигурации
или обязательную ручную обработку ссылок ради будущей смены домена.

Полные HTTPS URL нужны за пределами текущего браузерного origin: письма,
боты, QR, реклама, платёжные callbacks, webhook, MCP, мониторинг, canonical,
OpenGraph и sitemap. Они берут адрес из действующей настройки владельца,
а не из имени репозитория или случайного Host входящего запроса. Ссылки,
предназначенные для копирования вне сайта, также остаются полными.
Административный host и публичный сайт — разные origin: переходы между ними
нельзя механически превращать в `/…`. Внешние контакты и сторонние источники
сохраняют собственные URL. Архивные снимки HTML не переписываются.

### Уроки текущего переноса

Поиск по Git не видит актуальные ссылки в опубликованных редакциях и кнопках
БД. Проверять нужно и исполняемый шаблон, и текущий сохранённый источник;
исторические версии не переписываются. Рецепты публикуются через существующий
workflow с сохранением карточек, полные редакционные исходники — через свои API.
Рабочие Obsidian-файлы и их основу после технической правки синхронизировать,
не создавая второй оригинал в worktree.

Изменение `.env` ничего не доказывает, если Compose не передаёт соответствующий
ключ контейнеру. `PUBLIC_DOMAIN` сейчас обслуживает совместимый старый блок
Caddy; он не является общим публичным origin бота. Подмена его новым host без
проверки явных блоков Caddy создаёт конфликт. Новое значение DNS TTL не сокращает
ранее закэшированный срок; фактический минимум REG.RU — 3600 секунд.

При проверке приватных изображений клиент должен входить на тот же origin,
с которого запрашивает файл. Переносить cookie между доменами или ослаблять
проверку доступа ради прохождения теста нельзя. Внешние регистрации MAX,
watchdog и MCP не обновляются выпуском backend. Для MAX порядок такой:
добавить новый URL с прежним секретом и событиями → выпустить настройки →
проверить readiness → удалить прежний URL.

Перед переключением следующего домена достаточно подготовить карту изменений
по этим категориям, пройти ближайшие профильные проверки и короткий браузерный
проход с блокировкой прежнего host. Реальная оплата, подробный проход курса,
публикации канала, архив Tilda и перенос картинок включаются только по границам
конкретного поручения; их нельзя скрывать за общим статусом «всё проверено».

## История и процедура для повторного переноса

Разделы ниже сохраняют хронологию и условные действия при следующей смене
домена. Формулировки «до cutover» и старые адреса в сентябрьских снимках —
не состояние работающего сайта. Не выполнять DNS/Tilda-шаги повторно только
из-за их наличия в этой инструкции; текущий адрес закреплён выше и в AGENTS.

## Что было сделано 6 сентября 2026 года

До переноса система была разделена между несколькими адресами:

- `edabalans.ru` был припаркован в REG.RU и указывал на `95.163.244.138`;
- backend, приложения и технические таблицы использовали `api.`, `app.` и `data.`;
- часть пользовательских ссылок проходила через `go`;
- рекламная посадка Tilda вызывала короткую ссылку `/go`, которая затем вела в бота;
- ссылки из ботов открывали отдельный стартовый маршрут интенсива;
- webhook оплаты Tilda отправлялся на `api.edabalans.ru`.

После переноса:

- `edabalans.ru` указывает на production-сервер `201.51.2.210`;
- `/api`, `/apps`, `/lk`, `/intensive`, `/admin` и юридические страницы работают
  на одном origin;
- публичный NocoDB закрыт и доступен только локально на сервере или через SSH;
- Tilda получает персональную прямую ссылку Telegram/MAX через
  `POST /api/messaging/start-link`; при временной недоступности API остаётся
  рабочая прямая ссылка с алиасом;
- интенсив открывается напрямую по
  `/intensive?i=<код>&from=tg|max&entry=bot`, без промежуточного HTTP-редиректа;
- Tilda отправляет оплаты на `/api/integrations/tilda/payments`;
- MAX webhook и внешний мониторинг переведены на корневой домен;
- основная рекламная и бот-цепочка больше не требует промежуточного `go`, но
  технические домены пока остаются для совместимости и нескольких известных
  runtime-потребителей;
- секрет webhook Tilda удаляется из access-логов Caddy.

Схема БД, Robokassa, корзина Tilda, собственный личный кабинет и сохранённые оплаты
при этом не менялись. Тяжёлый backup/restore не требовался: перенос затрагивал
маршруты и настройки, а не постоянные данные.

## Почему первый перенос занял больше времени

Это была не простая замена домена. Одновременно пришлось:

1. объединить раздельные `api/app/data/go` границы;
2. добавить прямую рекламную атрибуцию Telegram и MAX;
3. изменить вход и меню интенсива;
4. найти внешние потребители адресов: Tilda, боты, письма, MAX, мониторинг и Direct;
5. исправить production-deploy и регистрацию новых файлов в карте модулей;
6. дождаться DNS и выпуска нового TLS-сертификата;
7. отдельно закрыть утечку служебного заголовка в access-логи.

При следующем переносе эта архитектурная работа не повторяется: меняется один
канонический origin и его внешние потребители.

## Главное условие следующего переноса

Текущее публичное имя и полный адрес сайта находятся в
[`knowledge-base/PROJECT_IDENTITY.md`](knowledge-base/PROJECT_IDENTITY.md).
По решению Сергея от 18.10.2026 уже перенесён существующий домен
`похудение-это-есть.рф` с Tilda на VM. Короткое обозначение в речи владельца
не означает отдельный домен. Старый сайт сохраняется на согласованном
поддомене `old.похудение-это-есть.рф` в Tilda, закрытом от индексации;
поддомен и DNS уже подключены. Следующая смена домена — отдельная работа.
Неизвестные старые страницы получают общую 404 с навигацией, старые
`/members/*` — сообщение о переезде. Уточнение владельца 18.10.2026:
карточку показываем с утверждённым текстом про письмо, саму рассылку он запускает отдельно.
Существующие рабочие страницы не заменяются заглушкой.
Покрытие старого кабинета задаётся семейством `/members` и `/members/*`,
а не перечнем известных курсов: сюда входят `/members/login`,
`/members/signup/group/*`, `/members/courses/*` и любые вложенные материалы.

Уточнение владельца 18.10.2026: итоговая цель — полностью убрать `edabalans.ru`
из действующего контура, включая административные адреса, ресурсы, API, ботов,
письма и внешние настройки. Прежнее исключение админки в этой инструкции
отменено в рамках текущего переноса; владелец выбрал административный адрес
`admin.похудение-это-есть.рф`. Старые опубликованные извне ссылки требуют
отдельного решения о совместимости; выключать их до инвентаризации нельзя.

До cutover весь публичный сайт уже должен быть перенесён на наш сервер. Если сайт
ещё остаётся на Tilda, сначала выполняется отдельный проект переноса сайта; его
время нельзя включать в оценку простой смены домена.

## Оценка времени

Если сайт уже готов на нашей VM и доступы сохранены:

- автоматическая подготовка кода и конфигурации: 45–90 минут;
- одно окно ручных действий Сергея: 5–10 минут;
- deploy и полная проверка: 20–40 минут;
- распространение DNS: обычно несколько минут после заранее сниженного TTL,
  иначе возможно до прежнего TTL, в текущем случае — почти сутки.

Итого активной работы: ориентировочно 1–2 часа. DNS может обновляться дольше, но
это ожидание, а не работа Codex. Новая функциональность, перенос страниц или смена
платёжной схемы оцениваются отдельно.

## Правило начала работы

Один чат назначается интегратором всего cutover. Он сначала проводит read-only
аудит и одним сообщением сообщает Сергею:

- какие действия полностью выполнит сам через API, Git, SSH и CLI;
- какие 2–5 действий останутся Сергею в браузере;
- точные значения для копирования;
- порядок нажатий и момент, когда их можно выполнять;
- оценку активного времени и максимальное ожидание DNS;
- меняются ли данные или только конфигурация;
- минимальный откат.

После ответа «делай» интегратор проходит весь согласованный маршрут без новых
пауз. Новый вопрос задаётся только при новом расходе, необратимом действии,
неожиданной migration или отсутствующем доступе.

## Этап 1. Read-only аудит

До любых изменений интегратор:

1. Проверяет актуальный `origin/main`, production SHA и состояние контейнеров.
2. Проверяет через официальный API или CLI все внешние сервисы, у которых он есть.
3. Ищет текущий origin и старые поддомены в runtime-коде, Caddy, env-настройках,
   документации и известных внешних потребителях.
4. Собирает таблицу обязательных маршрутов и владельцев:

| Граница | Что должно работать после переезда |
| --- | --- |
| Сайт | `/`, страницы продаж и опубликованные материалы |
| API | `/api/*`, включая приложения и выдачу ссылок |
| ЛК | `/lk`, вход, письмо с паролем и доступы |
| Интенсив | `/intensive`, дни и события прогресса |
| Messaging | Telegram polling, европейский proxy, MAX webhook |
| Tilda | T123, корзина и платёжный webhook |
| Маркетинг | UTM, `yclid`, `bot_start`, цели Метрики, ссылки Direct |
| Операции | `/ready`, Telegram readiness, watchdog и аварийная остановка рекламы |
| Совместимость | старый `edabalans.ru` продолжает обслуживать административные и временно совместимые пути; redirect публичных путей можно включить отдельно после приёмки |

5. Фиксирует, где сейчас обслуживается target-домен, и проверяет возможность сменить
   его DNS. Рабочую привязку к Tilda заранее не отключает.
6. За 24–48 часов до cutover снижает TTL A/AAAA-записей до 300 секунд, если
   интерфейс DNS это позволяет. Если TTL не снижен заранее, Сергей сразу получает
   точный максимальный срок старого кэша.

Не надо создавать новую БД, сервер, поддомены или второй набор приложений.

## Этап 2. Подготовка без переключения DNS

Интегратор в отдельном worktree от свежего `main`:

1. Добавляет `похудение-это-есть.рф` в Caddy параллельно с действующим доменом.
2. Делает runtime совместимым с обоими origin, но до смены DNS сохраняет
   `edabalans.ru` каноническим адресом во всех работающих ссылках.
3. Готовит замену абсолютных ссылок в ботах, письмах, ЛК, интенсиве, приложениях и
   юридических страницах, но не активирует новый origin заранее. Административные
   ссылки сохраняет отдельно и не переводит на публичный домен.
4. Готовит новые адреса:

```text
https://похудение-это-есть.рф/api/messaging/start-link
https://похудение-это-есть.рф/api/messaging/max/webhook
https://похудение-это-есть.рф/api/integrations/tilda/payments
https://похудение-это-есть.рф/api/health/telegram
https://похудение-это-есть.рф/ready
https://похудение-это-есть.рф/intensive
https://похудение-это-есть.рф/lk
```

5. Готовит новые значения Cloudflare watchdog, OAuth callback/redirect URI и ссылок
   рекламных кампаний. Watchdog и активные объявления до приёмки нового `/ready`
   продолжают использовать старый рабочий адрес.
6. Сохраняет `edabalans.ru` как второй рабочий host. Постоянные редиректы не входят
   в предварительный deploy и не обязательны для cutover.
7. Проверяет и меняет конкретные конфигурационные границы:

| Граница | Что сделать при следующем переносе |
| --- | --- |
| `PUBLIC_DOMAIN` | проверить фактические блоки Caddy; сейчас оставить имя legacy-блока, не подставлять публичный origin автоматически |
| `API_DOMAIN`, `GO_DOMAIN` | не превращать обратно в основные публичные адреса; оставить только как machine/legacy hosts до удаления совместимости |
| `APP_DOMAIN` | удалить legacy-зависимости платформы, но не переносить явно оставленные самостоятельные приложения вроде погоды без отдельного решения |
| `ALLOWED_ORIGINS` | добавить новый origin, старый оставить на переходное окно |
| `ACCOUNT_PUBLIC_URL` | заменить на новый `/lk` |
| `TELEGRAM_PUBLIC_BASE_URL`, `INTENSIVE_PUBLIC_URL` | независимые публичные адреса бота и `/intensive`, проверить значения внутри контейнера |
| `ROBOKASSA_RESULT_URL_2`, `ROBOKASSA_SUCCESS_URL_2`, `ROBOKASSA_FAIL_URL_2` | новые полные HTTPS callbacks, передаваемые Compose и включённые в подпись каждой оплаты |
| `BLOG_PUBLIC_ORIGIN`, MCP, MAX и watchdog | отдельно сверить SEO, доверенные host и клиент MCP, обе подписки MAX и публичные URL внешнего наблюдателя |
| `PUBLIC_LINK_ALLOWED_ORIGINS` | разрешить новый origin и временно сохранить старый |
| `MASTERCLASS_OFFERS_URL`, `MASTERCLASS_COURSE_URL`, `MASTERCLASS_ACCOUNT_URL` | сверить с фактическими страницами после переноса сайта |
| admin cookie в `backend/app/crm_routes.py` | не переносить на публичный домен; при запуске `admin.похудение-это-есть.рф` сделать host-only либо конфигурируемой для admin-host |

8. Валидирует Caddyfile, backend и маршруты до DNS. Полноценный публичный TLS для
   нового host на текущем HTTP ACME заранее не проверяется: пока DNS смотрит на
   Tilda, сертификат на нашей VM ожидаемо не выпустится.
9. Прогоняет ближайшие тесты и module inventory, вливает чистый commit в `main` и
   выпускает dual-host-совместимость в production **до** смены DNS. Канонические
   URL, production env, watchdog и реклама пока остаются на `edabalans.ru`.
   Неудачная попытка Caddy получить сертификат нового host не должна нарушить
   старый host.
10. Проверяет текущий `edabalans.ru`, production SHA и `/ready` после этого deploy.

## Этап 3. Один заранее подготовленный пакет ручных действий Сергея

Браузер используется только там, где нет подходящего API или активной авторизованной
сессии Codex. Интегратор заранее открывает нужные страницы и выдаёт готовые значения.

Интегратор выдаёт все значения одним сообщением, но пакет имеет две короткие части:
внешние Tilda endpoints нельзя переключать раньше, чем новый DNS и TLS заработают.

Часть А:

1. **REG.RU:** заменить A-запись корня на IP, который назовёт интегратор; проверить
   `www`; убрать конфликтующую привязку домена к Tilda только после готовности сайта
   на сервере.

После короткого сообщения интегратора «DNS и TLS готовы» Сергей выполняет уже
заранее выданную часть Б:

Пункты 2–3 — только историческая инструкция для отдельного согласованного переноса Tilda. В текущей серверной работе от 18.10.2026 их пропустить; Tilda не менять.

2. **Tilda, если корзина ещё используется и её перенос отдельно разрешён:** заменить только URL webhook на новый
   `/api/integrations/tilda/payments`; токен, Robokassa и события не менять.
3. **Tilda, если остались лендинги и их перенос отдельно разрешён:** заменить в T123 только канонический API URL и
   перепубликовать затронутые страницы.
4. **OAuth-консоли без API:** добавить новый redirect URI, не удаляя старый до
   успешного входа.

Если у Codex есть авторизованный браузер и действие уже согласовано, он делает эти
шаги сам. Если браузер разлогинен или Сергей выполнит их быстрее, интегратор не
пытается восстанавливать сессию. Он не придумывает новые инструкции между частями:
только подтверждает, что наступил заранее описанный момент для части Б.

## Этап 4. Автоматический cutover и приёмка

После части А интегратор без дополнительных вопросов:

1. Проверяет authoritative DNS и не менее одного внешнего resolver.
2. Перезагружает Caddy после подтверждения DNS, чтобы не ждать ACME backoff, и
   дожидается рабочего TLS-сертификата.
3. Одним production-изменением активирует подготовленные настройки Caddy и public
   URL и allowed-origin значения, не меняя БД.
4. Проверяет страницы, API, `/ready` и точный production SHA на новом домене.
5. Даёт короткий сигнал выполнить только применимые и разрешённые пункты части Б. В серверном этапе 18.10.2026 пункты Tilda исключены.
6. Переводит Telegram/MAX и рекламные ссылки штатными API.
7. Только после успешного `/ready` переводит Cloudflare watchdog на новый адрес;
   до этого он продолжает контролировать старый и не ставит рекламу на паузу из-за
   планового DNS-переезда.
8. Проверяет внешние webhook, включённые в текущий перенос. Tilda в серверный этап 18.10.2026 не входит: настройки, публикации и `test=test` не выполнять.
9. Выполняет минимальный сквозной тест двух веток:
   - серверная посадочная → персональная Telegram-ссылка → `bot_start` → интенсив;
   - серверная посадочная → персональная MAX-ссылка → `bot_start` → интенсив.
10. Подтверждает, что `i`, `from`, `entry`, UTM и `yclid` дошли до событий одного
   лида, а `/intensive` и открытый день записались в прогресс.
11. Проверяет тестовую оплату только если платёжный контур менялся. При простой
   замене URL достаточно штатного теста webhook; реальную оплату не проводить.
12. Проверяет watchdog и точные ID активных кампаний.
13. Оставляет `edabalans.ru` рабочим совместимым host. Если позже нужен именно
    redirect, добавляет его отдельным Caddy commit/deploy после приёмки; путь и query
    обязаны сохраняться.

## Условия готовности

Переезд завершён только когда одновременно подтверждены:

- новый домен и TLS работают из внешней сети;
- обязательные страницы и API возвращают ожидаемые ответы;
- Telegram и MAX принимают новых пользователей;
- персональный код и рекламная атрибуция сохраняются;
- включённые в текущий этап платёжные и MAX webhook отвечают по своему протоколу; Tilda-проверки исключены из серверного этапа;
- ЛК открывается, а действующие доступы не изменились;
- watchdog смотрит на новый домен;
- старый домен либо продолжает работать, либо перенаправляет на новый;
- production SHA совпадает с прошедшим CI commit;
- секреты отсутствуют в Git, отчётах и access-логах.

Браузерные сессии между двумя разными корневыми доменами не переносятся. После
cutover пользователю может понадобиться один раз снова войти в ЛК; персональная
ссылка `i` заново восстановит участника интенсива. Это не потеря аккаунта, прав или
прогресса. До объявления готовности интегратор отдельно проверяет чистый браузер и
повторный вход существующего пользователя.

DNS propagation не является незавершённой разработкой, если authoritative DNS уже
верен, новый сервер работает, старый домен совместим, а известный прежний TTL
зафиксирован.

## Минимальный откат

При проблеме, которая ломает вход или оплату:

1. вернуть прежнюю A/AAAA-запись;
2. вернуть предыдущий URL внешнего webhook только если новый endpoint не принимает
   запросы;
3. развернуть предыдущий исправный Git SHA;
4. сохранить управление рекламой по действующему контракту `operations.health`: остановка и возобновление зависят от готовности и настроенных порогов watchdog; перенос не меняет эту политику.

Откат не включает восстановление БД, если migration и запись постоянных данных не
выполнялись.

## Чего не повторять

- не начинать с браузера, если действие покрывает API;
- не менять DNS до deploy dual-host-конфигурации и проверки старого рабочего host;
- не менять одновременно домен и несвязанную бизнес-логику;
- не просить Сергея по одному клику после каждого технического шага;
- не использовать локальный DNS как единственную проверку propagation;
- не удалять fallback-ссылку на ботов до полной внешней проверки;
- не выводить токены в shell output и не оставлять их в access-логах;
- не объявлять работу готовой до проверки включённых в этап серверных страниц, Telegram/MAX, ЛК, атрибуции и мониторинга; отложенные Tilda, изображения, рассылку и подробные пользовательские сценарии перечислять отдельно.


## Уточнение владельца 18.10.2026: атрибуция и ссылки канала

Приоритет — законченный перенос без бесхозных прежних адресов. Не предполагать,
что исторические письма и ссылки обязательно требуют долгой совместимости:
сначала проверить реально отправленные сообщения, внешние настройки и фактические
потребители. Отсутствие важных отправок пока является предположением владельца,
а не установленным результатом аудита. Для каждого старого маршрута зафиксировать
потребителя и итог: замена у источника, временная совместимость с критерием
завершения либо отключение после подтверждения отсутствия зависимостей.
Исправление доменных зависимостей существующей атрибуции входит в перенос;
новый конструктор и сквозная аналитика остаются отдельным следующим этапом
по [сохранённому ТЗ](plans/CHANNEL_FIRST_ATTRIBUTION_20261018.md).

После готовности целевых статей и окончательных адресов блога пройти публикации
основного Telegram-канала и заменить ссылки на Пикабу, служащие только анонсом
собственной статьи, на ссылки соответствующих опубликованных статей сайта.
Исправить также формулировки обычных анонсов «новый пост на Пикабу» на анонсы
материала сайта через `edabalans-writer`, не ограничиваясь заменой href.
Сохранить ссылки и упоминания, где предмет сообщения — опыт автора на Пикабу,
обсуждение, комментарии либо конкретный контекст площадки. Не выполнять слепую
замену всех вхождений домена. Неоднозначные случаи и статьи без опубликованного
соответствия в блоге собрать для решения владельца, не подставляя главную блога.

Перед правкой составить карту message_id → исходный URL → статья блога → решение,
сохранить прежний текст и entities для отката вне Git, учесть URL в тексте,
скрытых ссылках и кнопках. Правка существующих постов не создаёт новые публикации
и не запускает рассылку. После правки проверить сохранность остального текста,
медиа и сущностей, доступность статьи и фактический адрес ссылки. Сначала получить
полную выборку через существующий API/экспорт; неполную выборку не объявлять
проверкой всего канала. Серверный каталог источников остаётся у `platform.knowledge`,
редакционная работа — у `platform.content`, публикации статей — у `platform.blog`.


## Аудит URL и правило редиректов — решение 18.10.2026

Сергей требует единый список прежних адресов Tilda, публичных ссылок канала,
платёжных страниц и рекламных посадок с комментариями и ручными действиями.
На основном домене страницы должны выдаваться непосредственно: HTTP-redirect,
meta refresh и JavaScript-переход между host не являются выполнением переноса.
Любой необходимый redirect — отдельное индивидуальное решение владельца;
прежние рекомендации этой инструкции о redirects не разрешают включать их автоматически.

Старый сайт на `old.похудение-это-есть.рф` должен сохранять прежние сценарии.
Смена host не переписывает абсолютные ссылки, API и внешние загрузчики. Если
сохранение old без правок конфликтует с полным удалением прежнего origin,
показать конкретную зависимость владельцу, не выбирать молча один вариант.

Первичный read-only отчёт сохранён вне Git:
`D:\Codex\exports\site-link-audit-20261018\index.html`; CSV 01–05 и JSON
рядом — доказательства аудита, не новая библиотека публикаций. Публичный sitemap
дал 41 URL, проверка расширена до 59 уникальных адресов. Публичная история канала
собрана до сообщения №1: 508 доступных постов. Объединённая таблица содержит
149 пар пост/URL: 130 подтверждены текущей публичной версией, 19 найдены только
в историческом серверном каталоге и требуют перепроверки. API Директа прочитан
без записи: 15 кампаний, 74 объявления и 43 быстрые ссылки; в выбранном аккаунте
все полученные кампании/объявления возвращены как архивные.

Подтверждённые зависимости до переноса:
- главная Tilda загружает `/homepage.js` с серверного origin, затем
  `/preview/homepage-release-candidate?embed=tilda`;
- `/podgotovka` загружает `/landing/direct/motivation-hero.js`, затем

  содержимое и соответствие новому сценарию не подтверждены;

неопубликованные и не связанные публичными ссылками страницы остаются отдельной
