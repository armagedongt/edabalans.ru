# Единая специализированная админка

## Решение

Нужна одна защищённая точка входа `/admin`, но не одна гигантская страница и не одна
таблица. Админка является общей оболочкой над независимыми предметными модулями.

```text
/admin
├── /admin/crm
├── /admin/dqs
├── /admin/strength
├── /admin/metabolism
└── /admin/messaging       # только отдельной будущей задачей
```

## Общая часть

- единая серверная авторизация администратора;
- единая навигация, визуальный каркас и обработка ошибок;
- общий `users.id` во всех модулях;
- ссылки между карточкой человека в CRM и его данными приложений;
- общий audit context для административных изменений;
- один публичный backend только через Caddy.

## Независимые модули

Каждый раздел сохраняет собственные таблицы, FastAPI router, service layer, тесты и
frontend. Сбой или изменение DQS не должно требовать переписывания CRM или силовых.

Предлагаемые API-префиксы:

```text
/admin/api/crm/...
/admin/api/dqs/...
/admin/api/strength/...
/admin/api/metabolism/...
```

Существующие `/admin/api/users` и `/admin/api/payments` можно поддерживать как
совместимые aliases во время переноса, затем удалить отдельной миграцией API.

## Карточка пользователя

CRM показывает только компактные сводки приложений:

- DQS: доступ, дата старта, число заполненных дней, последнее сохранение;
- силовые: доступ, последняя тренировка, число сессий;
- метаболизм: наличие расчёта и время последнего обновления.

Подробные данные открываются в соответствующем модуле с тем же `user_id`.

## Что не объединяется

- таблицы DQS, силовых и метаболизма не складываются в `users`;
- пользовательские frontend Tilda не встраиваются в admin shell;
- NocoDB остаётся отдельной технической админкой на `data.edabalans.ru`;
- Telegram/messaging не добавляется в текущий этап переноса приложений.

## Маршрутизация текущей CRM

Текущая `/crm` временно сохраняется и может перенаправлять на `/admin/crm`. После
проверки закладок и внешних ссылок основной точкой входа становится `/admin`.
