# Рабочий процесс разработки с ИИ

Статус: `current`
Проверено: 01.10.2026
Владелец процесса: Сергей Воронцов

Документ адаптирует полезные идеи публичного проекта
`pavel-molyanov/molyanov-ai-dev` на commit
`2104d6e16a8a0b805a80e87907fa50615bf88387` к уже существующей архитектуре
edabalans.ru. Исходная методика установлена глобально как набор рабочих
инструментов, но не становится вторым источником правил проекта.

Оригинальные Codex skills и роли-агенты установлены глобально 23.08.2026. Они
дают повторяемые способы исследования, планирования, реализации и ревью во всех
проектах, но не заменяют ограничения конкретного репозитория. Глобальный skill
`sergey-development-workflow` задаёт личные предпочтения владельца: русский язык,
пропорциональные вопросы, поиск экономии ручной работы и заранее согласованные
production-точки.

Источник: https://github.com/pavel-molyanov/molyanov-ai-dev

## 1. Выбирать самый короткий достаточный путь

| Вид задачи | Наш путь |
|---|---|
| Небольшая понятная правка | Сразу исследовать затронутую границу, изменить и выполнить одну ближайшую проверку без отдельного reviewer |
| Среднее изменение поведения | Собрать важные вопросы одним пакетом, реализовать, выполнить адресные tests и один профильный review |
| Исправление ошибки | Сначала воспроизвести и установить причину, затем исправлять только по просьбе владельца |
| Большая функция с неясным поведением | Канонические требования/ТЗ → решение владельца → реализация |
| Новый или существенно изменяемый модуль | Общий `knowledge-base/MODULE_DEVELOPMENT_STANDARD.md` и только применимое доменное дополнение |
| Новый или изменяемый Telegram-модуль | Общий стандарт плюс `knowledge-base/modules/telegram/MODULE_DEVELOPMENT_STANDARD.md` |
| Документация/аудит | Работать по явно названному источнику доказательств, не менять код без отдельной задачи |
| Визуальная правка | Сохранить существующий стиль, проверить затронутые размеры и состояния |

Полное интервью и большой user-spec не требуются для каждой мелкой правки. Они
нужны только тогда, когда отсутствие решения действительно может привести к двум
разным продуктам или несовместимым реализациям.

Для пространного запроса сначала найти факты в затронутой границе. Если остаётся
существенная развилка, предложить один ограниченный рабочий результат для оценки
либо предварительное ТЗ и объяснить рекомендуемый вариант. Ясный запрос не требует
выбора режима или формального интервью. Preview остаётся по прямой просьбе.

Тип изменения определяется результатом, а не расширением файла. Замена утверждённого
текста в HTML — редактура; code-writing нужен при изменении логики, разметки,
экранирования, доступа или иного программного договора. Название и описание
существующего продукта менять через редакцию `product-catalog/core` по
`knowledge-base/PRODUCT_CATALOG.md`, без migration только ради текста.

Перед реализацией задачи, которая может попасть в `main` или production, выполняется
короткий impact-аудит. Он заранее отвечает на пять вопросов: какой источник истины
меняется, будут ли затронуты постоянные данные, нужны ли migration/backup/test restore,
какие сервисы действительно требуют build/test/restart и как выглядит минимальный
откат. Результат определяет объём процесса: незатронутый Telegram, backend или другой
сервис не пересобирается и не перезапускается «на всякий случай». Для маленькой
безопасной правки аудит занимает секунды; отдельный отчёт нужен только при обнаружении
неожиданного риска или расширения маршрута.

Если маленькая правка неожиданно требует migration, нового сервиса, нескольких
модулей или тяжёлого выпуска, сначала проверить существующий редактор/API и
владельца факта. Если расширение неизбежно, объяснить его владельцу до зависимой
реализации. При новом серьёзном impact повторить аудит; не пересобирать и не
перезапускать незатронутый сервис без фактической зависимости.

## 2. Источники истины

- Код, миграции и конфигурация владеют фактической реализацией.
- `docs/knowledge-base/` владеет устойчивым продуктовым смыслом и правилами.
- `docs/modules.toml` владеет module id, техническим ownership и отношениями;
  карточка из `docs/knowledge-base/modules/catalog/` владеет человеческим смыслом модуля.
- `docs/plans/` хранит только то, что владелец явно отправил «на потом». Черновик
  текущей работы и незавершённый deploy планом не становятся.
- Реестры и runtime-источники владеют изменяемыми перечнями и порядком;
  `docs/generated/*` является только автоматически построенным представлением.
- Админка визуализирует серверную структуру, но не хранит независимую копию
  условий и переходов.
- Завершённый план не должен продолжать притворяться будущей логикой: фактическое
  состояние переносится в канонический документ, а исходный plan архивируется со
  ссылкой на новый источник истины.

Один факт должен иметь одного владельца. Ссылка допустима, пересказ той же логики
в нескольких файлах — только если явно указано, какой документ главный.

## 3. Правило масштаба и авторизации

Найденная по дороге идея, крайний случай или улучшение не расширяют задачу сами
по себе. Локальный дефект внутри уже согласованного поведения можно исправить.
Новая сущность, таблица, зависимость, продуктовый сценарий или внешний
запуск требуют отдельного решения владельца.
Обычную Git-ветку и безопасную изоляцию выбирать самостоятельно по
`CHAT_WORKSTREAMS.md`; они не расширяют продуктовую задачу.

Для долгой задачи сохраняется короткая точка продолжения:

- что реально сделано;
- что проверено;
- что осталось;
- какие решения от владельца нужны;
- какой документ является актуальным.

Не создавать для каждой задачи новую систему папок, если существующие
`docs/knowledge-base/`, `docs/plans/` и реестры уже покрывают эту роль.

Этап определяется законченным результатом и его проверкой, а не названием слоя
кода. Перед зависимым этапом в режиме «автономно» применять независимую проверку,
если скрытая ошибка предыдущего результата приведёт к дорогой переделке или
неверному выпуску. Порядок, лимит повторов и продолжение независимых частей —
в `references/autonomous-work.md` установленного `sergey-development-workflow`.

## 4. Проверки по риску, а не по ритуалу

Проверка защищает наблюдаемое поведение или явный контракт.

- unit — отдельное решение или вычисление;
- integration — API, PostgreSQL, очередь, файловый или сервисный контракт;
- end-to-end — критический пользовательский путь;
- smoke — запуск и минимальная связь компонентов;
- визуальная проверка — только интерфейс и адаптивные состояния.

Один риск не нужно механически дублировать на всех уровнях. Свободно редактируемый
текст и чистое оформление не фиксируются хрупкими тестами, если только конкретная
формулировка, доступность или протокол не являются обязательным контрактом.

Browser не является обязательной финальной проверкой. Он нужен для изменённого
интерактивного/адаптивного UI и реальной браузерной границы, которую нельзя
дешевле проверить кодом, API, test или детерминированным render. Обычная backend-
логика, Markdown, название или статическая ссылка не требуют ручного обхода мышкой.

Операционные backup/deploy-проверки выполняются тогда, когда задача доходит до
данных или production. Они не подменяют разработку черновой структуры, но остаются
обязательными перед соответствующей опасной операцией.

## 5. Ревью только по доказательствам

Ревью выбирается по масштабу изменения:

- маленькая механическая правка проходит прямую проверку автором изменения;
- изменение наблюдаемого поведения получает один профильный review;
- специализированный test/security/infrastructure review добавляется только при
  изменении соответствующего риска или по прямой просьбе;
- вторая волна выполняется, только если принятое замечание содержательно изменило
  уже проверенный результат.

Это проектное правило заменяет более тяжёлый общий ритуал установленных skills.
Наличие активного execution skill само по себе не требует отдельного reviewer для
опечатки, ссылки, локального CSS или механического обновления документа.

Замечание считается рабочим только если указаны:

1. конкретный файл/контракт и наблюдаемый факт;
2. нарушенное требование;
3. реалистичное условие возникновения;
4. последствие для пользователя, данных, безопасности или сопровождения.

Размер функции, количество веток, жёсткое значение, число mock или повторение кода
сами по себе не являются дефектом. Это только повод проверить реальный риск.

Ревьюер диагностирует и не меняет артефакты самостоятельно. Исправление не должно
создавать новый продуктовый смысл без решения владельца. Для обычной задачи
достаточно не более двух содержательных волн проверки; после этого оставшиеся
решения честно передаются владельцу.

## 6. Доменные правила загружать по задаче

Карточка модуля направляет к его канону. Для Мастер-класса это
`knowledge-base/modules/masterclass/README.md`, для Telegram —
`knowledge-base/modules/telegram/MODULE_DEVELOPMENT_STANDARD.md`.
Seed/runtime, прогресс, доставка и граф принадлежат доменным источникам;
общий workflow не пересказывает их и не загружает для несвязанной задачи.

## 7. Как исходный фреймворк адаптирован

- Claude не становится источником, а Codex — сгенерированной копией: проект уже
  ведётся непосредственно в Git и Codex.
- Skills и роли-агенты автора установлены глобально как инструменты процесса.
  Проектные правила и продуктовый смысл из них не заимствуются автоматически.
- Активных копий одного и того же skill в установленном наборе нет. Полное тело
  skill загружается только при совпадении trigger, поэтому наличие узких skills
  само по себе не утяжеляет каждую задачу. Проектный `AGENTS.md` имеет приоритет.
- Hooks и MCP-настройки автора не переносятся: они завязаны на другую среду и
  могут выполнять внешние действия без знания ограничений этого проекта.
- `work/{feature}` используется как временный контекст крупной работы, но не
  становится базой знаний или backlog и после завершения не владеет текущими фактами.
- Не вводится обязательное длинное интервью для каждой функции.
- Не вводится правило писать техническую документацию только по-английски.
- Субагенты не запускаются ритуально: только для независимых ограниченных задач и
  по прямой просьбе либо явному поручению применимого skill. «Работай автономно»
  поручает временные проверки из `sergey-development-workflow`; отдельные
  пользовательские чаты и параллельная реализация сохраняют свои условия.

## 8. Production согласуется как маршрут

Перед крупной работой план помечает локальные шаги, preview, изменения данных,
production и труднообратимые действия. Владелец может заранее разрешить весь
конкретный маршрут либо назначить точки промежуточного просмотра.

Если весь описанный маршрут явно разрешён, повторно спрашивать разрешение перед
каждым штатным production-шагом не нужно. Новое согласование требуется только при
изменении цели или production-цели, появлении нового внешнего сервиса/расхода,
неожиданном состоянии, разрушительном последствии, нехватке полномочий либо когда
сама среда требует интерактивного подтверждения.

В текущем проекте успешный push в удалённый `main` автоматически доходит до
production по `OPERATIONS.md`. При запрете выпуска («пока без сервера»,
«покажи перед сервером») сохранить проверенный результат в рабочей ветке,
но не отправлять его в публикующий `main` до разрешения. Отдельный механизм
удержания production этим workflow не создаётся.
