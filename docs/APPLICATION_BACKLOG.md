# Backlog клиентских приложений

Статус: `planned`

Владелец очереди: клиентские приложения и CRM.

Это новые решения, отложенные после миграции Google-приложений. Они не заменяют
`legacy/google/dqs/PENDING_CLIENT_CHANGES.md`: тот список должен быть применён в текущем
переносе.

## Сверка CRM, Tilda и исторических данных

Подробный план синхронизации и возможной замены Members Area:
`plans/TILDA_MEMBERS_SYNC.md`.

- [x] Импортировать каноничную выгрузку зарегистрированных пользователей Tilda Members
  Area от 22.08.2026. Связывать с CRM только по точному нормализованному email,
  сохранять исходные группы и дату снимка. Наличие человека или группы в Tilda
  подтверждает ручную выдачу доступа, но не создаёт выдуманную денежную операцию.
- [x] Сопоставить актуальные группы Tilda с ресурсами:
  - `Мастер-класс`, `Мастер-класс (Стандартный)` и
    `Мастер-класс (С консультацией)` подтверждают доступ к актуальному
    мастер-классу;
  - `«Калорийный» курс` подтверждает доступ к актуальному курсу о калориях;
  - группы с точной пометкой `ОТКРЫТ. Не обновляется.` подтверждают только доступ к
    старой необновляемой версии и не дают права на новые материалы;
  - `Книга рецептов`, `Записи разборов` и `Добро пожаловать` сначала сохранить как

  исторических покупателей. Оставлять только конфликт email/Telegram, спорную
  оплату, несовпадение реального доступа или начатое владельцем восстановление.
- [ ] Добавить безопасный способ обработки ручных клиентов: владелец отправляет человеку

- [ ] После канонической сверки от 22.08.2026 считать PostgreSQL главным источником
  положенных доступов, а Members Area — вторичной системой. Добавить очередь
  расхождений: ждём регистрацию, нужно выдать/убрать группу Tilda, ручное исключение.
- [ ] Настроить для каждого нового товара Tilda штатную автоматическую выдачу группы
  после подтверждённой оплаты: приёмщик «Личный кабинет», публичный ID группы во

- [ ] Запросить у поддержки Tilda наличие поддерживаемого API управления участниками

- [ ] Если API отсутствует и ручная очередь остаётся существенной, спроектировать

  Показывать это отдельно как оценочную legacy-сумму: не считать подтверждённой

- [ ] Добавить в CRM понятный экран сверки данных: подтверждённая выручка, оценочная

## Доступы и оплаты

- Удалить временные экстра-доступы с источником
  `temporary_extra_all_apps`, когда будет окончательно проверена выдача прав по
  покупкам. До удаления обычный доступ проверяется первым, эта группа — только
  резервный второй шаг для заранее согласованных тестовых пользователей.
- Удалить временные бессрочные выдачи DQS с источниками `google_dqs_allowed` и
  `google_dqs_data`, когда для всех актуальных товаров будут настроены и проверены
  `product_access_rules`. После этого единственным источником доступа должна стать
  подтверждённая покупка или явная ручная выдача владельца.
- Автоматически отзывать доступ при подтверждённом возврате оплаты.
- Поддержать срок действия продукта и подписки вместо только бессрочного доступа.
- Сделать владельцу безопасное ручное управление доступом из общей админки.
- Добавить оформление возврата из карточки покупки: продукт, полный/частичный,
  сумма при необходимости, отзыв соответствующего доступа и видимый тег возврата.
  Исходную покупку сохранять в истории.
- Для восстановления старых клиентов считать 01.09.2025 ориентиром права на
  обновляемую версию, но выдавать доступ только после ручного решения владельца;
  явные действующие группы Tilda имеют приоритет над датой.

## DQS

- Решить, нужно ли запрещать исправление прошлых дней после определённого срока или
  после завершения 30-дневной программы. Сейчас дни 1–30 можно исправлять всегда,
  день 31 не создаётся.

## Административная работа с приложениями

- Добавлять редактирование DQS, силовых и метаболизма из общей админки только как
  явные административные команды, а не через подмену пользовательского email.
- Для каждой такой команды сохранять в `admin_app_edits` администратора, целевой
  `user_id`, приложение, действие, изменённые поля, время и результат.

## Очистка пользовательского интерфейса после миграции

- Одной пачкой убрать из всех пользовательских приложений любые видимые упоминания
  Google, Google Sheets и Apps Script. Сообщения об ошибках входа, загрузки и
  сохранения должны говорить только о приложении или сервере, без названия старой
  инфраструктуры.
- В DQS заменить оставшиеся сообщения `Google не ответил` и
  `Ошибка связи с Google` нейтральными сообщениями сервиса. Заодно переименовать
  legacy-функции вида `saveDayToGoogle`, чтобы старые названия не оставались в
  клиентском коде.
- В силовых удалить оставшийся клиентский комментарий про `CORS preflight к Apps
  Script` и проверить собранный код всех трёх приложений поиском по словам
  `Google`, `Sheets` и `Apps Script`.
- Не применять эти правки отдельно: накопить остальные замечания владельца и внести
  согласованную пачку изменений во все приложения за один проход.

## Безопасность входа

- При необходимости усилить подтверждение личности сверх email Tilda: одноразовый код,
  magic link или другой проверяемый сервером механизм.
