# Правила работы с тегами

Этот документ — основной контекст для очистки тегов CRM, переноса старых тегов
LeadTeh и возможной обратной выгрузки в LeadTeh. Перед массовым изменением тегов
нужно сверяться с ним и с фактическими данными, а неоднозначные соответствия
показывать владельцу проекта.

## 1. Общие правила

- Названия, видимые владельцу, пишутся по-русски, могут содержать пробелы и
  нормально переименовываться.
- Технический идентификатор существует только для надёжной работы базы. Владелец
  не должен вводить или использовать его вручную.
- Теги предназначены для сегментации, ручных пометок и управления рассылками.
- Покупки, тарифы, доступы, текущая подписка и технический прогресс сценария не
  должны храниться только в тегах.
- Старые теги не удаляются необратимо. Их можно архивировать или объединять с
  каноническим тегом, сохраняя исходное название и назначения.
- Каждое преобразование хранит источник (`leadteh`, `tilda`, `manual`, `system`)
  и правило, по которому оно выполнено.

## 2. Где хранить разные виды информации

| Информация | Каноническое место |
|---|---|
| Покупка и тариф | `payments` и `products` |
| Фактически разрешённый материал | `user_accesses` и `resources` |
| Источник прихода | `attribution_events` |
| Текущая подписка на канал | `messenger_accounts.subscription_status` |
| Прогресс цепочки | таблицы Telegram-модуля `sequence_runs` |
| Просмотренный материал | событие/контентный тег с каноническим названием материала |
| Ручная остановка рассылки | активный бизнес-тег остановки |

## 3. Категории исторических тегов LeadTeh

### Покупки и тарифы

Исторические теги о покупке преобразуются в структурированные факты продажи.
После проверки старые назначения скрываются из обычного списка тегов. Сумму и
дату нельзя выдумывать: если источник их не содержит, они остаются неизвестными,
а факт покупки получает статус `confirmed` и источник `leadteh_tag`.

Текущая продуктовая терминология:

- `MASTERCLASS_BASIC` — мастер-класс без рецептов;
- `MASTERCLASS_RECIPES` — мастер-класс и рецепты;
- `MASTERCLASS_CONSULT` — мастер-класс, рецепты и консультация;
- `RECIPES_ADDON` — рецепты отдельно;
- `CALORIES_COURSE` — курс о калориях;
- `CONSULTATION` — консультация;
- `COACHING` — сопровождение;
- `TRAINING_COURSE` — курс по тренировкам;
- отдельный продукт для записей консультаций должен получить стабильный код до
  запуска продаж.

Старые комплексные названия необходимо раскладывать на отдельные приобретённые
продукты. Они не должны оставаться единственным доказательством состава покупки.

Предварительное соответствие 17 исторических тарифных тегов:

| Тег LeadTeh | Структурированный результат | Статус правила |
|---|---|---|
| `МК + я сама` | минимальный мастер-класс | согласовано |
| `Просто Мастер-класс` | минимальный мастер-класс | согласовано |
| `Сама 8 недель` | минимальный мастер-класс | согласовано |
| `Сама 3 недели` | минимальный мастер-класс | ожидает подтверждения |
| `МК «Минимальный»` | `MASTERCLASS_BASIC` | согласовано |
| `МК «Стандартный»` | `MASTERCLASS_RECIPES` | согласовано |
| `МК «С консультацией»` | `MASTERCLASS_CONSULT` | согласовано |
| `МК + обратная связь` | мастер-класс и курс о калориях | согласовано как старый средний тариф |
| `Мастер-класс + Калории` | мастер-класс и курс о калориях | согласовано |
| `МК + консультация` | мастер-класс, калории и консультация | согласовано как старый максимальный тариф |
| `МК+Сопровождение` | мастер-класс, калории и консультация | ожидает окончательного подтверждения состава |
| `Всё вместе + консультация` | мастер-класс, калории и консультация | согласовано |
| `Калории + консультация` | калории и консультация | согласовано по смыслу, проверить конфликтующие данные |
| `Калории + обратная связь` | курс о калориях | согласовано |
| `Только Только Калории` | курс о калориях | согласовано |
| `МК доступ 2 мес` | не создаёт покупку; архивный технический тег | согласовано |
| `Калории Доступ 2 мес` | не создаёт покупку; архивный технический тег | согласовано |

Достоверные сигналы вне этой группы:

- `МК Оплатил` — подтверждён факт покупки мастер-класса;
- `Калории Оплатил` — подтверждён факт покупки курса о калориях.

Правило приоритета: структурированная подтверждённая продажа не понижается из-за
старого тега. Если структурированной продажи нет, её можно восстановить из
однозначного тега. Случай, когда тег указывает более высокий тариф, чем уже
записанная продажа, пока направляется на ручную проверку; автоматическое повышение
требует отдельного подтверждения владельца.

Исторический средний тариф означал мастер-класс и курс о калориях без
консультации. Новый средний тариф означает мастер-класс и рецепты. Нельзя применять
новый состав к историческим тегам только из-за совпадения слова «Стандартный».

### Контент и посты

- Просмотр материала должен сохраняться у человека даже после удаления,
  переписывания или повторной публикации поста.
- Канонический вид видимого названия: `Пост - Название материала`. Слово после
  дефиса начинается с прописной буквы.
- Тип материала является частью названия после первого дефиса. Например:
  `Пост - Стрим - Вредная еда`, `Пост - Статья - Название`,
  `Пост - Видео - Название`. Отдельные префиксы `Материал -` и `Стрим -` больше
  не используются.
- Разные написания одного и того же материала объединяются только после сверки.
- Нельзя автоматически объединять два разных поста только из-за похожего названия:
  один материал мог публиковаться в нескольких вариантах.
- Примеры тегов, ранее признанных контентом: `Пристегните ремни`, `Отправил стрим`,
  `Отзыв Анна`, `Отзыв Любовь брокколи`, `Можно эмоции`, `12 изменений`, `Словарь`,
  `Оземпик`, `Скорость похудения`, `Ошибки в похудении`, `Главный принцип`,
  `Где справедливость`, `Сначала шаги`, `Посты 30 растений`.

### Источники

- Источник переносится в атрибуцию, а не остаётся обычным тегом.
- `Пикабу`, `Пикабу новые`, `Пикабу март` и `Пикабу органика` объединяются в
  источник `Пикабу`.
- `Пикабу реклама` остаётся отдельным платным источником.
- Старые названия посевов и площадок (`Шевяков выражение`, `Мышь`, `Соковые`,
  `Помлёва`, `Еда вино`, `Агрономы`, `Свечи`, `Квартира хозяйка` и подобные)
  каталогизируются как источники; неактуальные варианты архивируются после
  переноса атрибуции.

### Подписка и маршрутизация

До отдельного решения владельца текущие состояния подписки остаются видимыми
каноническими тегами. Бот обязан поддерживать их взаимоисключающими: при обновлении
статуса старый статус снимается и назначается только один актуальный. Внутреннее
поле состояния допустимо использовать для надёжности, но оно не заменяет видимые
владельцу теги.

Нужны понятные состояния «подписан сейчас», «не подписан» и «был подписан, затем
отписался». Окончательные русские названия нужно подтвердить перед активацией.

Маршрутизационные признаки хранятся рядом с подпиской, но означают событие входа,
а не текущий статус:

- `Первое посещение` — первый вход человека в основной сценарий;
- отдельный тег для случая, когда при первом входе человек уже был подписан;
- исторический `Зашел подписанный` необходимо сохранить и сопоставить с
  маршрутизацией после уточнения его точного смысла;
- исторический `Сразу подписался` нельзя автоматически считать тем же событием:
  он мог означать подписку уже после показа требования бота.

Архивными остаются датированные проверки и технические циклы: `Новые НЕ пдп`,
`Проверка подписки 02.11`, `Заначка в рассылку ПДП до 01.02.2025`,
`ЗАНАЧКА Старые НЕПОДПИСЧИКИ Новая рассылка`, `В цикле проверки подписки`,
`Нет пдп рассылка шаг 1`, `рассылка пачка 4 (проверь пдп)`, `Эфир НЕ ПДП`,
`не ПДП мёд`, `не ПДП Молоко`, `Не ПДП пластиковые фрукты`,
`Не ПДП подборка`, `Ещё не подписался`, `Рассылка НЕ подписан`,
`Рассылка НА ПОДПИСКУ`, `Новый цикл ПДП`, `подписался после словаря` и
`подписался после эмоционального голода`. Они не участвуют в новой логике.

### Устаревшие и технические теги

- Старые этапы интенсива, скидки, действия с планом, калькулятор, старая лотерея и
  технические шаги рассылок архивируются.
- Технический прогресс новых цепочек хранится в Telegram-модуле, а не в тегах.
- `Первое посещение` важно для маршрутизации. Историческое назначение преобразуется
  в `main_scenario_seen_at`; новые посещения записываются непосредственно в это
  состояние.
- Пустые, ошибочные и явно служебные значения вроде `пусто` или `сбой`
  архивируются.

## 4. Остановка рассылок

Нужны два независимых бизнес-тега:

1. `Стоп — до покупки мастер-класса` — остановить вступительную/продающую цепочку.
2. `Стоп — после покупки мастер-класса` — остановить цепочку после покупки.

Обновления продукта отдельным стоп-тегом не останавливаются.

Старый тег `Стоп Рассылка` означает остановку вступительной цепочки и должен быть
объединён с `Стоп — до покупки мастер-класса` без потери 493 исторических
назначений. Обнаруженный тег `стоп` назначен двум людям, но его смысл неоднозначен;
до ручной проверки автоматически объединять его нельзя.

`Стоп — до покупки мастер-класса` можно поставить вручную. Кроме того, при любой
подтверждённой покупке система автоматически:

1. сохраняет покупку;
2. назначает этот стоп-тег;
3. завершает все активные запуски вступительной цепочки;
4. при подходящей покупке запускает нужную цепочку после покупки.

Это должно быть одним централизованным обработчиком события подтверждённой
покупки, а не отдельным блоком во всех местах продажи. Tilda, ручное подтверждение
в CRM и будущие платёжные источники вызывают один и тот же обработчик. Сценарии
бота только реагируют на итоговое событие и не копируют бизнес-правило.

Упрощение логики бота:

- цепочка «до покупки» прекращается либо по ручному стоп-тегу, либо по событию
  подтверждённой покупки;
- цепочка «после покупки» имеет собственный ручной стоп-тег;
- прогресс и состояние запуска не кодируются десятками технических тегов;
- одно правило оплаты работает для всех входных каналов и отображается на общей
  карте сценариев.

## 5. Обратная выгрузка в LeadTeh

При необходимости восстановить сегменты в LeadTeh экспорт должен содержать:

- email и Telegram ID, если они известны;
- каноническое русское название активного тега;
- исходное название старого тега;
- источник назначения;
- статус преобразования (`active`, `archived`, `merged`, `review`);
- дату назначения, если она была известна источнику.

Покупки и доступы нельзя обратно превращать в неоднозначные комплексные теги.
Для совместимости создаётся явный экспортный словарь: один продукт или доступ —
один понятный тег LeadTeh. Например, мастер-класс, калории и консультация
экспортируются тремя независимыми признаками, а не старым тегом
`Всё вместе + консультация`.

Перед обратной загрузкой формируется CSV-предпросмотр без персональных данных в
Git и отчёт: сколько назначений будет добавлено, объединено, пропущено и оставлено
на ручную проверку.

## 6. Порядок массовых изменений

1. Создать резервную копию базы и зафиксировать контрольные количества.
2. Сформировать предварительный отчёт без изменения production.
3. Подтвердить неоднозначные соответствия у владельца.
4. Применить идемпотентное преобразование: повторный запуск не создаёт дубли.
5. Проверить покупки, доступы, активные теги и несколько карточек клиентов.
6. Сохранить отчёт преобразования без персональных данных.
7. Только после проверки архивировать старые определения и скрыть назначения.
