# Вставка серверного личного кабинета и приложений в Tilda

Статус: `current`
Состояние внедрения: серверный контур выпущен; production-страницу Tilda создаёт и
проверяет владелец.

## Общий принцип

На единственной физической странице Tilda «Личный кабинет» размещается один
контейнер и один стабильный загрузчик. Сервер показывает каталог купленных и
доступных программ; Мастер-класс открывается внутри этого же экрана. Весь
интерфейс и логика остаются на сервере. Email
определяется загрузчиком на закрытой странице Members Area; цена, доступ и срок не
передаются из Tilda. Повторный код на почту не запрашивается. Если загрузчик не
нашёл email Tilda, ручной ввод не показывается: клиент автоматически переходит на
штатную страницу входа Tilda `/members/login`. Перед переходом загрузчик запоминает
только внутренний путь страницы; после успешного входа возвращает человека к тому
же курсу, материалу или приложению. Внешний URL в маршрут возврата не принимается.

Главный экран кабинета показывает email текущего профиля и кнопку «Выйти». Она
завершает штатную сессию Tilda; отдельного серверного выхода для клиента нет.

Эта же единственная страница поддерживает прямые ссылки на курс. Параметр
`?course_day=N` после проверки доступа сразу открывает нужный день, а
`&course_material=ID` — указанный доступный материал. Отдельные страницы или код
в Tilda для каждого дня не нужны. Кнопка «Личный кабинет» открывает тот же адрес
без этих двух параметров и поэтому возвращает к каталогу программ.

Загрузчик получает email из штатного объекта профиля Tilda Members Area (поле
`login`) и короткое время ждёт его инициализации. Видимость email в тексте страницы
для работы не требуется. Ранее сохранённый серверным приложением email не заменяет
текущий профиль Tilda.

Подписанные маркеры предложений и рецептов больше не копируются в отдельные лекции
Tilda. Единое приложение получает нужный маркер от backend только тогда, когда
участник дошёл до соответствующего пункта программы.

```html
<style>
  .tlk-userbar,
  .tlk-userbar__popup,
  .tlk-userbar__user-icon,
  .t-userbar,
  [class^="tlk-userbar"],
  [class*=" tlk-userbar"] { display: none !important; }
</style>
<div data-edabalans-app="account"></div>
<script src="https://app.edabalans.ru/embed.js"></script>
```

На этой же физической странице должен находиться один стандартный блок корзины
Tilda `ST100`. Он может быть визуально скрыт, но не удалён: серверная кнопка
покупки передаёт заказ именно в эту корзину.

Не добавлять на страницу отдельную вставку `masterclass-course`: кабинет сам
откроет её после серверной проверки `ACCESS_MASTERCLASS`. Для аккаунтов со
статусом `waiting_registration`, `pending`, `conflict` или неизвестного CRM-email
тот же экран показывает витрину курсов и приложений с закрытыми кнопками и просьбу
связаться с Сергеем.

Для закрытой проверки перед запуском остаются только внешний адрес главной
Members Area и штатный `ST100` на странице. Саму вставку расширять дополнительным
кодом не нужно.

## Старые отдельные вставки

Блоки ниже оставлены только для совместимости старого стенда. В новую страницу
21-дневного курса их не вставлять: анкета, DQS, рецепты, саморевью и персональные
предложения открываются внутри единого приложения.

## Конкретные места старого стенда

```html
<div data-edabalans-app="onboarding-questionnaire"></div>
<script src="https://app.edabalans.ru/embed.js"></script>
```

### Предложение второго дня

На этой же странице добавить стандартный блок Tilda `ST100`.

## Переходный вход через Tilda

Закрытая страница Members Area определяет email, а backend проверяет по нему
серверные покупки и `ACCESS_MASTERCLASS`. Текущая группа Tilda не выдаёт доступ к
материалам. Ручного ввода email и почтового кода в этом переходном запуске нет.

## Корзина

Кнопка приложения не содержит самостоятельно заданной цены. Она запрашивает
актуальный вариант у backend и только затем передаёт корзине команду
`#order:Название=Цена`. Tilda webhook остаётся источником подтверждения оплаты;
нажатие кнопки само по себе не создаёт покупку и не выдаёт доступ.

Tilda может сначала прислать заказ со статусом `processing`, а затем повторить тот
же `orderid`/`paymentid` со статусом `paid`. Backend в таком случае обновляет одну
существующую оплату и выдаёт каждый положенный доступ ровно один раз; повторный
`paid` остаётся безопасным дублем.
