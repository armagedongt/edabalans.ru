# Рабочие потоки и чаты проекта

Статус: `current`  
Проверено: 29.08.2026
Назначение: не создавать несколько независимых источников решений при параллельной работе.

## Чат и субагент — не одно и то же

- Отдельный чат — долговременное направление со своей историей и ручным участием
  владельца.
- Субагент — временный исполнитель ограниченной подзадачи внутри одного текущего
  задания. Его результат возвращается в основной поток и сам по себе не становится
  новым владельцем требований.

## Рекомендуемая карта активных чатов

| Поток | Что делает | Главный результат |
|---|---|---|
| Сайт и Мастер-класс | структура курса, runtime, Tilda-встраивание, прогресс и интерфейс | код сайта и документы `modules/masterclass/` |
| Редактура материалов | авторский текст, порядок, хвосты и связи между материалами | файлы `content/masterclass/` |
| Telegram после покупки | сценарии сообщений по фактам курса до финального дня 20 | `POST_PURCHASE_MASTERCLASS.md`, затем граф и код бота |
| CRM/инфраструктура | отдельный поток только во время активного переноса или deploy | модели, миграции и `OPERATIONS.md` |

Одновременно достаточно двух потоков реализации одного продукта. Третий допустим
для независимого исследования или ревью, которое не меняет те же файлы и контракт.

Отдельный чат для обсуждения может подготовить spec/checkpoint и передать его
свободному рабочему чату. Нельзя «передать разговор»: сначала в Git фиксируются
`module_id`, решения, входные материалы, ожидаемый результат и точка продолжения,
затем другому чату отправляется точный путь или commit. Отдельный handoff-файл нужен
только когда другой чат реально продолжает эту работу. Он имеет уникальное имя;
общий `work/integration-handoff.md` не используется.

## Перед параллельной работой

Для каждого потока зафиксировать:

1. владельца решения;
2. `module_id` и входные материалы;
3. ожидаемый выход;
4. затрагиваемые файлы и контракты;
5. зависимость от другого потока;
6. точку объединения и checkpoint; отдельный документ передачи нужен только при
   реальном переходе работы в другой чат.

Интегратор — временная роль на одну приёмку. Им становится чат, который
в данный момент принимает готовую работу. Постоянный отдельный чат-интегратор
не требуется. В один момент `main` сводит только один поток.

## Checkpoint-лог параллельного потока

После каждого содержательного checkpoint и обязательно перед передачей результата
поток публикует в своём чате короткий фактический лог. Общий редактируемый лог для
нескольких чатов не создаётся. После статуса `ready_for_integration` тот же checkpoint
отдельным сообщением передаётся текущему интегратору.

```text
СТАТУС: working | blocked | ready_for_integration | integrated | production
СДЕЛАНО:
РЕШЕНИЯ/КОНТРАКТЫ:
ФАЙЛЫ И COMMIT:
ПРОВЕРКИ:
ЗАВИСИМОСТИ/БЛОКЕРЫ:
СЛЕДУЮЩИЙ ШАГ:
MAIN/PRODUCTION: local | main | production
```

Лог содержит факты, а не пересказ разговора: точные route/API-контракты, владельца
зависимости и commit/checkpoint. При `blocked` называется один конкретный внешний
вход, которого не хватает. Перед каждым merge интегратор перечитывает последние
checkpoint-логи связанных задач, а после production оставляет сводный итог по всем
потокам в той же форме.

Независимые feature-чаты не правят общие `docs/generated/*`: это build output.
CI и production пересобирают его из уже объединённого commit перед тестами и
сборкой, поэтому параллельные чаты не соревнуются за один JSON/Markdown и не
выпускают отдельный «догоняющий» commit.

Если два чата меняют один порядок дней, один контракт события или одну схему
таблиц, их не надо вести параллельно. Один поток меняет источник истины, второй
получает готовый checkpoint.

Если столкновение обнаружилось уже в работе, оба потока не продолжают править один
источник. Чат, который позже занял contract, останавливает эту часть, сохраняет
непересекающийся результат и ждёт checkpoint владельца contract. Это не делает
незавершённую ветку планом.

Старый чат можно архивировать, когда его результат уже принят в `main` или для
незавершённой работы сохранён понятный checkpoint. Архив сохраняет историю, поэтому
после такой проверки старые задачи лучше архивировать, чтобы не продолжать работу
из устаревшего контекста.

## Чистая production-линия

`main` и её рабочая папка не являются местом для незавершённых файлов. Каждый
поток создаёт отдельную ветку/worktree от актуального `origin/main`; integration
выполняется в отдельном чистом worktree. Если в основной папке остались старые
изменения, они сохраняются отдельно до разборки и не участвуют в следующем
выпуске.
