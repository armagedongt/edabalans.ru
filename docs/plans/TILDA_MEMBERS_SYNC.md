# Синхронизация доступов CRM и Tilda Members Area

Статус: `planned`

## Решение владельца об источнике истины

Канонический импорт участников Tilda от 22.08.2026 является исходной сверкой:
ручные доступы, которые на тот момент существовали только в Members Area, уже
перенесены в CRM и считаются достоверными для стартовой версии базы.

После этой сверки PostgreSQL является главным источником истины по покупкам и
положенным клиенту доступам. Members Area — вторичная система исполнения доступа
к страницам Tilda. Ручная выдача или удаление группы только в Tilda после этой
даты не должны молча менять канонические права CRM.

Нужно различать:

- **положенный доступ** — что записано в CRM на основании покупки, подарка,
  возврата или явного решения владельца;
- **фактический доступ Tilda** — в каких группах Members Area человек находится;
- **расхождение** — CRM требует группу, но человек не зарегистрирован или не
  добавлен; либо группа есть в Tilda, но соответствующее право отсутствует в CRM.

## Что Tilda умеет штатно

Для новых покупок Tilda может автоматически создать участника и добавить его в
нужную группу после подтверждения оплаты. Для этого к корзине подключается
приёмщик «Личный кабинет», включается отправка данных только после оплаты, а товар
связывается с публичным ID группы через внешний код товара.

Официальная инструкция:
https://help-ru.tilda.cc/membership

Такой механизм нужно использовать для обычных новых покупок на Tilda одновременно
с отправкой webhook в российский backend:

1. Tilda получает подтверждение платежа.
2. Webhook создаёт покупку и положенные доступы в PostgreSQL.
3. Штатный приёмщик Tilda добавляет пользователя в соответствующие группы Members
   Area.
4. CRM показывает, совпали ли положенные права и известный снимок Tilda.

## Ограничение публичного API

Документированный публичный Tilda API предназначен для проектов, страниц и
экспорта контента. В нём нет опубликованных методов создания участника Members
Area, добавления в группу или удаления из группы:
https://help.tilda.cc/api

Поэтому backend сейчас нельзя строить в расчёте на официальный двусторонний API
управления группами. Автоматизацию браузером с пользовательскими cookies и паролем
не использовать как production-интеграцию: она нестабильна, небезопасна и может
сломаться при изменении интерфейса Tilda.

Отдельно нужно запросить у поддержки Tilda, существует ли закрытый или партнёрский
API Members Area для текущего тарифа. До письменного подтверждения считать, что
такого поддерживаемого API у проекта нет.

## Ближайшее практическое решение

Добавить в CRM очередь сверки Members Area со статусами:

- `Синхронизировано`;
- `Ждём регистрацию в Tilda`;
- `Нужно выдать группу в Tilda`;
- `Нужно убрать группу в Tilda`;
- `Ручное исключение владельца`;
- `Не удалось определить`.

В карточке клиента показывать:

- положенные продукты и доступы из CRM;
- последний известный снимок групп Tilda;
- недостающие и лишние группы;
- готовый короткий список действий для владельца;
- дату последней сверки и источник изменения.

Для старого клиента без регистрации рабочий путь остаётся ручным:

1. владелец отправляет ссылку регистрации Tilda;
2. клиент сообщает использованный email;
3. CRM связывает email с существующим человеком;
4. владелец подтверждает положенные права и при необходимости цену обновления;
5. CRM помещает клиента в очередь «Нужно выдать группу в Tilda»;
6. после ручной выдачи владелец отмечает действие выполненным.

Пока нет API, это не полностью автоматическая выдача, но CRM становится единым
чек-листом и исключает забытые действия.

## Отложенное открытие уже купленных материалов

Покупка и фактическое открытие материала — разные состояния. Если клиент оплатил
пакет заранее, CRM сразу фиксирует все входящие в него права, но отдельный модуль
может оставаться закрытым до прохождения нужного этапа мастер-класса.

Согласованная продуктовая логика:

- первая часть каталога рецептов открывается после завершения дня 4; при
  необходимости правило дополнительно выдерживает индивидуальную паузу в три дня;
- вторая часть каталога рецептов открывается после завершения дня 20;
- курс о калориях и курс по тренировкам, купленные в составе пакета заранее,
  открываются после завершения мастер-класса;
- владелец не должен вручную просить клиента написать после прохождения и затем
  выдавать каждый модуль;
- две копии мастер-класса для разных тарифов не создавать.

В данных для каждого ресурса нужно различать:

- `entitled` — клиент приобрёл ресурс или получил его вручную;
- `locked` — ресурс приобретён, но условие открытия ещё не выполнено;
- `available` — условие выполнено, ресурс можно открыть;
- `revoked` — доступ отозван, например после возврата;
- основание права, условие открытия, время выполнения условия и фактическое время
  открытия.

Условие открытия должно задаваться централизованным правилом ресурса, например
`recipes_part_1 -> masterclass_day_4_completed`, а не копироваться во все сценарии
бота, страницы и webhook. После появления события о завершении этапа backend один
раз пересчитывает доступы. CRM, бот и приложения читают один результат.

### Что можно сделать только средствами Tilda

В одном курсе Tilda лекцию можно открыть после прохождения другой лекции
(стоп-урока) или после заданной даты. Это подходит для последовательного открытия
одинакового набора материалов всем участникам одного курса.

Это не является полноценным решением для разных оплаченных пакетов. Если рецепты,
калории и тренировки находятся в одном курсе и отличаются только стоп-уроками,
пользователь базового тарифа тоже сможет дойти до их открытия. Разные группы
Members Area разграничивают наборы материалов, но документированного API для
автоматического добавления уже существующего участника в новую группу после
завершения лекции нет.

Поэтому временное Tilda-only решение возможно лишь частично:

- сам мастер-класс остаётся в одном экземпляре;
- общие для всех материалы открываются штатными стоп-уроками Tilda;
- купленные дополнительные ресурсы остаются отдельными группами/курсами;
- их отложенная выдача остаётся в ручной очереди CRM, пока Tilda не предоставит
  поддерживаемый API управления группами.

### Рекомендуемое решение без ручной выдачи

Не строить сразу полноценный новый личный кабинет. Оставить мастер-класс и продажи
в Tilda, а отложенные модули открывать через защищённые страницы/мини-приложения на
сервере:

1. Tilda передаёт подтверждённую покупку в PostgreSQL.
2. Backend сохраняет все приобретённые ресурсы как `entitled`, но ещё `locked`.
3. Завершение дня 4, дня 20 или всего мастер-класса создаёт серверное событие;
   правило может добавить индивидуальную задержку от времени этого события.
4. Backend переводит только положенные этому клиенту ресурсы в `available`.
5. Кнопка в Tilda или сообщение бота ведёт на защищённый серверный материал;
   FastAPI проверяет личность, покупку и выполненный этап.
6. В CRM видны одновременно «Куплено», «Пока закрыто», причина и дата открытия.

Такой вариант убирает ручную выдачу, не требует двух версий мастер-класса и не
зависит от возможности Tilda программно менять группы. Перед реализацией нужно
отдельно согласовать надёжный сигнал завершения дня/курса и способ авторизации на
защищённых страницах. Простая скрытая ссылка без серверной проверки не подходит:
её можно передать другому человеку.

## Что нужно реализовать

- Справочник соответствий `product/resource -> Tilda group public ID` с датами
  действия правил.
- Раздельные понятия `desired_access` и `observed_tilda_group`.
- Импорт нового снимка Members Area без перезаписи канонических прав CRM.
- Экран расхождений и массовый CSV-чек-лист для ручной работы.
- Настройку всех новых товаров Tilda: внешний код товара, группа, приёмщик Members
  Area и отправка только после подтверждённой оплаты.
- Тестовую покупку каждого действующего тарифа: backend получил webhook, CRM
  назначила правильные ярлыки, Tilda создала участника и открыла правильные группы.
- Обработку возврата: история покупки сохраняется, CRM отзывает положенное право,
  а Members Area попадает в очередь на удаление группы.
- Запрос в поддержку Tilda о поддерживаемом API управления участниками и группами.
- Реестр правил отложенного открытия ресурсов и событий прогресса мастер-класса.
- Состояния приобретённых ресурсов `locked/available/revoked` и их отображение в
  карточке клиента.
- Серверную проверку доступа к рецептам, калориям и тренировкам без доверия одной
  скрытой ссылке.
- Автоматический пересчёт доступов после дня 4, дня 20 и завершения мастер-класса.

## Долгосрочный вариант

Если ручная очередь остаётся значимой или Tilda не предоставляет API, заменить
Members Area собственным кабинетом и проверкой доступов через российский FastAPI.
Тогда PostgreSQL будет не только источником истины, но и непосредственным
механизмом допуска к материалам. Страницы Tilda можно временно оставить публичной
оболочкой, но закрытые материалы должны проверять сессию и права на сервере.

Такое решение проектируется отдельной задачей: авторизация, восстановление доступа,
перенос страниц и материалов, защита файлов, журнал действий и поэтапное отключение
групп Members Area.
