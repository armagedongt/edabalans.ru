# раздел админки «Продукты и офферы»
Нужно добавить в общую админку отдельный раздел:
**Продукты и офферы**
Этот раздел не должен быть частью только Telegram-бота. Он является общей продуктовой системой проекта и должен использоваться:
-  Telegram; 
-  MAX в будущем; 
-  сайт; 
-  персональные страницы допродаж; 
-  CRM/Core; 
-  другие будущие каналы. 
Источник истины по продуктам, ценам, пакетам, скидкам и активным персональным предложениям — PostgreSQL.
Цены не хардкодить в Telegram-сценариях и HTML-страницах.

Текущие ориентиры цен:

`Калории + тренировки + разборы`
ориентировочная пакетная цена:
`8775 ₽`.

# 3. Продукты
В разделе должна быть вкладка/подраздел:
**Продукты**
Для каждого продукта хранить минимум:
- `product_code` — стабильный внутренний код; 
-  название для владельца; 
-  публичное название; 
-  описание; 
-  стандартную цену; 
-  валюту; 
-  активен / выключен; 
-  порядок отображения; 
-  какие `accesses` продукт выдаёт после покупки. 
Например:
`RECIPES`
после покупки выдаёт:
`ACCESS_RECIPES`
`CALORIES`
выдаёт:
`ACCESS_CALORIES`
---
# 4. Тарифы и пакеты
Отдельный подраздел:
**Тарифы / Пакеты**
Пакет должен собираться из существующих продуктов/accesses.
Например:
`MASTERCLASS_RECIPES`
Состав:
-  мастер-класс; 
-  рецепты. 
В админке владелец должен видеть:
-  название пакета; 
-  состав; 
-  сумму цен компонентов; 
-  зачёркнутую цену; 
-  фактическую цену продажи; 
-  размер экономии; 
-  активность; 
-  порядок отображения. 
Пример:
```
```
```
Мастер-класс + рецепты
Мастер-класс       6900
Рецепты            2900
-----------------------
Ценность            9800
Цена пакета         8900
Экономия             900
```
При изменении цены в админке новые значения должны использоваться всеми страницами и каналами через API без изменения исходного кода.
---
# 5. Офферы
Отдельный подраздел:
**Офферы**
Оффер — это не сам продукт, а правило продажи одного или нескольких продуктов конкретной аудитории по определённым ценам и условиям.
Пример:
`EARLY_UPSELL_72H`
Параметры:
-  название; 
-  внутренний `offer_code`; 
-  активен / выключен; 
-  длительность; 
-  набор доступных продуктов/пакетов; 
-  стандартные цены; 
-  специальные цены; 
-  зачёркнутые цены; 
-  текстовые метки/заголовки для страницы; 
-  порядок карточек. 
На первом этапе продолжительность такого оффера:
`72 часа`.
Значение должно быть редактируемым.
---
# 6. Персональные офферы пользователей
Создать сущность примерно:
`user_offers`
Поля минимум:
- `id`; 
- `user_id`; 
- `offer_id` / `offer_code`; 
- `started_at`; 
- `expires_at`; 
- `status`; 
- `created_by_event`; 
- `completed_at` nullable; 
-  timestamps. 
Главное правило:
**таймер акции существует только на сервере.**
Не использовать браузерный таймер как источник истины.
Когда бот впервые реально выдаёт пользователю предложение:
```
```
```
started_at = текущее серверное время
expires_at = started_at + duration
```
Например:
```
```
```
25.08.2026 15:00
→
28.08.2026 15:00
```
---
# 7. Не перезапускать таймер
Открытие страницы НЕ должно:
-  создавать новый оффер; 
-  менять `started_at`; 
-  продлевать скидку. 
Повторная отправка того же сообщения также не должна автоматически продлевать срок.
Один оффер стартовал один раз — срок считается от исходной даты.
Продление возможно только отдельным явным действием/новым оффером.
---
# 8. Проверка срока скидки
При каждом открытии персональной страницы backend проверяет:
```
```
```
now < expires_at
```
Если да:
показывается специальная цена.
Если:
```
```
```
now >= expires_at
```
показывается обычная цена.
Статус можно автоматически переводить в `expired`.
---
# 9. Обязательная повторная проверка перед покупкой
Критическое требование.
Недостаточно проверить скидку только при загрузке страницы.
Перед формированием кнопки/checkout или непосредственно перед переходом к оплате backend должен ещё раз проверить:
-  существует ли пользователь; 
-  существует ли оффер; 
-  активен ли он; 
-  не истёк ли `expires_at`; 
-  не куплен ли уже этот продукт; 
-  соответствует ли цена текущему офферу. 
Нельзя доверять:
-  цене из браузера; 
-  JavaScript; 
-  параметрам URL; 
-  старой открытой вкладке. 
Пример:
Пользователь открыл страницу со скидкой за 5 минут до окончания акции.
Через час нажал «Купить».
Backend обязан увидеть, что срок уже закончился, и не давать старую специальную цену.
---
# 10. Покупка во время действия оффера
Покупка одного товара должна немедленно менять набор доступных предложений.
Например изначально у пользователя нет:
-  рецептов; 
-  калорий; 
-  консультации. 
Ему показываются три предложения.
Через час он покупает рецепты.
После подтверждения платежа:
-  рецепты исчезают со страницы; 
-  соответствующий access появляется в CRM; 
-  оставшееся время первоначального 72-часового окна продолжает действовать; 
-  калории и консультация могут оставаться доступны по цене текущего оффера. 
**Покупка не должна автоматически перезапускать исходные 72 часа.**
Если для следующей покупки нужен новый срок — это должен быть отдельный `offer_code`.
---
# 11. Персональная страница допродаж
Нужна одна динамическая страница, а не отдельный HTML для каждого пользователя.
Условное назначение:
`offers.edabalans.ru`
Точный домен можно выбрать согласно существующей архитектуре.
Пользователь приходит по безопасной персональной ссылке.
Страница через API определяет:
-  пользователя; 
-  его покупки; 
-  accesses; 
-  активный `user_offer`; 
-  оставшееся время; 
-  товары, которые ему уже принадлежат; 
-  товары, которые ему разрешено предложить; 
-  актуальные цены. 
И только после этого рендерит карточки.
---
# 12. Что показывать на странице
Каждая карточка оффера должна уметь отображать:
-  название; 
-  краткое описание; 
-  состав; 
-  обычную цену; 
-  зачёркнутую цену; 
-  специальную цену; 
-  экономию; 
-  срок действия предложения, если применимо; 
-  кнопку покупки. 
Если продукт уже куплен или соответствующий access уже есть — не показывать предложение.
---
# 13. Логика Telegram/MAX
Telegram не должен содержать всю продуктовую матрицу.
Его задача:
1.  определить момент показа оффера; 
2.  попросить CRM/Core создать/получить `user_offer`; 
3.  отправить тизирующее сообщение; 
4.  дать кнопку на персональную страницу. 
Пример:
```
```
```
День 4–5 мастер-класса
↓
проверить, есть ли вообще доступные доппродукты
↓
создать EARLY_UPSELL_72H, если он ещё не создан
↓
отправить:
"Для вас доступны дополнительные материалы на специальных условиях"
↓
кнопка "Посмотреть"
```
Полный ассортимент и точную цену Telegram сам не определяет.
Позже MAX должен использовать тот же API и те же офферы.

# 14. Пример продуктовой персонализации
Если у пользователя:
```
```
```
MASTERCLASS_BASIC ✓
RECIPES ✕
CALORIES ✕
CONSULTATION ✕
```
страница может показать:
-  рецепты; 
-  калории; 
-  консультацию; 
-  подходящий пакет. 
Если:
```
```
```
MASTERCLASS_RECIPES ✓
RECIPES ✓
CALORIES ✕
CONSULTATION ✕
```
рецепты больше не показывать.
Если консультация уже включена в исходный тариф — не продавать её повторно.
Это должно определяться через покупки + accesses, а не через ручные Telegram-теги.

# 15. Tilda checkout
Оплата пока остаётся на Tilda.
На динамической странице кнопка должна запускать стандартную механику корзины/заказа Tilda.
В проекте уже используется синтаксис типа:
```
```
```
#order:Название товара=Цена
```
Не доверять этому примеру вслепую.
Перед реализацией найди в существующих рабочих Tilda-страницах реальный действующий формат заказа и используй его.
Название и цена должны формироваться из данных backend, а не быть хардкодом HTML.
Также необходимо обеспечить, чтобы после подтверждённой оплаты новая покупка попадала обратно в CRM/Core и сразу влияла на доступные предложения.
---
# 16. Цены
Архитектура должна различать минимум:
- `regular_price` — обычная стоимость; 
- `compare_at_price` — зачёркнутая цена/ценность; 
- `offer_price` — специальная цена конкретного оффера. 
При необходимости можно добавить пакетную цену как отдельное поле/сущность.
Не вычислять бизнес-значимые цены только на frontend.

# 18. Важное ограничение
Не смешивать:
- `product`; 
- `bundle`; 
- `offer`; 
- `user_offer`; 
- `payment`; 
- `access`. 
Это разные сущности.
Пример:
`CALORIES` — продукт.
`CALORIES + TRAINING + REVIEWS` — пакет.
`EARLY_UPSELL_72H` — маркетинговый оффер.
Персональное окно Васи с 25 по 28 августа — `user_offer`.
Платёж Васи — `payment`.
Право Васи открыть курс — `access`.

## Главная бизнес-идея

**Главная бизнес-идея:** Telegram продаёт интерес и приводит на страницу; CRM/Core решает, что человеку можно купить; страница показывает персональный ассортимент и актуальную цену; Tilda принимает оплату; подтверждённая покупка возвращается в CRM и немедленно меняет дальнейшие предложения.
