# Импорт Telegram-канала в каталог авторских материалов

Статус: `draft`
Владелец содержания: Сергей Воронцов
Проверено: 22.08.2026
Связанный общий документ: `CONTENT_CATALOG_SPEC.md`
Источник решения: запрос владельца о полной оцифровке собственного Telegram-канала
после пилота Pikabu.

## 1. Решение

Telegram-канал подключается как второй источник существующего модуля **«Каталог
статей»**, а не как отдельная база и не как часть движка рассылок Telegram-бота.

Для первой полной загрузки используется **штатный экспорт Telegram Desktop в JSON**.
Обычный бот, добавленный в канал, не является способом получить всю старую историю:
Bot API присылает ему новые `channel_post` и `edited_channel_post`, а очередь
неполученных updates хранится ограниченное время. Поэтому рекомендуемая схема такая:

```text
Telegram Desktop JSON export         бот / webhook после даты подключения
        ↓ история канала                         ↓ новые и изменённые посты
        └──────────────────────┬─────────────────┘
                               ↓
                    Telegram source adapter
                               ↓
                    общий Content Catalog
                               ↓
              PostgreSQL + /admin/content + AI API
```

Если штатного экспорта окажется недостаточно для отдельных метрик, обсуждений или
регулярной сверки, отдельным этапом допускается клиент TDLib/MTProto, авторизованный
как пользователь-владелец канала. Это более сложный и чувствительный по безопасности
вариант; для первой версии он не нужен.

Этот документ ничего не подключает к production, не добавляет бота в канал, не
переключает webhook и не импортирует реальные данные.

## 2. Что владелец должен передать

### Обязательно для первого dry-run

1. Ссылку или `@username` нужного канала.
2. Каталог штатного экспорта **именно в формате JSON**, полученный в Telegram
   Desktop для этого канала.
3. Короткое подтверждение, что это полный экспорт доступной истории, а не выбранный
   диапазон дат.
4. Путь к экспорту на локальном компьютере. Реальный экспорт не кладётся в Git.

### Желательно

- выгрузить фотографии, видео, голосовые и файлы вместе с JSON, если их нужно
  сохранять и использовать при будущих рерайтах;
- сообщить название связанной группы обсуждений, если у канала включены комментарии;
- отдельно экспортировать связанную группу обсуждений в JSON, только если принято
  решение импортировать комментарии;
- дать один-два примера постов, которые владелец считает одной публикацией, если они
  фактически разбиты на несколько последовательных сообщений;
- при наличии старых ручных выгрузок статистики передать их отдельным файлом, не
  смешивая с экспортом сообщений.

### Что передавать не нужно

- пароль Telegram;
- SMS-код или пароль двухфакторной авторизации;
- bot token в чат или Git;
- session-файл Telegram-клиента;
- права администратора существующему production-боту для первичного импорта.

Если позже будет одобрен collector на TDLib/MTProto, `api_id`, `api_hash` и session
хранятся только как серверные секреты. Их не должно быть в документации, логах,
GitHub или сообщениях чата.

## 3. Как сделать рекомендованную выгрузку

В Telegram Desktop открыть нужный канал и выбрать в меню **Export chat history**.
Формат — **Machine-readable JSON**. Для полного архива выбрать весь доступный период.

Рекомендуемые варианты:

- **быстрый пилот:** JSON + фотографии, без тяжёлых видео;
- **полный архив:** JSON + все нужные типы медиа;
- **комментарии:** отдельный JSON-экспорт связанной группы обсуждений.

Экспорт всего аккаунта через `Settings → Advanced → Export Telegram Data` тоже
возможен, но для этой задачи хуже: он содержит лишние чаты и больше персональных
данных. Предпочтителен экспорт конкретного канала.

До проектирования окончательного parser contract выполняется dry-run реального файла:
версии Telegram Desktop могут различаться по набору полей. Parser обязан сначала
составить отчёт о найденных типах сообщений и полях, а не молча потерять неизвестные
структуры.

## 4. Границы с существующим Telegram-ботом

В репозитории уже существует messaging-сервис `telegram-bot`, который обслуживает
цепочки, сообщения пользователям, рассылки и атрибуцию входа. Каталог канала решает
другую задачу:

| Система | Назначение |
|---|---|
| `telegram-bot` | диалоги с пользователями, цепочки, рассылки, покупки и лиды |
| `content catalog` | архив авторских публикаций, метрики, комментарии, поиск и рерайт |

Они используют общую PostgreSQL и административную авторизацию, но разные таблицы,
API и права. Контент канала не должен автоматически становиться сообщением рассылки,
а черновик ИИ не должен публиковаться без отдельного подтверждения владельца.

Существующий тестовый бот `@TetrisgfgfgfBot` не назначается администратором канала в
рамках этого ТЗ. Решение о dedicated collector bot или безопасном расширении
существующего сервиса принимается только на этапе инкрементальной синхронизации.

## 5. Единица публикации

По умолчанию один Telegram-пост — это одно сообщение канала. Исключения:

- медиагруппа/альбом с общим `grouped_id` становится одной публикацией с несколькими
  дочерними сообщениями и медиа;
- текст и подпись к медиа сохраняются без перестановки;
- сервисные сообщения не превращаются в статьи, но учитываются в отчёте импорта;
- удалённое сообщение не восстанавливается из воздуха и получает статус расхождения,
  если на него ссылаются комментарии или другие посты;
- несколько обычных сообщений подряд не склеиваются автоматически только по близкому
  времени. Для серии создаётся отдельная ручная или ИИ-связь;
- репост хранит исходный текст и метаданные пересылки, но получает признак
  `forwarded`; отдельно можно исключить чужие репосты из авторского корпуса.

Устойчивая внешняя идентичность: `telegram:<channel_id>:<message_id>`. Публичная
ссылка `https://t.me/<username>/<message_id>` хранится отдельно и может измениться
при смене username, поэтому не является первичным ключом.

## 6. Что сохраняется у каждого поста

### Идентичность и время

- внутренний UUID;
- `source=telegram`;
- channel ID, username и название канала;
- message ID и grouped ID;
- публичная ссылка, если она существует;
- дата публикации и дата редактирования;
- дата первого импорта и последней сверки;
- состояние: `published`, `edited`, `deleted`, `unavailable`, `unknown`;
- признак авторского, пересланного, рекламного, закреплённого и сервисного сообщения;
- подпись/имя автора поста, если Telegram его показывает.

### Контент

- исходный текст или caption без изменения;
- Telegram entities: ссылки, жирный текст, курсив, цитаты, код, упоминания, хэштеги;
- нормализованный текст для поиска и ИИ;
- упорядоченные блоки и безопасное представление форматирования;
- опросы и варианты ответов, если они присутствуют в экспорте;
- фотографии, видео, voice/video note, аудио, документы и их порядок;
- локальный относительный путь из export package, MIME/type, размер и checksum;
- кнопки или другие структуры только если они реально присутствуют в источнике;
- исходный JSON-фрагмент или его checksum для повторного разбора;
- `content_hash` и версия parser.

Исходник неизменяем. Редактирование поста создаёт новую версию в
`content_item_versions`; ИИ-аннотации и рерайты хранятся отдельно.

### Концовка, CTA и рекомендации

Как и для Pikabu, отдельно выделяются:

- последняя смысловая часть поста;
- дословная подводка;
- CTA-текст и целевое действие;
- ссылка, использованная в призыве;
- тип CTA: Telegram-бот, сайт, продукт, другой пост, комментарии, подписка, другое;
- список рекомендованных собственных постов;
- статус рекомендаций: `present`, `mentioned_without_links`, `absent`, `review`;
- уверенность автоматического выделения и ручная проверка.

Ссылки на PubMed, DOI, журналы и другие научные источники сохраняются в архивном
исходнике, но получают `type=reference` и `ignored_for_generation=true`. Они не
считаются CTA или рекомендациями, если контекст явно не говорит обратного.

### Метрики

Доступные счётчики сохраняются снимками с `captured_at`, потому что они меняются:

- просмотры;
- пересылки/forwards;
- ответы/комментарии;
- реакции по emoji/custom emoji;
- доступные дополнительные поля конкретного экспорта или Telegram API;
- источник снимка: `desktop_export`, `bot_update`, `tdlib`, `manual`;
- признак полноты и причина отсутствующих полей.

Нельзя обещать, что Telegram Desktop JSON содержит всю административную аналитику.
Dry-run фиксирует фактические поля. Детальные графики конкретного сообщения и
публичные пересылки доступны администратору через пользовательский Telegram API
только когда сам канал разрешает просмотр статистики. Это отдельный этап, а не
обязательная часть первой загрузки.

## 7. Комментарии

Комментарии к посту канала технически являются веткой автоматически пересланного
сообщения в связанной discussion supergroup. Поэтому экспорт только канала может
дать счётчик ответов, но не обязан содержать все тексты обсуждения.

Для полного импорта комментариев нужен отдельный экспорт связанной группы либо
пользовательский TDLib/MTProto-collector. В БД сохраняются:

- chat ID группы, message ID и thread/top message ID;
- связь с исходным channel post ID;
- parent message ID и дерево ответов;
- автор и `is_owner_comment`;
- дата публикации/редактирования;
- текст, entities, ссылки и медиа;
- реакции и доступные счётчики;
- deleted/hidden/service status;
- источник и полнота импорта.

Импорт комментариев является отдельным переключаемым этапом. Первая полезная версия
каталога может быть запущена без него. Это разумный вариант, если анализ пяти постов
Pikabu покажет, что стоимость комментариев выше их пользы.

## 8. Способы получения данных и их сложность

| Способ | История | Новые посты | Комментарии | Расширенная статистика | Сложность |
|---|---:|---:|---:|---:|---|
| Telegram Desktop JSON | да, доступная аккаунту | только новой выгрузкой | отдельный экспорт группы | частично | низкая |
| Bot API | нет полного backfill | да | только доступные боту новые события | нет admin-графиков | низкая/средняя |
| TDLib/MTProto от пользователя | да | да | да, с pagination | да, при наличии прав | высокая |

Рекомендуемый порядок:

1. JSON-export для всей истории.
2. Повторный JSON-export или ручной импорт для первой сверки идемпотентности.
3. Только после проверки — bot/webhook для новых постов и редактирований.
4. TDLib/MTProto — лишь если реально нужны детальные комментарии, admin statistics,
   удалённые расхождения или автоматическая регулярная сверка истории.

Bot API не сообщает надёжную полную историю удалений, а Telegram хранит ожидающие
bot updates не более 24 часов. Поэтому даже после подключения бота нужен периодический
reconciliation: новый export или TDLib-проверка по выбранному интервалу.

## 9. Модель данных

Используется общая схема из `CONTENT_CATALOG_SPEC.md`:

- `content_sources`;
- `content_items`;
- `content_item_versions`;
- `content_segments`;
- `content_links`;
- `content_recommendations`;
- `content_media`;
- `content_tags` / `content_item_tags`;
- `content_metric_snapshots`;
- `content_comments`;
- `content_import_runs`;
- `content_raw_snapshots`;
- будущие `content_ai_annotations`, `content_embeddings`, `content_ideas`,
  `content_derivatives`, `content_publications`.

Для Telegram адаптеру понадобятся поля/таблицы деталей сообщения: channel ID,
message ID, grouped ID, forward origin, discussion chat/thread ID и исходные entities.
Точная форма — отдельная JSONB detail-таблица или Telegram-specific columns —
принимается после dry-run реального экспорта, чтобы не проектировать по догадкам.

Контентные теги не смешиваются с CRM `tags/user_tags`, которые описывают людей,
источники лида и маркетинг.

## 10. Импорт и сверка

Importer выполняется локальной CLI-командой или закрытым worker, не публичным
HTTP-методом. Обязательные режимы:

- `inspect` — показать структуру экспорта без записи в БД;
- `dry-run` — посчитать публикации, альбомы, медиа, комментарии и ошибки;
- импорт одного message ID;
- полный идемпотентный импорт;
- `resume` после ошибки;
- повторное чтение неизменившегося экспорта без дублей;
- обновление метрик отдельным снимком;
- отчёт `discovered / imported / updated / unchanged / partial / failed / skipped`.

До записи проверяются:

- число сообщений и диапазон дат;
- неизвестные типы сообщений;
- наличие и целостность путей к медиа;
- дубли channel/message ID;
- альбомы и сообщения без текста;
- публичные ссылки и смена username;
- покрытие комментариев, если приложен discussion export;
- размер пакета и требуемое место в Object Storage.

## 11. Админка

Telegram добавляется фильтром источника в общую `/admin/content`, а не получает
отдельную несвязанную админку.

Нужно видеть:

- общее число постов и диапазон дат;
- дату последнего импорта/обновления;
- публикации, альбомы, репосты и серии;
- просмотры, forwards, реакции и комментарии по снимкам;
- концовку, CTA, целевую ссылку и рекомендации;
- комментарии автора/аудитории, если они импортированы;
- темы, о которых давно не было публикаций;
- дубли и близкие по смыслу материалы;
- статусы `partial`, неизвестные типы и ошибки медиа;
- происхождение любого ИИ-вывода вплоть до message/comment ID.

Ручное исправление меняет только классификацию и производные данные, но не исходный
текст Telegram.

## 12. ИИ-функции

После надёжного импорта каталог должен отвечать на вопросы:

- о чём и когда владелец уже писал;
- какие темы давно не обновлялись;
- какие посты лучше сработали по просмотрам, реакциям, forwards и обсуждению;
- какие хуки, концовки и CTA повторяются;
- какие Telegram-, bot-, site- и product-ссылки использовались;
- какие вопросы, возражения и формулировки аудитории можно превратить в идеи;
- какие старые материалы подходят для рерайта в блог или новую площадку;
- какие Pikabu- и Telegram-публикации являются версиями одной идеи;
- насколько новый черновик похож на уже опубликованное.

Дополнительные функции:

- единый timeline Pikabu + Telegram + будущий блог;
- `topic freshness score` и очередь тем на обновление;
- сравнение платформ по одному тезису;
- поиск удачных связок `hook → body → CTA`;
- граф внутренних рекомендаций и битых ссылок;
- сохранение происхождения каждой идеи и рерайта;
- контент-календарь с защитой от слишком частого повтора темы;
- подготовка черновика, но без автоматической публикации в первой версии.

## 13. Безопасность

- Реальные JSON/HTML/media exports и discussion messages не попадают в Git.
- До импорта discussion group, содержащей данные пользователей, проверяется свежий
  backup и настоящее восстановление PostgreSQL по `docs/OPERATIONS.md`.
- Raw package хранится во временном защищённом каталоге; постоянные media/raw copies —
  только в закрытом Object Storage.
- PostgreSQL не открывается наружу; API и админка доступны через Caddy.
- Токены, `api_hash`, session, телефон, SMS и 2FA не логируются и не коммитятся.
- Импорт идемпотентен и не удаляет исходники.
- Никакие посты или комментарии Telegram не редактируются и не публикуются.
- Подключение бота, TDLib и production synchronization требует отдельного явного
  разрешения владельца.

## 14. Этапы и предварительная трудоёмкость

Telegram структурированнее Pikabu и не требует обхода виртуализированной web-ленты,
поэтому базовый импорт ожидаемо значительно проще.

### T0 — проверить реальный экспорт

- inspect JSON и inventory типов;
- выбрать пять разнородных постов, включая альбом/медиа/редактирование;
- dry-run без БД;
- подтвердить, какие метрики реально присутствуют.

Оценка после получения файла: **1–3 часа**.

### T1 — история постов без комментариев

- parser JSON;
- маппинг в общий каталог;
- альбомы, entities, ссылки, медиа;
- идемпотентность, тесты и отчёт покрытия;
- первый безопасный импорт после проверки backup.

Если каркас общего Content Catalog уже существует: **0,5–1,5 рабочего дня**.
Если его ещё нет, создание общей схемы/API оценивается отдельно и не должно второй
раз приписываться Telegram.

### T2 — комментарии

- связать discussion export с постами;
- восстановить thread и parent tree;
- обработать удалённые/сервисные сообщения и расхождения;
- добавить фильтры автора и аудитории.

После просмотра реального discussion export: ориентир **0,5–2 рабочих дня**.
Этап можно полностью исключить.

### T3 — новые публикации

- минимальные права collector bot;
- `channel_post` / `edited_channel_post`;
- webhook или совместимый существующий polling-контур;
- очередь, идемпотентность, retries и reconciliation.

Ориентир: **0,5–1,5 рабочего дня** после отдельного разрешения на подключение.

### T4 — пользовательский API и расширенная статистика

- TDLib/MTProto authorization;
- безопасная session;
- history/comments pagination;
- admin message stats и public forwards при наличии прав;
- rate limits, renewal и эксплуатационная инструкция.

Ориентир: **2–4 рабочих дня**. Делать только если T0–T2 покажут реальную пользу.

Таким образом минимально полезный Telegram-каталог — T0 + T1. Комментарии, bot-sync
и TDLib не должны искусственно увеличивать оценку первого результата.

## 15. Критерии готовности T0/T1

- зафиксирован фактический формат и версия экспорта;
- показаны число сообщений, постов, альбомов, диапазон дат и неизвестные типы;
- каждый пост имеет устойчивый source/channel/message ID;
- повторный импорт не создаёт дублей;
- текст, entities, ссылки и порядок медиа сохраняются;
- исходник и рерайт физически разделены;
- редактирование создаёт новую версию;
- доступны дата, ссылка, концовка, CTA, рекомендации и последняя метрика;
- научные источники сохранены, но исключены из CTA/обычной генерации;
- missing metrics обозначены как отсутствующие, а не как нули;
- реальные export/media не попали в Git;
- импорт имеет dry-run, отчёт покрытия и тесты;
- production-бот и Telegram-канал не изменены.

## 16. Вопросы, решаемые после T0, а не заранее

1. Достаточно ли фактических полей Telegram Desktop для views/forwards/reactions?
2. Нужно ли копировать тяжёлые видео в Object Storage или хранить только metadata?
3. Считать ли цепочку последовательных сообщений одной публикацией?
4. Нужны ли комментарии после замера полезности/стоимости на пяти постах Pikabu?
5. Нужна ли автоматическая синхронизация или достаточно периодического экспорта?
6. Нужна ли дорогая admin statistics через пользовательский API?

Эти вопросы не блокируют inspect/dry-run.

## 18. Фактический результат T0

Статус проверки: `completed`, 22.08.2026. Проверен штатный Telegram Desktop JSON
публичного канала `@Fitness_Talks` без записи в БД.

- 703 записи, из них 694 сообщения и 9 service events;
- 509 консервативных публикаций, 73 уверенных альбома и 2 review-кластера;
- дубли и неизвестные поля/типы не найдены;
- присутствуют text entities, реакции, polls и метаданные вложений;
- отсутствуют views, forwards, comments count и `grouped_id`;
- discussion export пригоден для отдельного T2, но не даёт исходный channel message ID
  для всех корней, поэтому связь комментариев потребует отдельного контракта.

Владелец разрешил T1 в text-first режиме: без бинарных медиа и без комментариев, с
обычной и app-deep-link ссылкой на каждый пост.
