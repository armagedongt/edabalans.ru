# ТЗ: карта файлов, модулей и таблиц проекта

Статус: `archived`
Причина архивации: реализовано системой `docs/modules.toml`,
`tools/module_inventory.py` и `docs/generated/*`; текущие правила находятся в
`../README.md` и `../knowledge-base/OWNER_PROJECT_GUIDE.md`.
Источник требований: владелец проекта, 22.08.2026.

## Оценка требования

Цель правильная: без карты большой монорепозиторий становится понятен только авторам.
Однако один ручной список абсолютно всех файлов будет длинным, дублирующим код и почти
неизбежно устареет. Нужна двухуровневая система:

1. человекочитаемая карта по смысловым модулям;
2. автоматически проверяемый машинный инвентарь файлов и таблиц.

## Что должно быть описано вручную

Для каждого production-модуля:

- назначение и пользовательский процесс;
- главные точки входа и основные файлы;
- используемые таблицы и связи;
- входящие и исходящие API/интеграции;
- фоновые процессы;
- источник истины;
- безопасные операции и запреты;
- канонический документ;
- статус: работает, draft, planned или archived.

Для каждой постоянной таблицы:

- зачем существует;
- кто создаёт и читает записи;
- ключевые связи;
- можно ли редактировать вручную;
- какие данные являются персональными;
- какая миграция её создала;
- какой модуль считается владельцем.

## Что должно проверяться автоматически

Будущий скрипт документационного аудита должен:

1. получить список SQLAlchemy `__tablename__` и Alembic-объектов;
2. сравнить его с зарегистрированными таблицами в паспортах данных;
3. получить список production-каталогов, API routers, сервисов и фоновых worker;
4. проверить, что у каждого есть модуль-владелец и ссылка на документацию;
5. находить битые относительные ссылки Markdown;
6. завершаться ошибкой CI при появлении недокументированной таблицы;
7. формировать полный технический manifest автоматически, не заставляя человека
   вручную поддерживать список каждого CSS, теста и `__init__.py`.

## Уже реализованный первый этап

- единая точка входа `docs/README.md`;
- начальная карта модулей, файлов и таблиц;
- навигатор базы знаний `docs/knowledge-base/README.md`;
- очередь будущих изменений `docs/plans/`;
- правила обязательного обновления в `AGENTS.md`.

## Следующие этапы

1. Сверить карту с полным фактическим деревом production-кода.
2. Разделить `CRM_DATA_MODEL.md` на общую модель и паспорта модулей при росте объёма.
3. Добавить структурированный реестр модулей, например `docs/modules.yaml`.
4. Реализовать audit-скрипт и CI-проверку.
5. Добавить шаблон README для нового модуля и шаблон паспорта новой таблицы.
6. Подключить отчёт о непокрытых объектах к pull request.

## Критерий готовности

Ни одна новая постоянная таблица или production-модуль не может попасть в `main` без
владельца, назначения и канонической ссылки; полный список файлов генерируется, а
смысловая карта остаётся короткой и пригодной для чтения человеком.
