# Единая админка и административный контекст приложений

Статус: `archived`
Причина архивации: общая shell/session и каталог инструментов реализованы;
текущий контракт находится в `../ADMIN_ARCHITECTURE.md`, а карта инструментов —
в module registry. Оставшиеся новые функции требуют отдельного явного плана.
Владелец решения: Сергей
Согласовано: 22.08.2026
Область: `/admin`, CRM, DQS, силовые тренировки, метаболизм

## Цель

Сделать единую аккуратную административную оболочку, из которой владелец может найти
человека и бесшовно перейти к его карточке CRM, DQS, силовым тренировкам,
метаболизму и связанному контакту Telegram. Все переходы сохраняют один `users.id`.

## Зафиксированные решения

1. В меню используются короткие названия: `DQS`, `Силовые`, `Метаболизм`.
2. DQS в админке является аналитикой только для чтения. Администратор не исправляет
   пользовательские дни из этого интерфейса.
3. Силовые и метаболизм не получают отдельную копию клиентского интерфейса. Один и тот
   же frontend работает в двух контекстах:
   - `user` — текущий пользователь определяется обычным клиентским способом;
   - `admin` — авторизованный администратор выбирает `target_user_id`.
4. Расчёты, отрисовка, валидация и редактирование в обоих контекстах общие. Отличаются
   только получение личности, адреса административного API, плашка выбранного человека
   и запись аудита.
5. Административный backend никогда не подменяет email или сессию пользователя. Он
   проверяет административную сессию, принимает `target_user_id` и пишет изменение в
   `admin_app_edits`.
6. Люди с действующим доступом показываются в списке приложения даже без созданного
   состояния. Просмотр карточки или сводки не создаёт пустую строку состояния.
7. Пустое состояние создаётся только после явного действия `Открыть приложение`.
8. В рабочем frontend и его сообщениях не должно быть видимых или скрытых упоминаний
   прежнего табличного сервиса и прежнего скриптового backend. Архивные исходники в
   `legacy/google/` сохраняются как исторический материал и не являются production-кодом.
9. NocoDB остаётся внешним техническим разделом. Его интерфейс не встраивается и не
   копируется в общую оболочку.

## Контекст человека

Карточка человека содержит постоянную шапку и переключатель:

`CRM · DQS · Силовые · Метаболизм · Telegram`

Для каждого раздела показываются независимо:

- наличие действующего доступа;
- наличие состояния/данных;
- краткая сводка и время обновления;
- доступное действие: открыть, начать пустое состояние или посмотреть причину
  недоступности.

Параметр `?user=<uuid>` является общим способом передать выбранного человека между
административными разделами. Отсутствие данных не должно отключать переход, если у
человека есть доступ к приложению.

## DQS

Административный экран переносит полезную аналитику старого прототипа в общий стиль:

- поиск и список пользователей;
- дата старта, заполненные дни, средний DQS и краткая динамика;
- периоды 7, 14, 30 дней и произвольный диапазон;
- график динамики;
- средние значения по категориям;
- матрица дней и лента заполнений.

Все операции DQS в админке являются `GET`; элементов изменения пользовательских дней
нет.

## Силовые и метаболизм

Общий frontend получает адаптер контекста с единым контрактом:

```text
loadState()
saveState(expectedVersion, changes)
getIdentity()
```

Пользовательский адаптер использует обычный API приложения и проверку доступа.
Административный адаптер использует административную сессию и `target_user_id`.
Каждое успешное административное сохранение записывает приложение, администратора,
целевого пользователя, действие, изменённые поля, версию до/после и время.

## Визуальная система

- одна навигация, цветовая система, типографика, карточки, статусы и состояния загрузки;
- постоянная шапка выбранного человека внутри всех специализированных разделов;
- полноэкранные переходы без iframe;
- мобильная навигация без потери доступа к переключателю человека;
- CRM постепенно использует ту же оболочку, не меняя её предметную логику.

## Границы текущей работы

- не создаются новые таблицы и копии пользовательских данных;
- не меняется Telegram-движок; связь с его карточкой добавляется после завершения
  параллельной задачи Telegram, чтобы не перезаписать её файлы;
- не изменяются production webhooks, схема доступов и правила покупок;
- не стилизуется внешний NocoDB.

## Критерии приёмки

- администратор входит один раз и перемещается между разделами без повторного входа;
- из CRM открывается любой доступный модуль конкретного человека;
- список приложения включает состояния и доступы без состояния;
- обычный просмотр не создаёт состояние;
- силовые и метаболизм используют один frontend для пользователя и администратора;
- административное сохранение создаёт запись `admin_app_edits`;
- DQS показывает согласованную аналитику и не содержит действий изменения;
- поиск по production-статике не находит названия старой инфраструктуры;
- backend-тесты и проверки frontend-ассетов проходят.
