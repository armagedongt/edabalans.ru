DQS — доработки сайта и интеграций


Назначение: сюда складывать задачи не по внутреннему клиентскому коду DQS, а по сайту, оплатам, продуктовой логике, интеграциям Tilda / Google Sheets / Apps Script / LeadTeh и другим связанным сервисам.


Статус: ПЛАН / НЕ РЕАЛИЗОВАНО


1. Единая таблица покупок пользователей на основе общей ленты оплат Tilda


Исходная ситуация


Tilda уже отправляет оплаты из разных форм в одну общую Google-таблицу. Первый лист остаётся сырой лентой событий: каждая новая покупка добавляется новой строкой подряд. В этой ленте могут быть мастер-класс, дополнительные продукты, консультации, сопровождение, подписка и любые будущие продукты.


Целевая структура


В той же Google-таблице создать отдельную вкладку-реестр пользователей, например «Покупки_по_пользователям».


Одна строка = один уникальный email.
Первый столбец = email.
Дальше отдельные колонки по каждому продукту / услуге / докупке, например:
— Мастер-класс;
— Система рецептов;
— Калории;
— Тренировки;
— Консультация;
— Сопровождение;
— Подписка;
— будущие дополнительные продукты.


Конкретный набор колонок определяется позже после фиксации продуктовой линейки.


Механика Apps Script


При появлении новой строки в листе с общей лентой оплат скрипт должен:
1) прочитать email покупателя и идентификатор / название купленного продукта;
2) нормализовать email, чтобы регистр и случайные пробелы не создавали дублей;
3) найти email на вкладке «Покупки_по_пользователям»;
4) если email отсутствует — создать новую строку пользователя;
5) если email уже есть — использовать существующую строку;
6) определить по таблице соответствий, какой колонке соответствует купленный продукт;
7) записать факт покупки в нужную ячейку;
8) не стирать уже имеющиеся покупки этого пользователя;
9) корректно переживать повторный запуск и по возможности не создавать дублирующие события.


Первый лист остаётся первичным журналом оплат. Второй лист — агрегированным состоянием пользователя, удобным и для автоматизации, и для визуального просмотра вручную.


Нужно отдельно определить формат значения в продуктовых колонках. Базовый вариант — TRUE / пусто. Если понадобится история, можно дополнительно хранить дату первой покупки, последней покупки, количество оплат или статус подписки.


2. Единая страница докупки дополнительных материалов в Tilda Members Area


Сделать одну страницу внутри Members Area, которая показывает разным пользователям разный набор предложений в зависимости от уже купленных продуктов.


Механика страницы


1) Tilda определяет авторизованного пользователя.
2) Код страницы получает email текущего пользователя тем же способом, который уже успешно протестирован для DQS.
3) Код отправляет email в Google Apps Script.
4) Apps Script находит строку пользователя во вкладке «Покупки_по_пользователям».
5) Скрипт возвращает фронтенду набор фактов покупки или сразу номер сценария допродажи.
6) Страница показывает только те продукты, которые этому пользователю ещё имеет смысл предлагать.
7) Уже купленные продукты повторно не показываются.


Не делать шесть отдельных физических страниц Tilda. Предпочтительно одна страница и несколько заранее описанных сценариев отображения внутри неё.


После фиксации продуктовой линейки отдельно составить матрицу примерно из 6 сценариев: какое сочетание уже купленных продуктов соответствует какому набору предложений.


3. Корзина и штатная оплата Tilda на странице докупок


Внешний вид карточек / предложений можно сделать собственным кодом, но сама оплата должна идти через штатную корзину и существующую платёжную систему Tilda.


На страницу нужно добавить штатный блок корзины Tilda.
В собственных кнопках / ссылках карточек прописать корректный вызов корзины и передачу нужного товара / формы оплаты согласно механике Tilda.


Задача: визуал страницы контролируется нашим кодом, но покупка проходит тем же штатным путём, что и остальные оплаты, чтобы новая покупка снова автоматически попадала в общую ленту оплат и затем агрегировалась тем же Apps Script.


4. Связка страницы покупок с Telegram-ботом LeadTeh для персональных допродаж


Цель


Использовать ту же таблицу покупок как единый источник состояния пользователя и для сайта, и для Telegram-бота.


В LeadTeh у контакта должна быть сохранена почта пользователя в стандартном поле email или пользовательской переменной. Эта почта является ключом, по которому бот связывается с реестром покупок.


Механика при запланированном сообщении


1) В нужной точке сценария LeadTeh перед отправкой допродажи запускает блок HTTP-запрос.
2) В запрос в Google Apps Script передаётся email конкретного контакта.
3) Apps Script ищет email во вкладке «Покупки_по_пользователям».
4) Apps Script применяет ту же матрицу продуктовой логики, что используется на странице сайта.
5) В ответ возвращается минимум номер сценария, например upsell_variant = 1…6. При необходимости можно вернуть и отдельные флаги продуктов.
6) LeadTeh записывает значение из JSON-ответа в пользовательскую переменную.
7) Сценарий бота делает развилку по этой переменной и отправляет соответствующее сообщение с нужным набором дополнительных продуктов.


Это предпочтительнее, чем вручную собирать в LeadTeh поиск по Google Sheets и много отдельных условий.


Технически LeadTeh это поддерживает: в сценарии есть блок «HTTP-запрос», который умеет GET/POST, передавать пользовательские переменные и записывать JSON-ответ сервера обратно в переменные для дальнейшей логики. Поэтому Google Apps Script может выступать простым API между ботом и таблицей.


Пример логики ответа Apps Script:
{
  "ok": true,
  "email": "user@example.com",
  "upsell_variant": 3
}


Текст рекламного сообщения лучше хранить и редактировать в LeadTeh. Apps Script должен возвращать именно состояние / номер сценария, а не быть хранилищем Telegram-текстов.


5. Единая продуктовая матрица


Перед реализацией страницы и Telegram-ветвлений нужно отдельно зафиксировать:
— полный список продуктов и услуг;
— как каждый продукт называется в строках, которые присылает Tilda;
— какие названия относятся к одному и тому же продукту / тарифу;
— какие покупки считаются активными, одноразовыми или подписочными;
— какие продукты нельзя предлагать повторно;
— какие продукты можно докупать несколько раз;
— какие сочетания покупок образуют каждый из сценариев допродажи;
— что именно показывается на сайте для каждого сценария;
— какое сообщение уходит в Telegram для каждого сценария.


Желательно, чтобы логика определения сценария хранилась в одном месте — в Apps Script. Тогда сайт и LeadTeh получают один и тот же upsell_variant и не расходятся по логике.


6. Общая архитектура


Tilda формы / оплаты
→ сырой лист «Все оплаты»
→ Apps Script-агрегатор
→ лист «Покупки_по_пользователям»
→ единая функция определения upsell_variant
→ два потребителя:
   а) страница докупок Tilda Members Area;
   б) Telegram-бот LeadTeh перед запланированным сообщением.


Таким образом, Google-таблица становится визуальным реестром покупок, Apps Script — единственным слоем бизнес-логики, а Tilda и LeadTeh только запрашивают готовое состояние пользователя.
