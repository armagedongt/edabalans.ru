# Писатель edabalans.ru

Этот навык — обязательная точка входа для любой генерации или редактуры
пользовательского, учебного, маркетингового и редакционного текста проекта.
Он не хранит второй голос: все правила письма принадлежат только модулю
`platform.content`.

Все пути ниже указаны относительно корня репозитория edabalans.ru — каталога, в
котором лежат `AGENTS.md` и `docs/modules.toml`. Сначала найти этот корень, затем
разрешать пути от него; не разрешать их относительно каталога установленного
skill.

## Обязательный вход

1. Выбрать профиль и режим по короткой карте:
   - «только структура» → `structure` + `structure_only`: не менять ни одного
     авторского символа, кроме точных разрешённых заголовков;
   - голосовая/видео-расшифровка → `transcript_to_article` + `rewrite`: сохранить
     авторский ход, формулировки, примеры и заранее зафиксированные якоря;
   - материал из заметки с нуля → `new_material` + `draft`; полная пересборка
     существующего текста допустима только как явный `creative_rebuild`;
   - расширить или усилить готовую статью → `develop_existing` и минимально
     достаточный `targeted_edit`, `proofread`, `text_only` либо `rewrite`.
   При неоднозначности или сложной границе полностью прочитать
   `authoring-work-profiles-v1.md` и `editing-modes-v1.md`; в ясной задаче эта
   загрузка не обязательна.
   Обязательные границы ясных режимов уже заданы здесь:
   - `structure_only` сохраняет все авторские символы, ссылки и медиа; добавляет
     только заголовки из точного `structural_labels`;
   - `transcript_to_article` удаляет лишь дословные фрагменты из
     `allowed_removals`, сохраняет примеры, ход мысли, anchors, ссылки и медиа и
     работает только на записанный `rewrite_goal`;
   - `targeted_edit` меняет только уникальные исходные фрагменты из
     `editable_scope`; всё между ними остаётся без изменений;
   - `text_only` меняет формулировки внутри всего текста, но сохраняет порядок и
     типы блоков, ссылки, медиа и привязку inline-выделений;
   - `proofread` допускает только орфографию, пунктуацию и явно названное
     согласование; `rewrite` готовой статьи сохраняет anchors и обслуживает
     конкретный `rewrite_goal`; `draft` создаёт новый текст, а
     `creative_rebuild` требует прямого разрешения пересобрать существующий.
2. Для `draft`, `rewrite`, `creative_rebuild`, `targeted_edit` и `text_only`
   полностью прочитать `content/author-voice/writer-contract-v1.md`: даже
   локальная замена формулировки обязана сохранять единый голос, первое лицо и
   экологию резкой подачи. Для `proofread` и `structure_only` он не нужен, если
   границы правки заданы явно и смысл текста не расширяется: здесь достаточно
   исходника, `editable_scope`, сохранения структуры и назначенных validator
   checks.
3. Подключить только применимый источник:
   - точный CTA, ссылка или комментарийный импульс —
     `content/author-voice/editorial-linking-v1.md`;
   - серия, ссылка на старый материал или узел бот-цепочки — тот же документ и
     адресный поиск по каталогу старых материалов;
   - обычная статья сайта, интенсива или курса — держать `h1` вне тела, использовать
     только `h2`/`h3`, абзацы, списки, `strong`/`em`, ссылки, изображения,
     многострочную цитату `>` и единую плашку `:::note ... :::`; полный
     `docs/knowledge-base/ARTICLE_STANDARD.md` читать только при переносе legacy
     HTML или изменении визуального/runtime-контракта, а
     `content/author-voice/article-component-router.md` — только когда в тексте
     действительно нужны продуктовые вставки;
   - полный курс — карточка продукта, существующая программа и структурный
     контракт курса; результатом должен быть согласованный набор дней и
     материалов, а не один пост;
   - визуальная оболочка или поля курса — её визуальный контракт; для обычного
     текста урока он не загружается;
   - продажный текст или упоминание продукта —
     `content/author-voice/product-fact-router.md` и найденные через него владельцы
     текущих фактов.
4. Для новой задачи создать приватный JSON по
   `content/author-voice/author-task.schema.json` и явно записать `work_profile`,
   а при известной площадке — `surface_context`.
   В `required_facts` записать только **существенные проверяемые утверждения**:
   цифры и нормы, медицинский риск или безопасность, причинность, актуальные
   условия продукта и любой факт, ошибка в котором изменит совет или основной
   вывод. Разговорное округление, метафору, иронию и явно приблизительную
   формулировку туда не добавлять, если они не меняют фактический смысл. Для
   `required_facts` добавить непустые fingerprints в `fact_sources`; явные
   запреты задачи записать в `forbidden_claims`. Профиль фактчека определяется
   автоматически по площадке: учебный материал проверяется строго, публичный
   пост — по порогу существенной правды. Явный `fact_check_profile` нужен только
   для исключения из этого правила. Использовать канонические площадки:
   `masterclass_material`, `course_material`, `intensive_article` — учебные;
   `telegram_channel`, `pikabu_article`, `site_article` — публичные. Неизвестное
   имя площадки без явного профиля является ошибкой, а не поводом молча выбрать
   мягкую проверку.
   Собрать pack через `tools/author_workflow.py prepare`. Глубина `light`,
   `standard` или `deep`
   выбирается пропорционально объёму и риску задачи; обычный новый пост использует
   `standard`. Для `proofread`, `structure_only`, `targeted_edit` и `text_only`
   retrieval не выполняется: локальный scope и исходный текст уже задают голос.
   Для профиля «Транскрипт → статья» при изменении фраз используется лёгкий
   retrieval только как защита от пересказа и смены голоса; он не даёт права
   заменять речь Сергея новым текстом.

## Выполнение

Для большого материала из существующих авторских источников и для серии
материалов не схлопывать работу в один прогон. Использовать зависимые слои:

1. собрать максимально полный исходный Markdown или карту переноса без рерайта;
2. проверить сохранность авторских фраз, примеров, изображений и порядка мысли;
3. отдельно выполнить структурную редактуру;
4. оценить получившуюся структуру и только после этого уточнить план смысловой
   доработки;
5. выполнить только необходимые связки, сокращения повторов и дополнения;
6. снова проверить голос, сохранность и достижение задачи материала;
7. отдельным последним процессом работать с источниками.

Результат каждого слоя определяет следующий. Если проверка показала потерю
фактуры или неверную структуру, сначала исправить этот слой, а не продолжать по
изначально придуманному плану. В автономном режиме это внутренний checkpoint, а
не обязательная остановка ради ответа Сергея. Объединять слои можно только в
маленькой однозначной правке либо по прямому разрешению.

Для такой задачи включать **версионность писательского прогона**. До первой
содержательной правки сохранить неизменяемую базовую версию. Каждый слой,
который заметно меняет смысл, структуру или доказательные ссылки, получает новую
версию либо отдельный version record с fingerprint. Минимально различать:

- `source` — полный перенос или исходная авторская сборка;
- `structured` — версия после структурной редактуры;
- `developed` — версия после адресной смысловой доработки;
- `sourced` — версия после отдельного прохода источников.

Не создавать копию после каждой опечатки. Версия нужна там, где по сравнению
«до / после» можно проверить сохранность голоса, фактуры, структуры или
доказательств. Принятую или показанную Сергею версию не перезаписывать. Для
редакторской витрины давать кликабельные ссылки на сопоставимые версии одного
материала.

Состояние серии и итоговый отчёт вести по
`content/author-voice/material-status-v1.md`: отдельно записывать редакторский
этап, проверку Сергеем, проверку источников и доставку. Не называть материал
просто «готовым» и не считать опубликованную по прямой команде версию авторски
утверждённой без отдельного подтверждения Сергея.

Выполнить выбранный режим по границам выше и content contract из pack. Если для
неоднозначного случая были загружены полные нормативные документы, применить их
уточнения. Площадки и продукты поставляют контекст, поля и факты, но не создают
отдельную личность автора.

Если задача добавляет, переставляет или проверяет доказательные ссылки, после
смысловой сборки отдельно выполнить
`content/author-voice/source-integration-pass-v1.md` полностью. Не смешивать его
с основным рерайтом и не схлопывать зависимые прогоны: сначала построить карту
авторского нажима, затем найти кандидатов, оценить отбор и плотность и только
после этого встраивать ссылки. Следующий прогон корректируется по результату
предыдущего. Конфликтующий источник не вставлять и авторский текст не менять —
конфликт выносится Сергею отдельно. После прохода записать дату, версию или
fingerprint текста, версию политики, глубину и статус проверки.

После текста запустить `tools/author_workflow.py validate`. Состояние
`needs_fix` требует исправить машинные ошибки. Для `manual_review_required`
закрыть ровно выданные checks через `author_workflow.py review`, указав по каждому
содержательное пояснение, затем повторить validate с review artifact. Только
`pass` является готовым материалом. В любом режиме один и тот же проваленный слой
исправлять автоматически не более двух раз; затем оставить один существенный
блокер, а не продолжать цикл из-за стилистической неточности.

Если Сергей прямо просит опубликовать готовый обычный текстовый материал курса,
не редактировать `content/masterclass/source-current/` и не запускать code deploy.
Найти стабильный `step_id` через
`tools/publish_course_material.py list`, получить текущую версию через `get`, а
после подготовки вызвать `publish` с pack и validation report. Команда публикации
сама проверяет свежий `pass`, использует optimistic locking и создаёт неизменяемую
версию. После ответа API один раз получить материал
через `get` и сверить версию и содержимое. Анкеты, messenger, DQS, офферы,
рецептурные приложения и tutorial этим инструментом не публикуются. Изменение
структуры курса, карточки, renderer или нового вида оформления остаётся обычной
задачей разработки.

### Быстрая публикация из открытого редактора

Если Сергей сохранил готовый текст в открытом боковом редакторе и просит внести
его на сайт, применяется короткий маршрут. Перед публикацией сделать только
быструю корректуру: исправить орфографию, пунктуацию и очевидные опечатки без
переписывания текста. Затем сразу опубликовать сохранённый файл штатным API.

Не сравнивать полный текст с опубликованной версией, не перечитывать материал
заново и не выполнять отдельную содержательную сверку после ответа API. Номер
версии передаётся API только как техническая защита от параллельной перезаписи;
если API вернул конфликт версии, сообщить Сергею и запросить дальнейшее решение.
Для такого маршрута не нужны Git, code deploy и промежуточные ручные загрузки.

## Проверка и память

Применить только проверки, назначенные выбранным режимом в
`editing-modes-v1.md` и `writer-contract-v1.md`.

Существенную правку Сергея сохранить через `tools/record_author_correction.py`
или `tools/record_author_correction_from_codex.py`. Новое устойчивое правило
вносить в единственного владельца соответствующего правила внутри
`content/author-voice/` и связанные машинные доказательства модуля
`platform.content`. Не создавать правила письма в карточках продуктов, курсах,
Telegram-модулях, `work/` или новом паспорте голоса.

## Редакторская витрина

Фраза Сергея **«покажи редакторскую витрину»** означает: вывести прямо в чат
компактный список рабочих текстовых файлов с понятными названиями и кликабельными
абсолютными локальными ссылками. При нажатии файл должен открываться в правой
редактируемой панели Codex. Материалы группировать по этапам или задачам; несколько
версий одного фрагмента можно дать ссылками через запятую. Полный текст в чат при
этом не копировать, если Сергей отдельно его не попросил.
