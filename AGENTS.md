# Правила работы с edabalans.ru

Единая платформа сайта, курсов, приложений и CRM. Писать и объяснять по-русски.

## Вход в задачу

1. Открыть `docs/README.md`, найти `module_id` в `docs/modules.toml` и карточку модуля.
   При первом упоминании сайта, продукта, услуги, тарифа, домена, канала или бота
   открыть `docs/knowledge-base/PROJECT_IDENTITY.md` (`products.catalog`) и через
   него проверить нужный факт у владельца до ответа/записи. Это относится и к
   обычному упоминанию, и к продолжающемуся чату. Сокращение Сергея — ключ поиска,
   не новое название: «мой сайт»/«похудение.рф» разрешать в полный канонический
   адрес; точные названия продуктов/тарифов брать из `product-catalog/core`,
   цены — из активного pricing, контакты — из карты и действующих настроек.
2. Читать только нужные каноны карточки и затронутые файлы. `PROJECT_CONTEXT.md` нужен
   для цели/границ продукта, `ARCHITECTURE.md` — для архитектуры и общих договоров;
   не читать их целиком для локальной правки. Соседей, `work/` и планы читать по зависимости.
   В старом смешанном checkout сверять канон и registry со свежим `origin/main`;
   отсутствующий локально документ читать из этой ревизии, не создавать замену.
3. Найти существующую функцию и владельца факта до создания новой логики или структуры.
   Менять источник истины, а не отображение или копию.
4. До завершения обновить изменившийся канон, карточку и ownership/relations. Техническую
   классификацию выполнить самому; Сергей решает только реальную развилку смысла/границ.
   Общий порядок — `docs/knowledge-base/MODULE_DEVELOPMENT_STANDARD.md`.

## Работа и проверки

- Ясную маленькую задачу сразу выполнить и проверить. Текст в HTML сам по себе не
  является изменением программы: `copy-only` не запускает code/security/test-review,
  migration, backup или полный прогон проекта без соответствующего риска.
- Для средней задачи собрать существенные вопросы одним пакетом. При реальной развилке
  большой задачи предложить первый ограниченный рабочий результат либо заранее ТЗ;
  после выбора сохранить границы, этапы и критерии готовности.
- Слово «автономно» не отменяет предстартовый аудит. Применить глобальный skill
  `sergey-development-workflow`: найти известное самому, спросить только решение владельца,
  проверять важные зависимые результаты временными субагентами без отдельных разрешений.
- Маленькой механической правке достаточно diff и ближайшей прямой проверки;
  поведению — профильное ревью. Специалистов добавлять по фактическому риску.
  Не дублировать проверки одного результата; максимум две содержательные волны.
  Подробный порядок — `docs/AI_DEVELOPMENT_WORKFLOW.md`.
- Готовый текст Сергея переносить дословно; смысловые замены согласовать. Служебные
  объяснения разработки не переносить в пользовательский текст.
- Для средней/крупной работы применять `sergey-development-workflow`; остальные skills —
  по задаче. Preview только по прямой просьбе; browser — для изменённого UI/границы,
  которую нельзя дешевле проверить кодом, API, test или детерминированным render.

## Рабочая папка и выпуск

- Перед записью проверить папку, ветку, состояние и владельца изменения. В общей папке
  один пишущий поток; отсутствие ответа не означает свободу. Не делать там
  switch/pull/rebase/reset/stash и не включать чужую работу в свой выпуск.
  Изоляция и передача — `docs/CHAT_WORKSTREAMS.md`; один canonical source не менять параллельно.
- Готовый проверенный набор перенести поверх свежего `origin/main` и выполнить push;
  черновики, запрет выпуска, явно локальную, незаконченную или конфликтующую работу не принимать.
  Push в удалённый `main` запускает выпуск: при «пока без сервера»/«покажи перед сервером»
  сохранить рабочую ветку и не отправлять её в публикующий `main` до разрешения.
  Точные границы, исключения и подтверждения — `docs/knowledge-base/OWNER_PROJECT_GUIDE.md`.
- Не спрашивать про штатные commit/push/CI/retry. Если необходимо существенное подтверждение,
  сначала поместить короткую готовую фразу в системный буфер, затем показать код-блок
  с последствиями. Финал: что локально, что в `main`, что в production.
- `docs/generated/*` — build output: CI/production пересобирают его из целевого commit.
  Не создавать отдельный commit только ради обновления generated.

## Обязательные границы

- Не добавлять новый сайт/кабинет, Telegram-движок или MAX без отдельной задачи.
  Существующие адаптеры входа используют один `user_id`, права и материалы;
  не вводить второй кабинет, набор прав или дополнительный вход.
- Публичная главная сейчас: `https://похудение-это-есть.рф/` на Tilda;
  серверные публичные страницы: `https://edabalans.ru/<путь>`. Отдельная будущая
  цель после ухода с Tilda — `https://похудение.рф/<путь>` по доменному runbook;
  её не подставлять вместо текущего сайта. Админка сейчас `/admin`, будущий отдельный host —
  `admin.edabalans.ru`; API/webhook — `api.edabalans.ru`. `app.edabalans.ru` только
  для самостоятельных приложений, не новых админок. Рабочие URL, включая `/weather`,
  DNS и Caddy не переносить попутно; подробности — `docs/ADMIN_ARCHITECTURE.md`.
- PostgreSQL/backend/NocoDB наружу только через Caddy; открыты 22/80/443, 5432 закрыт.
- В Git не помещать `.env`, секреты, дампы, персональные данные и реальные выгрузки.
  `/srv/edabalans-private` не сканировать и не менять без отдельного прямого поручения.
- Перед импортом персональных данных проверить backup и восстановление. Migration,
  разрушительные действия, массовые сообщения, новый расход, изменения Tilda/платежей
  и столкновение независимых изменений требуют предусмотренного подтверждения.
  До разрушительной операции назвать точную цель и последствия.
- Legacy переносить по фактическому коду/таблицам; production-хуки Tilda/LeadTeh
  не переключать и Google-данные не удалять без явного подтверждения.

## Маршруты по задаче

| Задача | Что обязательно открыть/применить |
|---|---|
| Упоминание или проверка названия сайта, продукта, услуги, тарифа, домена, канала или бота | `docs/knowledge-base/PROJECT_IDENTITY.md` → владелец конкретного факта; `products.catalog`, даже если ничего не переименовываем |
| Рецепт, каталог продуктов/КБЖУ, приложение рецептов, его материал, карточка или доступ | `docs/knowledge-base/RECIPE_CONTOUR.md` → нужная ветка и владелец; `products.recipes`, без второго каталога/стандарта в чате |
| Любой читательский, учебный, маркетинговый или редакционный текст | выполнять только через skill `edabalans-writer`; канон `content/author-voice/skill/edabalans-writer/SKILL.md`, маршрут `docs/knowledge-base/EDITORIAL_PRODUCT_SYSTEM.md`, общение `docs/knowledge-base/CONTENT_COLLABORATION_STANDARD.md` |
| Источники, накопленный контекст, дубли и provenance | skill `edabalans-librarian`, серверная карта `platform.knowledge`; при недоступности MCP не заводить параллельную библиотеку |
| Генерация/правка изображения, SVG, иконки | Задача «Художник», `content/design-workflow/image-generation-protocol.md`; не заводить второго постоянного генератора |
| Любые голосовые, аудио и видео | Только задача «Голосовые — приём и расшифровка», `docs/knowledge-base/VOICE_TRANSCRIPTION_WORKFLOW.md`; до приёма не расшифровывать самостоятельно, не менять исходник и не публиковать производные |
| Курс: создание или изменение общей оболочки/входа/загрузки/навигации | Полностью `docs/knowledge-base/COURSE_APPLICATION_STANDARD.md`, затем продуктовые структурный, визуальный и runtime-контракты |
| Видео и плеер | `backend/app/static/video-player-development/README.md`; готовый профиль/оболочка, без копии движка; неоднозначный профиль согласовать |
| Название/описание продукта или тарифа | `docs/knowledge-base/PRODUCT_CATALOG.md`; штатная редакция `product-catalog/core`, без migration ради текста |
| Административный интерфейс | `docs/ADMIN_ARCHITECTURE.md`; единый `admin_catalog`, без отдельной админки/меню |
| Telegram-модуль | Общий стандарт модуля плюс `docs/knowledge-base/modules/telegram/MODULE_DEVELOPMENT_STANDARD.md`; sequence/edges из runtime graph |
| DQS/силовые legacy | `legacy/google/README.md`, схемы и код; не выполнять `SUPERSEDED_INTEGRATIONS_PLAN.md` |
| Изменение/импорт/очистка/выгрузка тегов | Полностью `docs/TAG_RULES.md` |
| Доступность, DNS, аварии, уведомления, restart, защита рекламы | `docs/runtime-health/README.md`, `operations.health`; версию сверять с принятым `main` и production |
| Deploy, backup, restore | `docs/OPERATIONS.md` |

Единый писательский канон принадлежит только модулю `platform.content`; продукты и
временные файлы поставляют факты, но не создают собственных правил голоса/редактуры.
Перед первой содержательной работой с текстами/источниками нового чата выполнить
`python tools/install_edabalans_writer_skill.py --check` и
`python tools/install_edabalans_librarian_skill.py --check`; устаревшие runtime обновить
из свежего канона и перечитать проектный skill. Библиотекарь отвечает за источники,
Писарь — только за текст; предложение, цены, права, дизайн и публикация имеют своих владельцев.
Технические сообщения направлять в `@TetrisgfgfgfBot`, продуктовые — в основной чат продукта;
технический чат не принимает редакционных решений. Маршрут черновиков постов — `docs/CHAT_WORKSTREAMS.md`.

## Источники и планы

`docs/modules.toml` владеет ownership/relations; карточки — человеческим смыслом модуля;
канонические документы/код/runtime — фактами. Wiki/generated показывают их. У каждого
tracked-объекта один module owner. Термины — в общем стандарте модулей, статусы — в `docs/README.md`.
`work/` — временный контекст. В `docs/plans/` писать только по явному решению «на потом»;
метаданные и правила — `docs/plans/README.md`. Незаконченная работа планом не становится.
