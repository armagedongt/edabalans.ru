# Правила работы с edabalans.ru

## Обязательный маршрут нового чата

1. Начать с `docs/README.md`.
2. Перед изменениями прочитать `PROJECT_CONTEXT.md` и `ARCHITECTURE.md` в объёме задачи.
3. Найти затронутый `module_id` в `docs/modules.toml` или в сгенерированной карте
   `docs/generated/module-map.md` и открыть его карточку.
4. Проверить канонические источники, соседние модули, активные `work/` и только явно
   отложенные планы этого модуля.
5. Сначала искать существующую функцию и владельца факта; не создавать второй источник
   логики, таблицу, тег, формат или новый модуль без необходимости.
6. Менять источник истины, а не его отображение или копию. Вместе с поведением обновлять
   карточку, ownership/relations и релевантный канонический документ.
7. До завершения задачи самому определить, появилась ли/изменилась функция или граница
   модуля. Если задача затрагивает несколько модулей, создаёт новый или допускает две
   разумные границы, кратко предложить владельцу устойчивый вариант и спросить только
   решение, которое он действительно должен принять. Не перекладывать на владельца
   техническую классификацию.
8. Выполнить проверки пропорционально риску. `docs/generated/*` — build output:
   обычный чат не создаёт отдельный commit только ради него; CI и production
   пересобирают его из целевого commit перед тестами и запуском.

## Общий язык

- **Модуль** — самостоятельная функциональная возможность внутри области/продукта.
- **Функция** — пользовательское поведение внутри модуля.
- **Компонент** — экран, API route, таблица, job, файл, скрипт, migration или документ.
- **Программный символ** — function/class/method в коде.
- Каждый tracked-файл и технический объект имеет одного module owner; потребителей может
  быть несколько. Бесхозный объект — ошибка классификации, а не постоянный «прочий» модуль.

## Авторские материалы

Все задачи по созданию, редактуре, сокращению, расширению и структурированию
читательского текста edabalans.ru выполнять только через skill `edabalans-writer`.
Единый писательский канон принадлежит только модулю `platform.content`; продукты
и временные рабочие файлы не создают отдельные правила авторского голоса.

## Масштаб работы и общение с владельцем

- Маленькую ясную задачу исследовать в затронутой границе, сразу выполнить и проверить.
- Для средней задачи одним пакетом спросить только то, что меняет результат или заметно
  экономит ручную работу.
- Для крупной или неоднозначной задачи сначала исследовать факты и практики, затем
  согласовать поведение/ТЗ и реализовать.
- Проектное правило пропорциональности важнее общего review-ритуала skill: маленькой
  механической правке достаточно diff и ближайшей прямой проверки без отдельного
  reviewer. Изменение поведения проходит один профильный review; test/security/infra
  reviewers добавляются только при соответствующем риске. Вторая волна нужна только
  после содержательного исправления первой.
- Preview показывать только по прямой просьбе. Browser использовать для реально
  изменённого интерактивного/адаптивного UI или браузерной границы, которую нельзя
  дешевле проверить кодом, API, test или детерминированным render.
- Режим публикации для владельца определён в `docs/knowledge-base/OWNER_PROJECT_GUIDE.md`.
  Без явного «пока без сервера» или «покажи перед сервером» после готовой обычной задачи
  автономно выполнить commit/push/deploy. Решения, нужные для результата, собрать в начале
  одним пакетом; не останавливать готовую работу из-за технической детали. Повторно
  остановиться только при migration или импорте данных, массовом сообщении реальным людям,
  изменении Tilda/платёжной настройки, новом сервисе/расходе, разрушительном/неожиданном
  состоянии, нехватке полномочий или столкновении чатов в одном canonical source.
- Не превращать штатные commit/push/CI/retry в сообщения владельцу. Сообщать только выпуск,
  конкретно нужное действие владельца или сохраняющийся после нескольких попыток блокер.
- Документацию вести по-русски. Сложные объяснения давать владельцу простыми словами:
  он не обязан знать Git, сервер и программирование.
- Для средней и крупной задачи применять глобальный skill `sergey-development-workflow`.
  Другие skills включать только по их trigger, а не ритуально.

## Чистая линия production

- `main` — только чистая опубликованная линия. Не использовать её рабочую папку для
  незавершённой разработки, черновиков, экспортов, баз-превью или временных файлов.
- Любая работа начинается в отдельной ветке/worktree от актуального `origin/main`.
  В `main` попадает только готовый, проверенный и изолированный результат.
- Если основная папка уже грязная, не смешивать её состояние со следующим выпуском:
  сначала сохранить известные изменения в отдельную локальную ветку или backup,
  затем выпускать из свежего worktree. Ничего не удалять или не переносить вслепую.

## Источники истины и планы

- `docs/modules.toml` — машинная маршрутизация, ownership и связи.
- `docs/knowledge-base/modules/catalog/` — единственные человеческие карточки модулей.
- Канонические Markdown/код/runtime-данные владеют своими фактами; Wiki и
  `docs/generated/*` только показывают их.
- `work/` — временный контекст активной работы, не база фактов и не планы.
- В `docs/plans/` записывать идею только после явного «положи в планы» или ясного решения
  владельца «на потом». Незавершённая или ещё не deployed работа планом не становится.
- Новый plan обязан иметь `module_id` либо `cross_project: true`, дату и
  `origin: owner-explicit`. Не ставить `owner-explicit` без явной команды владельца.
- Статус документа: только `current`, `draft`, `planned`, `archived`. Состояние
  реализации хранить отдельно: `implemented`, `in_development`, `planned`, `archived`.

## Неподвижные ограничения

- Не добавлять Telegram-движок, MAX, новый сайт или личный кабинет без отдельной задачи.
- В текущем ЛК Tilda — единственный пользовательский вход. Email брать только из
  авторизованного профиля Tilda; не добавлять повторный email, пароль, код или отдельную
  пользовательскую сессию без новой задачи.
- Не публиковать PostgreSQL, backend или NocoDB в обход Caddy; наружу только 22/80/443,
  порт 5432 закрыт.
- Не помещать в Git `.env`, секреты, дампы, персональные данные или реальные выгрузки.
- До импорта персональных данных проверить backup и восстановление.
- Apps Script переносить по фактическому коду и таблицам. Не переключать production-хуки
  Tilda/LeadTeh и не удалять Google-данные без явного подтверждения владельца.
- Перед разрушительной операцией назвать точную цель и последствия простыми словами.

## Специальные маршруты

- Создание, существенное изменение, разделение, объединение или удаление любого модуля:
  `docs/knowledge-base/MODULE_DEVELOPMENT_STANDARD.md`.
- Любое написание, переписывание, сокращение, расширение, корректура или
  структурирование пользовательского, учебного, маркетингового и редакционного
  текста выполнять только через skill `edabalans-writer`. Его канонический
  источник находится в `content/author-voice/skill/edabalans-writer/SKILL.md`.
  Единый писательский канон принадлежит только модулю `platform.content`:
  голосом и аргументацией владеет `content/author-voice/writer-contract-v1.md`,
  разрешениями редактуры — соседний `editing-modes-v1.md`, а общим оформлением
  статей сайта и материалов курсов — `docs/knowledge-base/ARTICLE_STANDARD.md`.
  Продуктовые и технические модули поставляют факты и ограничения формата, но не
  заводят собственные правила голоса, редактуры или оформления авторского текста.
- Telegram-модуль: общий стандарт дополняется
  `docs/knowledge-base/modules/telegram/MODULE_DEVELOPMENT_STANDARD.md`; общий перечень
  модулей берётся из `docs/modules.toml`, исполняемые sequence/edges — из runtime graph.
- DQS/силовые legacy: дополнительно читать `legacy/google/README.md`, требования, схемы
  листов и фактический legacy-код; не реализовывать исторический
  `legacy/google/dqs/SUPERSEDED_INTEGRATIONS_PLAN.md`.
- Теги: перед очисткой, переименованием, объединением, импортом или обратной выгрузкой
  полностью читать `docs/TAG_RULES.md`.
- Production и эксплуатация: `docs/OPERATIONS.md`.
- Параллельные чаты: `docs/CHAT_WORKSTREAMS.md`; два потока не меняют один canonical
  source одновременно.
