# Контракт интеграции с CRM Core

Этот документ описывает будущие точки соединения и не меняет текущую CRM.

## Telegram-модуль читает из CRM

- `users.id` — единый UUID человека;
- `messenger_accounts` — Telegram user/chat id, username, статус блокировки;
- `products`, `payments`, `accesses` — покупки и права доступа;
- `tags`, `user_tags` — бизнес-сегменты;
- `attribution_events` — первый/последний источник и история касаний.

## Telegram-модуль записывает в CRM

- новый или связанный аккаунт мессенджера;
- событие перехода по deep-link;
- полученные от пользователя сообщения и действия;
- бизнес-тег только как явный результат сценария.

Технический прогресс цепочки тегом не является. Он хранится в
`telegram.sequence_runs` и показывается в карточке пользователя как шкала:
версия → выполнено шагов → следующий шаг → время → ошибка.

## Команды из карточки клиента

Общая админка должна вызывать сервис Telegram-модуля:

- отправить ручное сообщение;
- поставить активную цепочку на паузу;
- продолжить цепочку;
- остановить цепочку;
- запустить опубликованную версию цепочки;
- повторить упавшую доставку.

Каждая команда создаёт аудит-запись: кто, когда, для какого пользователя и что
сделал. Ручная отправка по умолчанию не меняет указатель следующего шага.

## Deep-link и атрибуция

Админ создаёт внутренний `slug`, источник, площадку, кампанию и набор действий.
Публичная ссылка имеет вид `https://t.me/<bot>?start=<token>`. Токен короткий,
не содержит персональных данных и разрешается сервером в запись tracking link.
При `/start` CRM получает attribution event, а правила ссылки могут добавить тег
или запустить цепочку.

## До объединения кода нужно согласовать

1. Финальные имена таблиц и моделей CRM Core.
2. Как backend получает текущего администратора и пишет audit log.
3. Очередь/планировщик и способ блокировки конкурентных доставок.
4. Модель хранения входящих и исходящих сообщений.
5. Политику удаления и выгрузки персональных данных.
# Восстановление доступа старого клиента

Исторические покупки и LeadTeh-теги никогда не выдают доступ автоматически.

1. Владелец отправляет человеку ссылку регистрации в Tilda Members Area.
2. Затем отправляет ссылку специального сценария Telegram.
3. Бот просит email, находит существующего человека по Telegram ID и привязывает email
   только если он не занят другим `user_id`.
4. CRM переводит человека в состояние `pending`; конфликт email — в `conflict`.
5. Владелец сверяет старую покупку, группы Tilda и нужные ресурсы, вручную выдаёт доступ
   и завершает проверку.

Для главного бесплатного интенсива повторный вход определяется по истории запуска
сценария. Мигрированный тег `Первое посещение` заполняет `main_scenario_seen_at` и служит
начальной исторической подсказкой: такой человек получает оглавление без повторного
приветственного блока.
