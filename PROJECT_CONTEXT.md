## Канон входа в текущий личный кабинет

Новый покупатель входит в собственный кабинет `https://похудение-это-есть.рф/lk` по email
и выданному паролю. Backend проверяет хеш пароля, создаёт непрозрачную серверную
сессию и каждый раз читает продуктовые права из PostgreSQL.

Tilda Members Area остаётся только совместимым входом для прежних пользователей и
старых необновляемых материалов. Оба входа сопоставляются с одним внутренним
`user_id`, покупками и правами; отдельного второго кабинета и копии данных нет.

1. ЦЕЛЬ

Построить собственную российскую инфраструктуру, на которой постепенно будут работать:
— DQS / «Баланс продуктовых категорий»;
— приложение силовых тренировок;
— Telegram-бот;
— MAX-бот;
— единая база пользователей, покупок, доступов и тегов;
— формы и webhook Tilda;
— специализированные админки;
— в будущем собственный личный кабинет и при необходимости весь сайт.

Главный принцип: интерфейсы могут меняться, но данные, user_id и backend остаются центральными и независимыми от Tilda, Telegram, MAX и других внешних сервисов.

2. ДОМЕНЫ

Основной публичный домен: `похудение-это-есть.рф`.

Функции сайта используют `/api/*`, `/apps/*`, `/lk` и `/intensive`; внутренние
переходы — пути от корня. Административные `/admin` и `/crm` открываются на
`admin.похудение-это-есть.рф`. NocoDB — только loopback/SSH.

Сокращение «похудение.рф» всегда означает этот длинный домен, не отдельный адрес.
`edabalans.ru` — историческое имя репозитория и совместимых host. Прежние
`api.`/`app.` не используются в новых ссылках. Погода и игра также доступны на
текущем административном host; отдельный preview Щербаковой остаётся исключением
на старом app-host. Архив Tilda и старые webhook не переключать попутно.

3. ИНФРАСТРУКТУРА СТАРТА

На первом этапе: одна обычная VM/VPS в РФ.

На VM:
— Linux (готовый образ Ubuntu);
— Docker;
— PostgreSQL;
— backend;
— NocoDB или Baserow;
— reverse proxy + HTTPS;
— автоматические backup и мониторинг.

Это не временная «урезанная» архитектура. Компоненты сразу делаются стандартными и переносимыми. При росте их можно разнести по разным VM или Managed-сервисам без переписывания приложений.

4. РОЛИ КОМПОНЕНТОВ

PostgreSQL = центральная база данных.
Backend = серверная логика / «мозг» системы.
NocoDB/Baserow = универсальная техническая админка для просмотра и ручного редактирования таблиц.
Специализированные админки = удобные интерфейсы для конкретных задач: DQS, силовые, рассылки и т. д.
GitHub = официальное хранилище кода, конфигурации и истории версий.
Сервер = место, где код реально запущен.

6. АРХИВ TILDA И ДЕЙСТВУЮЩИЙ КАБИНЕТ

До переноса Tilda использовалась для публичных страниц, продаж, Members Area
и закрытых вставок приложений. Эта схема сохраняется только в архиве и совместимых
адаптерах. Установленные T123 могут обращаться к старым техническим host;
не переносить такие адреса в новые пользовательские сценарии.

Сайт и авторизация уже работают на собственном сервере. Backend проверяет
серверную сессию и права; email из JavaScript страницы не является доказательством
личности. Архив и его webhook не перенастраиваются попутно.

7. СОБСТВЕННАЯ ИДЕНТИФИКАЦИЯ ПОЛЬЗОВАТЕЛЯ

В центральной БД у каждого человека собственный стабильный user_id.

Email, Telegram ID, MAX ID, Tilda-идентификаторы, покупки и другие внешние идентификаторы привязываются к user_id, но не являются главным ID системы.

Пример:
user_id 18427
  email
  telegram_id
  max_id
  products/accesses

Это позволяет менять Tilda, мессенджеры и frontend без миграции самой пользовательской истории.

8. ПОКУПКИ И ДОСТУПЫ

Tilda/платёжная система передаёт данные в российский backend.

Нужно различать:
— создан заказ;
— реально подтверждена оплата.

Источник истины по оплате желательно получать через серверное уведомление платёжной системы.

После подтверждения:
— покупка записывается в PostgreSQL;
— обновляются доступы;
— Telegram/MAX сразу видят изменение;
— могут запускаться/останавливаться цепочки;
— пользователю можно автоматически отправить сообщение.

9. TELEGRAM И MAX — ОДНА MESSAGING-СИСТЕМА

Telegram и MAX — не два отдельных проекта, а два канала одного messaging backend.

Общее:
— пользователи;
— покупки;
— теги;
— сегменты;
— автоматические цепочки;
— тексты;
— условия;
— разовые рассылки;
— статистика.

Разное только технические адаптеры:
— telegram adapter;
— max adapter.

Боты не общаются друг с другом. Оба работают с одной PostgreSQL.

10. АВТОМАТИЧЕСКИЕ ЦЕПОЧКИ БОТА

Основная модель — последовательность блоков.

Поддерживаемые типы блоков со временем:
MESSAGE
DELAY
CONDITION
PHOTO
VIDEO
VIDEO_NOTE
VOICE
BUTTONS
GOTO
STOP

Пример:
1. MESSAGE
2. DELAY 24h
3. MESSAGE
4. CONDITION: куплен МК?
   YES → цепочка «После покупки»
   NO → блок 5
5. VIDEO
6. DELAY 48h
7. MESSAGE

Backend исполняет цепочки автоматически. Сами структуры и контент желательно хранить в БД, а не в коде.

11. ДВЕ БАЗОВЫЕ ЦЕПОЧКИ

A. До покупки
— старт после входа пользователя в бота;
— последовательность сообщений по времени;
— периодические проверки условий;
— прекращение рекламной цепочки после нужной покупки.

B. После покупки
— запускается после подтверждённой покупки;
— последовательность клиентских сообщений;
— периодические проверки дополнительных покупок;
— ветвление по результатам.

Не требуется переносить состояние прохождения старых цепочек LeadTeh при миграции: старая база подписчиков переносится, новые рассылки и цепочки стартуют уже в новой системе.

12. РАЗОВЫЕ РАССЫЛКИ

Специализированная админка должна позволять:
— создать рассылку;
— выбрать Telegram / MAX / оба;
— выбрать сегмент: все, купили, не купили, по продукту, по тегу;
— написать текст;
— добавить медиа и кнопки;
— отправить тест себе;
— запустить сразу или по расписанию;
— видеть прогресс, ошибки, блокировки.

Разовая рассылка создаётся через API/БД, GitHub для неё не нужен.

13. УПРАВЛЕНИЕ ЦЕПОЧКАМИ

Контент и стандартную структуру цепочки лучше редактировать через собственную простую админку:
— список блоков;
— добавить блок;
— удалить;
— переместить вверх/вниз;
— изменить задержку;
— отредактировать текст/медиа;
— настроить переходы условия.

Изменять backend-код требуется только когда появляется новый тип блока или новая системная возможность.

14. LEADTEH — ПЕРЕХОДНЫЙ ПЕРИОД

Пока LeadTeh оплачивается и используется:
LeadTeh → HTTP API → похудение-это-есть.рф/api → PostgreSQL → ответ LeadTeh.

Проверки вроде:
has_product()
has_access()
get_upsell_variant()
и другие условия сразу пишутся как общие backend-функции.

После переноса Telegram на сервер эти же функции используются напрямую самим ботом, без переписывания бизнес-логики.

15. МИГРАЦИЯ TELEGRAM С LEADTEH

Сначала полностью сделать и протестировать систему на отдельном тестовом Telegram-боте.

Когда готово:
— экспортировать из LeadTeh telegram_id/chat_id и нужные теги;
— импортировать в PostgreSQL;
— остановить старые рассылки;
— отключить основной токен бота от LeadTeh;
— подключить тот же токен к собственному webhook;
— username основного бота и существующие чаты пользователей сохраняются;
— запустить новые рассылки уже с сервера.

Обратный переход в LeadTeh также должен быть возможен через экспорт пользователей/тегов.

16. DQS И СИЛОВЫЕ

Оба приложения работают через один общий API и PostgreSQL.

DQS:
frontend → похудение-это-есть.рф/api/dqs/... → PostgreSQL.

Силовые:
frontend → похудение-это-есть.рф/api/strength/... → PostgreSQL.

Специализированные админки остаются отдельными по UX, но работают с общей системой пользователей и общей БД.

Текущие данные Google Sheets позже мигрируются в PostgreSQL через одноразовые migration-скрипты.

17. ФОРМЫ TILDA

Подтверждённые заказы отправляются webhook напрямую:
Tilda → похудение-это-есть.рф/api/integrations/tilda/payments → PostgreSQL.

На переходном этапе можно параллельно сохранять существующие интеграции, если это требуется.

18. NOCODB / BASEROW

Это не backend, а универсальная техническая админка.

Использование:
— посмотреть Users;
— Purchases;
— Sessions;
— Sets;
— Bot Users;
— Tags;
— сырые данные;
— вручную исправить отдельное значение.

Для сложного UX делаются отдельные специализированные админки.

Предварительно предпочтение: NocoDB как визуальная оболочка над PostgreSQL. Финальный выбор сделать перед установкой после сравнения актуальных возможностей.

19. МОНИТОРИНГ И НАДЁЖНОСТЬ

Обязательно автоматизировать:
— health-check backend;
— доступность PostgreSQL;
— свободное место на диске;
— RAM/CPU;
— успешность backup;
— Telegram-уведомление при проблеме.

Docker-контейнеры настраиваются на автоматический restart.

Backup PostgreSQL автоматически ежедневно → отдельное российское хранилище.

20. МАСШТАБИРОВАНИЕ

Старт:
одна VM
  PostgreSQL
  backend
  NocoDB

При росте:
— увеличить CPU/RAM VM;
— затем при необходимости вынести PostgreSQL в Managed PostgreSQL;
— backend в отдельную VM/serverless;
— NocoDB отдельно;
— Object Storage отдельно.

Для Tilda, мобильных приложений и ботов ничего принципиально не меняется, поскольку они обращаются к одному каноническому origin и его `/api`.

21. БУДУЩИЕ МОБИЛЬНЫЕ ПРИЛОЖЕНИЯ

iOS/Android становятся ещё одним frontend той же системы:
мобильное приложение → похудение-это-есть.рф/api → PostgreSQL.

Не требуется создавать отдельную базу или backend для телефона.

22. ИСТОРИЯ ПЕРЕХОДА К СОБСТВЕННОМУ САЙТУ И КАБИНЕТУ

Следующие этапы выполнены; это история, а не текущая очередь переноса.

Этап 1:
Tilda = сайт + продажи + Members Area.
Сервер = backend + приложения + база + боты.

Этап 2:
Tilda = публичные страницы/лендинги.
Сервер = login + личный кабинет + приложения + покупки + доступы.

Этап 3 — выполнен для технической платформы:
Перенос публичного сайта и оплат на собственный сервер завершён 18.10.2026;
основной origin — `похудение-это-есть.рф`. Архив Tilda и legacy-webhook имеют
отдельную границу совместимости, описанную в доменном runbook.

23. РАБОТА С CHATGPT / CODEX

ChatGPT:
— обсуждение продукта;
— архитектура;
— постановка задач;
— принятие решений.

Codex:
— работа непосредственно с реальным GitHub-репозиторием;
— изменение файлов;
— тесты;
— refactoring;
— подготовка deploy.

GitHub должен стать официальной технической памятью проекта.
Важные принятые решения фиксируются в docs/*.md и AGENTS.md, а не существуют только внутри чатов.

Целевая рабочая схема:
пользователь голосом/текстом формулирует изменение → ChatGPT/Codex → GitHub → test → production → сервер.

Для операционных задач вроде разовой рассылки:
ChatGPT/админка → защищённый backend API → PostgreSQL → Telegram/MAX.

24. ИСХОДНЫЙ ЧЕК-ЛИСТ РАЗВОРАЧИВАНИЯ (ВЫПОЛНЕН)

1. Провайдер VM: предварительно Timeweb Cloud / Yandex Cloud / Selectel.
2. Стартовая конфигурация VM: ориентир 2 vCPU, 4 ГБ RAM, 40–50 ГБ SSD/NVMe.
3. NocoDB или Baserow.
4. Язык backend: предварительно Python + FastAPI либо Node.js. Нужно выбрать один стек и дальше его придерживаться.
5. Создать приватный GitHub-репозиторий.
6. Поддерживать DNS единого origin `похудение-это-есть.рф` по доменному runbook.
7. Поднять Docker/HTTPS/PostgreSQL/backend/admin.
8. Настроить monitoring + backup.
9. Первым пилотным сервисом подключить силовые или Telegram test bot.

25. ПРИНЦИП РАЗРАБОТКИ

Не строить отдельную инфраструктуру под каждое приложение.

Один фундамент:
— один user_id;
— одна PostgreSQL;
— один backend/API;
— одна messaging-система;
— один GitHub-репозиторий на старте;
— универсальная техническая админка;
— отдельные специализированные frontend/admin интерфейсы только там, где они реально нужны.

Это позволяет постепенно переносить существующую систему без одномоментного отказа от Tilda, LeadTeh и Google.
